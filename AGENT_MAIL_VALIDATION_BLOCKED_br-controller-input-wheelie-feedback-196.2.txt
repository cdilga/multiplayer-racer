ROOT CAUSE: shaping is applied DESTRUCTIVELY inside ControlMapper.setTouchInput()
(static/js/input/ControlMapper.js:113-123). It mutates this.touchInput.steering
with the shaped value and then copies that into debugValues.touchRaw. This:
  1. Breaks the canonical touch contract established by the DEPENDENCY bead
     br-controller-input-wheelie-feedback-196.1 (touch input passes through as
     the canonical {steering,accel,braking,fire} shape). 196.2 depends on 196.1;
     it must not retroactively break 196.1's passing tests.
  2. Corrupts the "raw" debug/overlay channel: touchRaw no longer exposes the
     raw touch value, so any overlay/test reading touchRaw is now wrong.

ADDITIONAL FINDINGS (not the gating blocker, but fix while in here):
  - Dead code / unmet sub-criterion: _snapToZero() and the steeringSnapThreshold
    option (0.03) exist but are NEVER called in _shapeSteering()
    (ControlMapper.js:103-111). The acceptance lists "snap-to-zero" as a unit-CI
    sub-criterion and the bead asks for snap-to-zero below ~0.03 after shaping.
    As implemented, sub-threshold steering only decays asymptotically via the
    low-pass filter; it never snaps cleanly to 0. joystick-shaping.test.js's
    "suppress small inputs" passes only because the filter starts at 0 on a fresh
    mapper, not because snap-to-zero runs.
  - Frame-rate assumption: _applyFilter is driven once per setTouchInput call with
    a fixed assumed dt (16.667ms); full-lock reachability and convergence speed
    therefore depend on call frequency, not real frame timing. (Deterministic for
    tests, but worth a note.)
