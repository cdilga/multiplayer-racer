## 1. Playtest 1 in one page

**The question Playtest 1 answers:** on the new stack, is driving and crashing the Cruz Missile
around generated Australian tracks with friends fun enough to build the rest of 0.2 on?

**What the owner does on playtest night** (the acceptance story):

1. Opens the **preview index** (`https://jammers-preview.dilger.dev/`), picks the pinned
   "Playtest 1" build and clicks **Host** on the laptop driving the TCL TV.
2. The TV shows a big QR and a room code. Six to ten friends scan it with their phone camera (or
   the in-page scanner) and are driving within ~20 s. Nobody installs anything. Controls go over
   WebRTC, directly on the home Wi-Fi when possible, through Cloudflare TURN otherwise.
3. Each player gets a numbered, coloured Cruz Missile and a tile in a dynamic grid. **Identify**
   makes "which car am I?" a one-second question.
4. They race three laps around a freshly generated track that passes through **town, Olgas-style
   rocks, outback dirt and outback bitumen** (R83). Doors and wheels go **loose, then fly off** and
   stay on the track as debris (R86). Wrecked cars respawn in ~2 s.
5. Someone arriving mid-race joins at the back a few seconds behind the last car. A phone that
   locks hands its car to a weak autopilot and gets it back on unlock.
6. Results, then an end-of-round **highlight reel** while the next track generates; the next round
   starts on its own. The host can End or Disband.
7. Afterwards the owner records a G-FEEL verdict and a playtest round record. **Development never
   stopped**: other previews kept shipping while the playtest build stayed pinned (R85).

**Done means** (P1-Q02): the story above works on the pinned preview with real phones (iOS and
Android), host-local pads/keys, a forced-TURN path and a direct LAN path, with receipts for input
latency/bytes, host frame pacing and connection paths, and the owner's couch verdict recorded.
Known gaps are listed, not hidden.

## 4. Architecture for Playtest 1

### 4.1 Processes and data flow

```text
Phone controller (browser)                        Host (laptop/phone browser, drives the TV)
  DOM touch sticks + HUD                            Main thread: Three.js render, DOM UI,
  jj-input + jj-protocol (WASM, ~small)             WebRTC peers (one per controller endpoint),
  RTCPeerConnection ──── WebRTC data channels ────► host-local pads/keys, highlight playback
     state  (unordered, 0 retransmits)                       │ raw input bytes / commands (postMessage)
     cmd    (reliable, ordered)                              ▼
                                                    Sim worker: jj-session + jj-input + jj-sim
         ▲ HTTPS: room resolve, signalling (SSE),    (Rust → WASM, Rapier, 120 Hz game time)
         │ ICE credentials                                   │ snapshots (pooled transferables), events
         ▼                                                   ▼
jj-server (Rust, Asupersync) ◄────── HTTPS ──────── Procgen worker: jj-procgen (Rust → WASM)
  static bundles, rooms, signalling, ICE creds
         │ server-to-server HTTPS
         ▼
Cloudflare Realtime TURN/STUN (credentials API; relays only when ICE picks relay)
```

Rules that hold everywhere (REQUIRED unless marked):

- The server never sees gameplay input. Controllers talk to the host over WebRTC; the server only
  creates/resolves rooms, relays signalling and issues ICE credentials (R77, R79).
- The host owns the room: seats, rules, physics, results (master §3.1). The server keeps a small
  in-memory registration (room code → host credential) and nothing about players.
- Controllers never download Three.js, Rapier, `jj-sim`, `jj-procgen` or world assets (master §3.6).
- No caps anywhere (R66). Buffers, arrays and lists grow to the actual N.

### 4.4 Worker ABI (host)

DEFAULT. Versioned in `jj-protocol`, implemented by `jj-wasm-host` and `web/host`.

| Direction | Message | Notes |
|---|---|---|
| main → sim | `Init{abiVersion, rulesHash, mapBytes, vehicleSidecars, seed}` | Map bytes are canonical `jj.map.v1` |
| main → sim | `NetBytes{endpointId, channel, bytes}` | Raw controller bytes, forwarded as they arrive (no batching on main) |
| main → sim | `LocalSource{sourceId, axes, buttons, seq}` | Host pads/keys, already sampled |
| main → sim | `Ui{commandId, command}` | Host UI commands (start, End, reroll, camera…) |
| main → sim | `Lifecycle{visible, renderOk}` | Composes pause reasons (§7.1) |
| main → sim | `ReturnBuffer{buf}` | Pooled snapshot buffer back to the worker |
| sim → main | `Snapshot{buf, tick, simTime, sessionRev}` | Transferable; car transforms, wheel poses, part states/angles, debris transforms, HUD facts |
| sim → main | `Events{batch}` | Ordered: joins, detaches, wrecks, laps, finishes, results; reel recorder reads these |
| sim → main | `Outbound{endpointId, channel, bytes}` | Welcome, ActionResult, HUD and room state for controllers |

Snapshots are bulk binary (no per-entity calls). If no pooled buffer is free, the worker skips that
presentation publish; it never blocks physics or drops events (master §13.4).

## 5. Networking, rooms and controller transport

### 5.1 Server API v1 (DEFAULT)

All paths sit under the deployment base path `B` (`/` in production, `/p/<id>/` in a preview).
JSON bodies, `Cache-Control: no-store` on API responses.

| Endpoint | Who | Purpose |
|---|---|---|
| `GET B/`, `B/host`, `B/c`, `B/j/<CODE>` | anyone | Landing, host app, controller app, join link (opens controller with the code) |
| `GET B/assets/<hash>.<ext>` | anyone | Immutable, long-cache static files; real 404s, never SPA HTML |
| `GET B/version` | anyone | `{build, protocol, realm}` |
| `GET B/healthz` | ops | Liveness + readiness (TURN provider status reported, not fatal) |
| `POST B/api/v1/rooms` | host | `{requestId, hostSecretHash}` → `201 {roomId, code, joinUrl}`; retry with the same `requestId` returns the same room |
| `PUT B/api/v1/rooms/<code>` | host | Re-register after a **server** restart: `{roomId, hostSecretHash}` + `Authorization: Bearer <hostSecret>` |
| `GET B/api/v1/rooms/<code>` | anyone | `{status: available\|host-unreachable\|ended\|not-found, roomId, build, realm}` |
| `POST B/api/v1/rooms/<roomId>/endpoints` | controller | `{requestId, endpointId, endpointSecretHash}` → registers a signalling endpoint (not a seat) |
| `GET B/api/v1/rooms/<roomId>/signal?endpoint=<id>` | both | SSE stream (see §5.2) |
| `POST B/api/v1/rooms/<roomId>/signal` | both | `{from, to, kind: offer\|answer\|candidate\|restart\|bye, gen, payload}` |
| `POST B/api/v1/ice` | both | `{roomId, endpointId}` → `{iceServers, expiresAt}` |
| `POST B/api/v1/rooms/<roomId>/end` | host | Ends the room; a tombstone stops stale re-registration |

Authentication: every non-public call carries `Authorization: Bearer <secret>`; the server stores
only SHA-256 hashes. Secrets are 128-bit random, base64url. Never log secrets or full join URLs with
secrets.

**Room codes:** 4 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no O/0/I/1/L), case-insensitive
entry, a small deny-list of rude words, random with collision retry. A code is a locator, never a
credential. Exact-code legibility on the TV is a fixture (master §3.6).

**State:** rooms live in memory. A server restart drops them; hosts re-register (`PUT`) on their
next SSE reconnect and keep their codes; existing WebRTC connections keep working throughout
(R84 keeps exactly this much).

### 5.2 Signalling over SSE through Cloudflare

- Use `fetch()` with a streamed body and an SSE parser (not `EventSource`), so the bearer token goes
  in a header, not the URL.
- Response `Content-Type: text/event-stream` (Cloudflare Tunnel streams only with this header).
- Send a comment heartbeat every **15 s** (Cloudflare's proxy read timeout is ~100 s).
- Event IDs are monotonic per endpoint; the client reconnects with `Last-Event-ID`; the server keeps
  undelivered messages for 60 s (DEFAULT) per endpoint stream. Signalling buffers are per endpoint
  and grow with traffic; they're never a cap on endpoints.
- One SSE stream per browser endpoint (hub sources share it later).

### 5.3 WebRTC

- **Controller is the offerer.** It fetches ICE config and registers its endpoint **in parallel**
  with resolving the room; direct negotiation doesn't wait for TURN credentials.
- `RTCPeerConnection({iceServers, iceTransportPolicy: "all"})`, trickle ICE, no candidate stripping,
  mDNS host candidates allowed (R79).
- Two **pre-negotiated** data channels (`negotiated: true`): id 0 `state` (`ordered: false,
  maxRetransmits: 0`), id 1 `cmd` (reliable, ordered).
- Negotiation generation `gen` tags every offer/answer/candidate; the host fences older gens.
- Recovery: on `disconnected` for 3 s, or on page resume, the controller tries `restartIce()` with a
  new offer (gen + 1); if still not connected after 5 s it builds a new peer connection (gen + 1).
  Same seat throughout (resume proof, §5.5).
- TURN (R88): the ICE list carries **self-hosted coturn first** (`turn:turn.dilger.dev:3479?transport=udp`,
  UDP only, see `docs/infra/turn-and-previews.md`) and **Cloudflare TURN second** (UDP/TCP/TLS 443,
  for UDP-blocked networks and as overflow). coturn credentials are minted by `jj-server` with the
  TURN REST scheme: `username = "<expiry>:<endpointId>"`, `credential = base64(HMAC-SHA1(secret,
  username))`, TTL 7,200 s (DEFAULT). Cloudflare credentials come from `generate-ice-servers` with
  the same TTL; drop any URL on port 53. Refresh both at 75 % of the TTL with `setConfiguration()`.
  A provider failure drops only that provider's entries and shows "relay unavailable" when none is
  left; direct paths keep working (master §13.3). Measure which relay actually gets selected.
- Diagnostics: both ends read the selected candidate pair (`local/remote candidateType`,
  `relayProtocol`) and RTT; the host diagnostics overlay and the receipts show them. Redact IPs.
- The host holds one peer connection per controller endpoint. Browsers have platform ceilings on
  peer connections; we report any we hit honestly and never impose our own (R66).

### 5.4 Controller wire format v1 (DEFAULT)

**State channel:** one message carries every due source of this endpoint.

```text
StateBatch:  u8 type=0x10 | u8 minor | u16 batchSeq | u8 count      (5 bytes)
  record × count:
    u16 sourceHandle   (assigned by the host on claim; per connection)
    u16 sourceSeq      (wrapping, per source)
    i16 driveX, i16 driveY, i16 actionX, i16 actionY   (quantised −32767..32767)
    u8  flags          (bit0 available, bit1 driveTouch, bit2 actionTouch,
                        bit3 wheeliePreload, bit4 menuOpen)                  (13 bytes)
```

One source = 18 bytes; at 60 Hz that's 1,080 B/s of payload, under the 2,000 B/s target (R80).
`count` > 255 sources splits into more batches, never truncates.

Axes carry the **personal response curve already applied** on the controller (a device preference,
master §10.6a). Game interpretation (DriveIntent, sectors, boost/drift) happens in `jj-input` on the
host, the same code path pads and keys use.

**Cadence** (master §4.4): flush changing state up to 60 Hz; refresh unchanged state at 20 Hz;
send neutral/cancel/unavailable immediately. The host neutralises a source after **250 ms** without
fresh state and hands the car to autopilot after **2 s**.

**Command channel:** `u8 version` + a `postcard`-encoded enum. Controller → host: `Hello{protocol,
build, endpointId, resume?: endpointSecret}`, `Claim{requestId, name}`, `Action{actionId, sourceHandle,
kind, roundId, lifeId, atSourceSeq}`, `Identify`, `SetName`, `SetCamera{fp|tp}`, `Ready{on}`,
`Recover`, `SitOut`, `Leave`, `Menu{open}`. Host → controller: `Welcome{seatId, number, colour,
sourceHandle}`, `ClaimRejected{reason}`, `ActionResult{actionId, applied{tick}|expired|rejected{reason}}`,
`RoomState{phase, you, countdown, results}`, `Ended`. HUD updates (position, lap, boost, connection,
pause reason) go on the **state** channel at ~10 Hz and on change, because they're disposable.

**Discrete actions** (wheelie release, forward/rear utility) are detected on the controller by
`jj-input` (the same code the host uses for pads) and sent as `Action` with a stable `actionId`. The
host deduplicates, applies at a tick or returns `expired`/`rejected`; it never executes an expired
action late and never infers an edge from the lossy state stream (master §4.1, §13.3).

### 5.5 Seats, claims and resume

- A controller endpoint keeps `endpointId` + `endpointSecret` in `localStorage`, namespaced by realm
  (production vs preview id). Memory-only storage still plays and is told resume may not survive.
- Opening a URL never claims a seat. **Join the race** sends `Claim{requestId}`; the host answers
  `Welcome`. Retries with the same `requestId` can't create a second car.
- Reconnect sends `Hello{resume: endpointSecret}`; the host matches the stored hash and returns the
  **same seat, car, progress and score**. A duplicate tab with the same secret fences the older one
  ("Playing in another tab").
- Explicit device handoff is deferred (R84). A new device gets a new seat.

  the ground between the axles, parts `core`, `front`, `back`, `door_FL/FR/RL/RR`,
  `wheel_FL/FR/RL/RR`, each with pivot, **hinge axis + loose limits** (§6.3), mass fraction (sum 1 ±
  0.01), collider proxy (convex/cuboid/capsule), and anchors `cam_fp`, `cam_tp_target`, `com`,
  `roof_number`, `lplate_front`, `lplate_rear`.
- One material; the atlas carries the paint key. No texture files beyond the atlas.
- Budgets start at ≤ ~1.3k / 0.9k / 0.6k tris; P1-Q01 qualifies them on a weaker host.

### 6.3 Damage model (R86)

Each part goes **intact → loose → detached**. No dents.

- **Health:** per part, DEFAULT/TUNE: `front` 100, `back` 100, each door 60, each wheel 80.
- **Damage episodes:** every part is its own collider on the chassis body, so a contact's collider
  handle tells you the part. Per (car, part, other body), aggregate normal impulses over a 50 ms
  game-time window; count only contacts with closing speed ≥ 4 m/s (TUNE), which excludes resting
  and suspension support. Damage = `k_part × Σ impulse`. Calibrate `k` with scenarios, not formulas:

  | Scenario | Expected |
  |---|---|
  | `bump-4`: 4 m/s nudge into another car | no damage |
  | `rest-60`: parked against a wall for 60 s | no damage |
  | `side-swipe-8`: 8 m/s door-to-door | that door goes loose, nothing detaches |
  | `wall-head-on-15`: 15 m/s into a wall | `front` detaches |
  | `t-bone-12`: 12 m/s into a door | that door detaches |
  | `wheel-kerb-12`: 12 m/s wheel strike on a barrier end | that wheel goes loose |

- **Wheel colliders:** small cylinders/balls at each hub, in a collision group that **excludes
  terrain and road**, so wheel strikes from cars/debris/barriers register without fighting the
  raycast suspension.
- **Loose** (health ≤ 50 %): the part stays attached and its collider stays at the attached pose.
  `jj-sim` integrates a damped 1-DOF spring about the part's hinge axis, driven by chassis
  acceleration (deterministic, published in snapshots, replayable). DEFAULT limits: doors 0–70°
  about the front edge; bumpers hang 0–25° about their top edge; wheels wobble ±6° camber. A loose
  wheel also loses 15 % friction slip (TUNE).
- **Detached** (health 0): at the end of the tick, remove the part's collider from the chassis,
  create a dynamic body with the part's proxy and mass at its current world pose, set velocity to the
  chassis velocity at that point (`v + ω × r`) plus a small outward kick, and recompute chassis mass
  properties. A detached wheel disables that wheel in the vehicle controller (zero suspension force,
  friction and engine force; verify the Rapier 0.36 API in P1-S04) so that corner drops onto its
  collider.
- **Debris persists** for the round as dynamic bodies that may sleep and wake (R58, R66): no TTL, cap,
  static conversion or merging.
- **Wreck:** a car with ≥ 2 wheels detached, or stuck/flipped past the recovery timeout, or out of
  bounds, is wrecked. Its remaining parts pop off as debris and its **husk stays as a dynamic body**
  (DEFAULT; see Q-A2). After ~2 s (R20) the player respawns at their own legal recovery anchor in a
  fresh intact car with the same identity and progress.
- **Rendering:** a loose part is its instance with the hinge rotation applied; a detached part is
  the same part-type instance with a physics-driven matrix; a missing part shows the core's dark
  bay. Detached parts keep the owner's paint colour.

## 7. Simulation (`jj-sim`)

### 7.1 Time, ticks and pauses

- 120 Hz fixed step, `dt = 1/120` (R61). The worker owns the accumulator and steps whole ticks;
  rendering interpolates between the last two snapshots.
- **Tick order:** apply commands and inputs due at this tick → set vehicle controls and surface
  friction → `update_vehicle` against current query data → `step` → read contact data and build
  damage episodes → apply structural changes (detach, spawn, respawn) → race progress → emit ordered
  events → publish snapshot when a buffer is free.
- **Pause reasons** compose: `manual`, `host-hidden`, `renderer-unavailable`, `performance-stall`,
  `fault`. Hidden time is never replayed; resume goes through a short visible countdown with input
  re-armed at neutral (master §7.1). Controller loss never pauses (R45).
- Persistently unplayable lag enters `performance-stall` at the last completed tick. Never enlarge
  `dt`, skip ticks, delete debris or refuse joins.

### 7.2 Determinism

Seeded RNG streams, stable iteration order, no wall clock in the sim, Rapier `enhanced-determinism`.
Same-build same-target runs produce identical full-state hashes. Native vs WASM physics identity is a
measured claim (P1-Q01), not an assumption. Canonical **map bytes** must match native vs WASM.

### 7.3 Vehicle feel (P1-S03; targets are TUNE, judged at G-FEEL)

| Affordance | DEFAULT starting behaviour | Scenario |
|---|---|---|
| Suspension | Soft springs, strong damping, visible roll/squat/dive, single-settle landings | `idle-settle`, `jump-land` |
| Steer/throttle/brake/reverse | DRIVE X steers; up throttles; down brakes, reversing near rest | `progressive-brake`, `slalom` |
| Handbrake drift | ACTION left: rear friction slip × 0.35, 0.4 s smooth recovery; drifting charges boost | `drift-entry-exit` |
| Boost | ACTION right: meter 0–1, drains 0.35/s, recharges 0.12/s, +60 % engine force | `boost-hold` |
| Wheelie | DRIVE pulled past the full-brake point (y < −0.85) preloads; releasing within 250 ms lifts the front, scaled by preload time (max at 0.4 s); needs ≥ 3 wheels grounded | `wheelie-ok`, `wheelie-fail`, `brake-no-wheelie` |
| Air control | Mild pitch/roll torque from DRIVE while airborne | `air-level` |
| Surfaces | Per surface ID: tarmac 1.0, packed dirt 0.8, gravel 0.7, rock 0.9 friction multipliers | `surface-deltas` |

### 7.4 Recovery, out of bounds and flip assist

- **Flip assist** (load-bearing, per Spike C): when up·Y < 0.2 and speed < 2 m/s for 1 s, apply a
  visible self-right torque; if still inverted after 3 s, the car is wrecked (§6.3).
- **Recover** button on the controller: available when speed < 3 m/s for 1 s or inverted; 2 s
  penalty; respawn at the own anchor.
- **Out of bounds:** below the kill height or outside map bounds → wreck → respawn.

### 7.5 Race progress, placement and autopilot

- Route = the map's centerline with checkpoint gates (~every 40 m). Legal progress needs gates in
  order; the **recovery anchor** is the last gate passed, offset onto the centerline at a clear pose.
- **Placement service** (one service for start grid, respawn and drop-in): commit placements at tick
  boundaries against current cars and debris; 1.5 s spawn protection disables car/debris contacts
  (terrain and barriers stay solid) and only ends in a non-overlapping pose. Start grid supports any
  N (rows extend back along the route).
- **Drop-in (R63):** a new seat spawns ~3 s of route behind the last still-racing car, with that
  car's lap/gate state, marked as a late joiner. Reconnect and wreck use the seat's own anchor.
- **Autopilot:** pure pursuit on the centerline (look-ahead ≈ 0.8 s × speed), target speed from
  curvature × 0.7 (low skill), small noise, self-recovers when stuck 3 s. Visible badge "autopilot".
- **Race end:** 3 laps DEFAULT; 30 s window after the first finisher; absolute deadline
  `max(180 s, 2 × laps × refLap)`; finished cars stop colliding with racers and coast on autopilot;
  unfinished cars rank by legal progress (master §10.12 Race rules apply).

### 7.6 Utilities on the ACTION stick (DEFAULT for Playtest 1, no weapons yet)

The two-stick layout (R60) needs something on ACTION up/down before weapons exist:

- **Up (forward utility): "OI!" flash.** Headlights flash and a comic "OI!" pops over the car.
  0.5 s cooldown. Harmless; tests forward sector entry.
- **Down (rear utility): drop a traffic cone** 1.5 m behind the car, a light dynamic prop that
  persists (R58). 2.5 s game-time cooldown (a rule cadence, not a count cap). Tests rear sector entry
  and gives people something silly to do.
- Right/left: boost / handbrake drift (§7.3).

## 9. Session, round flow and players (`jj-session`)

- **Phases:** Lobby → Preparing → Countdown → Running → Finalising → Intermission → Preparing …;
  End returns to Lobby; Disband ends the room (master §10.8 boundary rules apply).
- **Lobby:** big QR + code; player strip (number, name, colour, Ready, connection). Start policy:
  start when all active human seats are Ready, or host **Start now** with a 10 s warning to
  not-ready controllers (banner + vibration where supported), then everyone plays with their current
  car (R31).
- **Intermission:** results + highlight reel (~60 s, skippable by the host), next track generating
  in the background, then auto-start (R38, R50). New players can join during intermission.
- **Late joins** enter the running round immediately at the tail (§7.5). No queue, no "room full".
- **Dropout:** 250 ms stale → neutral; 2 s → autopilot; fresh deliberate input reclaims (R45).
  Connected but idle 15 s → 3 s takeover cue → autopilot.
- **Leave / Sit out:** explicit, at a tick boundary; car withdrawn with a visible cue; debris stays;
  standings kept (master §4.4).
- **Results:** in-memory session standings, Race points table from master §10.12. Nothing persists
  across host death (R84). The host page asks for confirmation before unload.
- **Names:** prefilled fun Aussie name, editable (≤ 32 graphemes, text only); colours from a
  curated palette, reused with distinct numbers as N grows (no cap).

## 13a. Validation in the loop: introspection, stepping and fixtures (R90)

**Why.** What made the Physical Soccer process work was a game whose state could be read as data,
tools to step through that state, and fixtures that pinned behaviours down. The agentic game-dev
survey (pro-kb `agentic-game-dev-techniques-report.md`, 2026-10-01) found the same across projects:
structured state beats pixels for agents, determinism and replay make claims provable, an external
pass/fail signal beats self-assessment, and the strongest setups make **the game itself the test
surface**. It also found that good tools are *extracted* once a step repeats, not designed up front.
This capability compounds: every area that becomes introspectable makes later work on it cheaper.

**Rule (REQUIRED, R90).** Every distinct part of the game ships with a way for an agent to:

1. **See** its state as structured data (not pixels) at a given tick or moment;
2. **Set up** a state directly (spawn, place, configure, jump to a phase) without playing to it;
3. **Step** time deterministically (tick by tick, or until a condition) and **replay** a recorded run;
4. **Assert** behaviour with a saved fixture (setup + inputs + expected observations or envelopes)
   that fails loudly and prints what it actually observed.

**How** each area does this is the implementing agent's call: a test API on the worker, a `--json`
CLI, a scenario file, a debug channel, whatever fits. Keep it lean, and extract shared tooling only
when the same step shows up in two areas. Test-only surfaces are never reachable from production
controllers (master §15.1). Captures still judge looks; owner playtests still judge feel.

| Area (tasks) | Must be introspectable | Example fixtures (illustrative, not a checklist) |
|---|---|---|
| Rooms, seats, controllers (N03–N07, G02, G03) | seats, claims, assignment generations, per-source freshness, autopilot state, selected ICE path | 40 fake controllers join over WebRTC → 40 seats, no duplicates, 40 tiles; one drops → autopilot within 2 s, room never pauses |
| Grid, cameras, identity (R04–R06) | tile rects, the camera per tile (mode, target, FOV), LOD class per tile, identity overlays | fake players join one by one → each join creates exactly one tile and camera; existing tiles keep order |
| Vehicle feel (S03) | per-wheel compression, slip and contact; yaw rate; speed; the authority metric | cornering at 15 m/s full lock stays in its yaw-rate envelope; drift entry/exit angles |
| Collisions and damage (S04) | contact episodes, part health/state/loose angle, debris bodies (dynamic, sleeping), mass totals | 12 m/s T-bone → that door detaches; the debris is still dynamic and wakeable at round end |
| Race rules, placement, autopilot (S05–S08) | progress, gates, anchors, placement decisions, autopilot targets, utility cooldowns | drop-in during lap 2 → spawn ~3 s behind the last car with its lap/gate state |
| Round flow (N07b–c, G01) | director phase, presentation-clock timers, ready cohort, results | jump to 1 s before intermission ends; force-start with one not-ready seat |
| Controller input (N06, C02, C05) | sent records and bytes, detected actions with IDs, applied/expired results | a pointer cancel mid-wheelie fires nothing; press + release between two sends yields one action |
| Procgen (M01–M09) | the map document, validator report, per-biome placements, generation timings | seed 42 → identical bytes native/WASM; houses stay clear of the route |
| Rendering and perf (R01–R02, Q01) | draws/tris per tile, frame timings, LOD choices | the 24×24 bench stays inside its envelope |
| Audio (A01–A03) | cue triggers, which clip played, mix state | a finish triggers the winner cue exactly once |
| Deploy (D01–D07) | the preview register, smoke steps | a publish adds an index row with its smoke status |
| Later, Full: L-plates and the like | assist parameters in force, reductions applied | an L-plate boost pays out the configured fraction of the full boost |

**Done-ness.** Every §15 task's acceptance must be checkable by an agent from that area's
structured state (plus captures where looks matter). A task that adds behaviour also extends its
area's introspection and fixtures; that's part of the task, not a follow-up.
