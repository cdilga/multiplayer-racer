## 1. Playtest 1 in one page

**The question Playtest 1 answers:** on the new stack, is driving and crashing the Cruz Missile
around generated Australian tracks with friends fun enough to build the rest of 0.2 on?

**What the owner does on playtest night** (the acceptance story):

1. Opens the **preview index** (`https://jammers-preview.dilger.dev/`), picks the pinned
   "Playtest 1" build and clicks **Host** on the laptop driving the TCL TV.
2. The TV shows a big QR and a room code. Six to ten friends scan it with their phone camera (or
   the in-page scanner) and are driving within ~20 s. Nobody installs anything. Controls go over
   WebRTC, directly on the home Wi-Fi when possible, through the self-hosted TURN relay otherwise,
   and through Cloudflare TURN only when neither works (R88, R92).
3. Each player gets a numbered, coloured Cruz Missile and a tile in a dynamic grid. **Identify**
   makes "which car am I?" a one-second question.
4. They race three laps around a freshly generated track that passes through **town, Olgas-style
   rocks, outback dirt and outback bitumen** (R83). Doors and wheels go **loose, then fly off** and
   stay on the track as debris (R86). Wrecked cars respawn in ~2 s.
5. Someone arriving mid-race joins at the back a few seconds behind the last car. A phone that
   locks hands its car to a weak autopilot and gets it back on unlock.
6. Results, then an end-of-round **highlight reel** while the next track generates; the next round
   starts on its own. The host can End or Disband.
7. Afterwards the owner records a G-FEEL verdict and a playtest round record. **Development never
   stopped**: other previews kept shipping while the playtest build stayed pinned (R85).

**Done means** (P1-Q02): the story above works on the pinned preview with real phones (iOS and
Android), host-local pads/keys, a forced-TURN path and a direct LAN path, with receipts for input
latency/bytes, host frame pacing and connection paths, and the owner's couch verdict recorded.
Known gaps are listed, not hidden.

## 3. Delivery model: continuous rainbow previews (R85)

**No freeze.** Every candidate that passes CI publishes a preview. The playtest is just a preview
the owner **pins**. Work on later features continues while the owner tests.

- The deploy track starts in the first week. The **first preview** is the walking skeleton (P1-G00):
  a host page with a room code, a phone that joins over WebRTC, and a stick that moves a marker.
- Every preview appears on the **preview index** at `https://jammers-preview.dilger.dev/`, newest
  first, with what changed, smoke status and expiry (§12.4).
- Retention per R73: pinned previews and the latest always survive; other unpinned previews expire
  after 24 h; at most three unpinned previews.

**Drops** name the preview milestones. They're labels for what a preview can do, not gates: a task
starts when its dependencies close.

## 4. Architecture for Playtest 1

### 4.1 Processes and data flow

```text
Phone controller (browser)                        Host (laptop/phone browser, drives the TV)
  DOM touch sticks + HUD                            Main thread: Three.js render, DOM UI,
  jj-input + jj-protocol (WASM, ~small)             WebRTC peers (one per controller endpoint),
  RTCPeerConnection ──── WebRTC data channels ────► host-local pads/keys, highlight playback
     state  (unordered, 0 retransmits)                       │ raw input bytes / commands (postMessage)
     cmd    (reliable, ordered)                              ▼
                                                    Sim worker: jj-session + jj-input + jj-sim
         ▲ HTTPS: room resolve, signalling (SSE),    (Rust → WASM, Rapier, 120 Hz game time)
         │ ICE credentials                                   │ snapshots (pooled transferables), events
         ▼                                                   ▼
jj-server (Rust, Asupersync) ◄── HTTPS (host page) ──  Procgen worker: jj-procgen (Rust → WASM)
  static bundles, rooms, signalling, ICE creds
         │ coturn: credentials minted locally (HMAC, no call)
         │ Cloudflare: via the one turn-broker, only on a relay-fallback request (R92)
         ▼
TURN relays (used only when ICE picks relay): coturn turn.dilger.dev:3479/udp first,
Cloudflare Realtime TURN (UDP, TCP, TLS incl. 443) as the lazy fallback
```

Rules that hold everywhere (REQUIRED unless marked):

- The server never sees gameplay input. Controllers talk to the host over WebRTC; the server only
  creates/resolves rooms, relays signalling and issues ICE credentials (R77, R79, R88, R92).
- The host owns the room: seats, rules, physics, results (master §3.1). The server keeps a small
  in-memory registration (room code → host credential) and nothing about players.
- Controllers never download Three.js, Rapier, `jj-sim`, `jj-procgen` or world assets (master §3.6).
- No caps anywhere (R66). Buffers, arrays and lists grow to the actual N.

**Two Gitea repos, one monorepo.** All game code, art, tools and docs live in one monorepo:
`cdilga/multiplayer-racer` on Gitea (primary) and GitHub (passive mirror). The only other repo is a
small `jammers-deploy` holding deploy workflows, deploy secrets, smoke steps, the preview register,

scripts. Both repos are created with `tea` (P1-D01).

## 5. Networking, rooms and controller transport

### 5.1 Server API v1 (DEFAULT)

All paths sit under the deployment base path `B` (`/` in production, `/p/<id>/` in a preview).
JSON bodies, `Cache-Control: no-store` on API responses.

| Endpoint | Who | Purpose |
|---|---|---|
| `GET B/`, `B/host`, `B/c`, `B/j/<CODE>` | anyone | Landing, host app, controller app, join link (opens controller with the code) |
| `GET B/assets/<hash>.<ext>` | anyone | Immutable, long-cache static files; real 404s, never SPA HTML |
| `GET B/version` | anyone | `{build, protocol, realm}` |
| `GET B/healthz` | ops | Liveness + readiness (TURN provider status reported, not fatal) |
| `POST B/api/v1/rooms` | host | `{requestId, hostSecretHash}` → `201 {roomId, code, joinUrl, hostEndpointId, iceServers, iceExpiresAt}`; retry with the same `requestId` returns the same room. The host's signalling endpoint is registered with the room (`hostEndpointId = "host"`) |
| `PUT B/api/v1/rooms/<code>` | host | Re-register after a **server** restart: `{roomId, hostSecretHash}` + `Authorization: Bearer <hostSecret>` |
| `GET B/api/v1/rooms/<code>` | anyone | `{status: available\|host-unreachable\|ended\|not-found, roomId, build, realm}` |
| `POST B/api/v1/rooms/<roomId>/endpoints` | controller | `{requestId, endpointId, endpointSecretHash}` → `201 {iceServers, iceExpiresAt}`; registers a signalling endpoint (not a seat) and returns the initial ICE list in the same round trip (§5.3) |
| `GET B/api/v1/rooms/<roomId>/signal?endpoint=<id>` | both | SSE stream (see §5.2) |
| `POST B/api/v1/rooms/<roomId>/signal` | both | `{from, to, kind: offer\|answer\|candidate\|restart\|bye, gen, payload}` |
| `POST B/api/v1/ice` | both | `{roomId, endpointId}` → `{iceServers, expiresAt}`: refresh of the initial list (STUN + coturn), bearer = that endpoint's secret |
| `POST B/api/v1/ice/fallback` | both | `{roomId, endpointId, reason}` → `{iceServers, expiresAt}` with **Cloudflare TURN** entries, or `429 {retryAfterMs}` (issuance rate), or `503 {reason: relay-unavailable}` (no key configured, key deleted by the guard, or provider down). R92; §5.3 |
| `POST B/api/v1/rooms/<roomId>/end` | host | Ends the room; a tombstone stops stale re-registration |

Authentication: every non-public call carries `Authorization: Bearer <secret>`; the server stores
only SHA-256 hashes. Secrets are 128-bit random, base64url. Never log secrets or full join URLs with
secrets.

**Room codes:** 4 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no O/0/I/1/L), case-insensitive
entry, a small deny-list of rude words, random with collision retry. A code is a locator, never a
credential. Exact-code legibility on the TV is a fixture (master §3.6).

**State:** rooms live in memory. A server restart drops them; hosts re-register (`PUT`) on their
next SSE reconnect and keep their codes, and controllers re-register their endpoints (the same
idempotent `POST …/endpoints` with their existing id and secret hash) on theirs, so later ICE restarts
can still signal; existing WebRTC connections keep working throughout (R84 keeps exactly this much).

### 5.2 Signalling over SSE through Cloudflare

- Use `fetch()` with a streamed body and an SSE parser (not `EventSource`), so the bearer token goes
  in a header, not the URL.
- Response `Content-Type: text/event-stream` (Cloudflare Tunnel streams only with this header).
- Send a comment heartbeat every **15 s** (Cloudflare's proxy read timeout is ~100 s).
- Event IDs are monotonic per endpoint; the client reconnects with `Last-Event-ID`; the server keeps
  undelivered messages for 60 s (DEFAULT) per endpoint stream. Signalling buffers are per endpoint
  and grow with traffic; they're never a cap on endpoints.
- One SSE stream per browser endpoint (hub sources share it later).

### 5.3 WebRTC

- **Controller is the offerer.** It resolves the code (`GET rooms/<code>`), registers its endpoint
  (the response carries the initial ICE list, so there's no separate credential round trip) and opens
  its SSE stream, then offers at once. Direct negotiation never waits for a relay fallback. (r3: the
  r2 text fetched ICE "in parallel" with registration, but `/ice` is authenticated by the endpoint
  secret that registration creates.)
- `RTCPeerConnection({iceServers, iceTransportPolicy: "all"})`, trickle ICE, no candidate stripping,
  mDNS host candidates allowed (R79). Test browsers (Playwright on eris or a CI runner without an mDNS
  responder) launch with `--disable-features=WebRtcHideLocalIpsWithMdns`, otherwise loopback `.local`
  candidates don't resolve; that flag is test-only and never changes production behaviour.
- Two **pre-negotiated** data channels (`negotiated: true`): id 0 `state` (`ordered: false,
  maxRetransmits: 0`), id 1 `cmd` (reliable, ordered).
- Negotiation generation `gen` tags every offer/answer/candidate; the host fences older gens.
- Recovery: on `disconnected` for 3 s, or on page resume, the controller tries `restartIce()` with a
  new offer (gen + 1); if still not connected after 5 s it builds a new peer connection (gen + 1).
  Same seat throughout (resume proof, §5.5).
- **Initial ICE list (R88).** Cloudflare STUN `stun:stun.cloudflare.com:3478` (free, no credentials)
  plus self-hosted coturn `turn:turn.dilger.dev:3479?transport=udp` (UDP only, AU sources only; see
  `docs/infra/turn-and-previews.md`). coturn credentials are minted by `jj-server` with the TURN REST
  scheme: `username = "<expiry>:<endpointId>"`, `credential = base64(HMAC-SHA1(secret, username))`,
  TTL 7,200 s (DEFAULT). Refresh at 75 % of the TTL via `POST /ice` and `setConfiguration()`.
- **Cloudflare TURN is lazy (R92).** It is never in the initial list, because an issued Cloudflare
  credential can't be revoked (measured: it outlives key deletion, revocation and its TTL). Either side
  (controller or host) calls `POST /ice/fallback` only when, for that peer connection:
  ICE reaches `failed`; or gathering finished with no coturn `relay` candidate and the connection isn't
  `connected` 3 s later; or it still isn't `connected` 8 s after the offer (TUNE). It then merges the
  Cloudflare entries with `setConfiguration()` and restarts ICE (gen + 1). Keep the URLs the API
  returns (UDP, TCP and TLS on their documented ports) except any on port 53; the TLS-on-443 entry is
  the one UDP-blocked networks need. The qualification receipt records the exact URLs. Cloudflare credentials carry `customIdentifier = jj-<realm>-<roomId>-<endpointId>` (the
  guard reads usage per tag) and a 30 min TTL, re-requested through the same path only while the peer
  still needs a relay. A credential belongs to an **endpoint**, not a peer connection: the host (one
  endpoint, many peers) reuses one fallback credential for every peer that needs it.
- **One credential broker, not one per preview.** Every preview runs its own `jj-server` from
  candidate code, so limits kept inside each backend would reset on restart, multiply by the number of
  previews and be removable by any branch. DEFAULT: a single `turn-broker` (a role of the `jj-server`
  binary, deployed once from `jammers-deploy`) holds the only copy of the Cloudflare API token and
  enforces the limits; backends call it on the internal network with a per-backend secret and forward
  the client IP taken only from the tunnel's `CF-Connecting-IP` header. Each fallback request carries a
  `requestId`, so a lost response retried returns the same credential instead of minting another.
- **Issuance limits are rates, not totals** (R66, R92): DEFAULT token buckets per endpoint (burst 2,
  then 1 per 5 min), per room (burst 32, then 1 per 2 s) and per client IP (burst 32, then 1 per 5 s).
  Worst realistic case: 40 guests behind one public IP on a UDP-blocked network get 32 credentials at
  once and the other 8 within 40 s. Nobody is refused permanently; a refused call returns
  `429 {retryAfterMs}`, the controller shows "Finding a relay…" and retries. These are abuse limits,
  never player caps; the guard's egress thresholds bound the cost of whatever is issued (TUNE).
- A provider failure drops only that provider's entries and shows "relay unavailable" when none is
  left; direct paths keep working (master §13.3). Until P1-N04b lands, `/ice/fallback` answers `503`.
  Measure and report which path each seat actually selects (host, srflx, coturn relay, Cloudflare
  relay and its transport).
- **The playtest topology is the hard case.** The host laptop sits on the home LAN (`192.168.10.0/24`)
  and coturn on TrueNAS (`192.168.11.12`); the FortiGate exposes coturn only WAN-side to AU sources and
  coturn denies private peers except its own address. A guest on cellular data therefore probably
  can't reach a LAN host through coturn (it needs NAT hairpinning or a LAN-side route to coturn), and
  would fall back to Cloudflare. That costs nothing that matters at controller bitrates (~1 KB/s per
  player), but it has to be observed, not assumed: the P1-Q02 playtest checklist has a row for it,
  and §17.2 Q-N1 holds the owner decision on a LAN-side coturn route.
- Diagnostics: both ends read the selected candidate pair (`local/remote candidateType`,
  `relayProtocol`) and RTT; the host diagnostics overlay and the receipts show them. Redact IPs.
- The host holds one peer connection per controller endpoint. Browsers have platform ceilings on
  peer connections; we report any we hit honestly and never impose our own (R66).

### 5.4 Controller wire format v1 (DEFAULT)

**State channel:** one message carries every due source of this endpoint.

```text
StateBatch:  u8 type=0x10 | u8 minor | u16 batchSeq | u16 sentAtMs | u8 count      (7 bytes)
  record × count:
    u16 sourceHandle   (assigned by the host on claim; per connection)
    u16 sourceSeq      (wrapping, per source)
    i16 driveX, i16 driveY, i16 actionX, i16 actionY   (quantised −32767..32767)
    u8  flags          (bit0 available, bit1 driveTouch, bit2 actionTouch,
                        bit3 wheeliePreload, bit4 menuOpen)                  (13 bytes)
```

One source = 20 bytes; at 60 Hz that's 1,200 B/s of payload, under the 2,000 B/s target (R80).
A batch splits when it would pass ~1,000 application bytes (master §13.3a's message-size target,
DEFAULT) or 255 records, whichever comes first; the extra batches go out in the same flush, fairly
rotated across sources, and nothing is ever truncated.

**Input age.** `sentAtMs` is the controller's monotonic clock (wrapping ms). The `cmd` channel carries
`Ping{t}`/`Pong{t, hostT}` on connect and every 5 s, so the host keeps a clock-offset estimate with
±RTT/2 uncertainty per endpoint. Receipts report sample-to-send (measured on the controller),
host-applied input age and action age as p50/p95/p99 **with that uncertainty**, never by comparing
unsynchronised clocks directly.

Axes carry the **personal response curve already applied** on the controller (a device preference,
master §10.6a). Game interpretation (DriveIntent, sectors, boost/drift) happens in `jj-input` on the
host, the same code path pads and keys use.

**Cadence** (master §4.4): flush changing state up to 60 Hz; refresh unchanged state at 20 Hz;
send neutral/cancel/unavailable immediately. The host neutralises a source after **250 ms** without
fresh state and hands the car to autopilot after **2 s**.

**Command channel:** `u8 version` + a `postcard`-encoded enum. Controller → host: `Hello{protocol,
build, endpointId, resume?: endpointSecret}`, `Claim{requestId, name}`, `Action{actionId, sourceHandle,
kind, roundId, lifeId, atSourceSeq}`, `Identify`, `SetName`, `SetCamera{fp|tp}`, `Ready{on}`,
`Recover`, `SitOut`, `Leave`, `Menu{open}`, `Ping{t}`. Host → controller: `Welcome{seatId, number,
colour, sourceHandle}`, `ClaimRejected{reason}`, `ActionResult{actionId, applied{tick}|expired|rejected{reason}}`,
`RoomState{phase, you, countdown, results}`, `Pong{t, hostT}`, `Ended`. HUD updates (position, lap, boost, connection,
pause reason) go on the **state** channel at ~10 Hz and on change, because they're disposable.

**Discrete actions** (wheelie release, forward/rear utility) are detected on the controller by
`jj-input` (the same code the host uses for pads) and sent as `Action` with a stable `actionId`. The
host deduplicates, applies at a tick or returns `expired`/`rejected`; it never executes an expired
action late and never infers an edge from the lossy state stream (master §4.1, §13.3).

### 5.5 Seats, claims and resume

- A controller endpoint keeps `endpointId` + `endpointSecret` in `localStorage`, namespaced by realm
  (production vs preview id). Memory-only storage still plays and is told resume may not survive.
- Opening a URL never claims a seat. **Join the race** sends `Claim{requestId}`; the host answers
  `Welcome`. Retries with the same `requestId` can't create a second car.
- Reconnect sends `Hello{resume: endpointSecret}`; the host matches the stored hash and returns the
  **same seat, car, progress and score**. A duplicate tab with the same secret fences the older one
  ("Playing in another tab").
- Explicit device handoff is deferred (R84). A new device gets a new seat.

### 6.3 Damage model (R86)

Each part goes **intact → loose → detached**. No dents.

- **Health:** per part, DEFAULT/TUNE: `front` 100, `back` 100, each door 60, each wheel 80.
- **Damage episodes:** every part is its own collider on the chassis body, so a contact's collider
  handle tells you the part. Per (car, part, other body), aggregate normal impulses over a 50 ms
  game-time window; count only contacts with closing speed ≥ 4 m/s (TUNE), which excludes resting
  and suspension support. Damage = `k_part × Σ impulse`. Calibrate `k` with scenarios, not formulas:

  | Scenario | Expected |
  |---|---|
  | `bump-4`: 4 m/s nudge into another car | no damage |
  | `rest-60`: parked against a wall for 60 s | no damage |
  | `side-swipe-8`: 8 m/s door-to-door | that door goes loose, nothing detaches |
  | `wall-head-on-15`: 15 m/s into a wall | `front` detaches |
  | `t-bone-12`: 12 m/s into a door | that door detaches |
  | `wheel-kerb-12`: 12 m/s wheel strike on a barrier end | that wheel goes loose |

- **Wheel colliders:** small cylinders/balls at each hub, in a collision group that **excludes
  terrain and road**, so wheel strikes from cars/debris/barriers register without fighting the
  raycast suspension.
- **Loose** (health ≤ 50 %): the part stays attached and its collider stays at the attached pose.
  `jj-sim` integrates a damped 1-DOF spring about the part's hinge axis, driven by chassis
  acceleration (deterministic, published in snapshots, replayable). DEFAULT limits: doors 0–70°
  about the front edge; bumpers hang 0–25° about their top edge; wheels wobble ±6° camber. A loose
  wheel also loses 15 % friction slip (TUNE).
- **Detached** (health 0): at the end of the tick, remove the part's collider from the chassis,
  create a dynamic body with the part's proxy and mass at its current world pose, set velocity to the
  chassis velocity at that point (`v + ω × r`) plus a small outward kick, and recompute chassis mass
  properties. A detached wheel disables that wheel in the vehicle controller (zero suspension force,
  friction and engine force; verify the Rapier 0.36 API in P1-S04) so that corner drops onto its
  collider.
- **Debris persists** for the round as dynamic bodies that may sleep and wake (R58, R66): no TTL, cap,
  static conversion or merging.
- **Wreck:** a car with ≥ 2 wheels detached, or stuck/flipped past the recovery timeout, or out of
  bounds, is wrecked. Its remaining parts pop off as debris and its **husk stays as a dynamic body**
  (DEFAULT; see Q-A2). After ~2 s (R20) the player respawns at their own legal recovery anchor in a
  fresh intact car with the same identity and progress.
- **Rendering:** a loose part is its instance with the hinge rotation applied; a detached part is
  the same part-type instance with a physics-driven matrix; a missing part shows the core's dark
  bay. Detached parts keep the owner's paint colour.

## 7. Simulation (`jj-sim`)

### 7.1 Time, ticks and pauses

- 120 Hz fixed step, `dt = 1/120` (R61). The worker owns the accumulator and steps whole ticks;
  rendering interpolates between the last two snapshots.
- **Tick order:** apply commands and inputs due at this tick → set vehicle controls and surface
  friction → `update_vehicle` against current query data → `step` → read contact data and build
  damage episodes → apply structural changes (detach, spawn, respawn) → race progress → emit ordered
  events → publish snapshot when a buffer is free.
- **Pause reasons** compose: `manual`, `host-hidden`, `renderer-unavailable`, `performance-stall`,
  `fault`. Hidden time is never replayed; resume goes through a short visible countdown with input
  re-armed at neutral (master §7.1). Controller loss never pauses (R45).
- Persistently unplayable lag enters `performance-stall` at the last completed tick. Never enlarge
  `dt`, skip ticks, delete debris or refuse joins.

### 7.2 Determinism

Seeded RNG streams, stable iteration order, no wall clock in the sim, Rapier `enhanced-determinism`.
Same-build same-target runs produce identical full-state hashes. Native vs WASM physics identity is a
measured claim, checked where the fixtures live (S01 runner, S02 worker, S03 feel bank), not in the
perf task: the target is identical full-state hashes; if they differ, record where they diverge and
compare feel scenarios by their envelopes and discrete events (detach, lap, finish) instead, and
say so in the receipt. Canonical **map bytes** must match native vs WASM exactly, always.

### 7.3 Vehicle feel (P1-S03; targets are TUNE, judged at G-FEEL)

| Affordance | DEFAULT starting behaviour | Scenario |
|---|---|---|
| Suspension | Soft springs, strong damping, visible roll/squat/dive, single-settle landings | `idle-settle`, `jump-land` |
| Steer/throttle/brake/reverse | DRIVE X steers; up throttles; down brakes, reversing near rest | `progressive-brake`, `slalom` |
| Handbrake drift | ACTION left: rear friction slip × 0.35, 0.4 s smooth recovery; drifting charges boost | `drift-entry-exit` |
| Boost | ACTION right: meter 0–1, drains 0.35/s, recharges 0.12/s, +60 % engine force | `boost-hold` |
| Wheelie (the forward/back "lift and launch", master R64) | DRIVE pulled past the full-brake point (y < −0.85) preloads; releasing within 250 ms lifts the front, scaled by preload time (max at 0.4 s); needs ≥ 3 wheels grounded. **Payoff (DEFAULT, TUNE):** a well-timed release (preload ≥ 0.35 s) adds a short launch (+15 % drive force for 0.8 s) and lifts the front enough to hop kerb-height obstacles and small debris; an early release only lifts a little; a late one does nothing; steering is reduced while the front is up, so a badly placed wheelie costs time | `wheelie-ok`, `wheelie-fail`, `brake-no-wheelie` |

### 7.3a Affordance bank: what a player can always do

Physical Soccer's most useful tests weren't unit tests or parity numbers; they were **affordance
tests** that came out of playtests ("from comparable states a deliberate input produces useful
forward movement, and another produces useful backward movement") and stayed as invariants (master
§7.4a: desired affordances are the physics truth). We have no original game to trace against, so
these, plus the builds the owner accepts (§13.4), are our ground truth. Each row is a scenario-bank
case in `scenarios/affordances/` with an outcome signature; it runs from several starting states and
compares deliberate input with mash, hold and no-input baselines. Numbers are TUNE envelopes set at the
first accepted playtest.

| The player can… | Scenario | Owner |
|---|---|---|
| Go forward and backward from rest, on every surface, without an accidental wheelie or stunt | `fwd-back-rest` | S03 |
| Stop: progressive braking reaches a stop within an envelope from 10/20/30 m/s | `brake-stop` | S03 |
| Turn around inside the road width (three-point turn) | `turn-around` | S03 |
| Reverse out of a nose-in wall or barrier contact within 2 s | `unstick-wall` | S03 |
| Steer with authority at 5/15/30 m/s (heading change from full lock in 0.5 s, §14) and counter-steer out of a slide | `authority`, `slalom` | S03 |
| Enter and leave a drift on purpose, and gain boost from it | `drift-entry-exit` | S03 |
| Go meaningfully faster with boost than without, and boost-forever isn't the best line | `boost-line` | S03 |
| Wheelie only from the pull-release gesture, never from braking | `wheelie-ok`, `brake-no-wheelie` | S03 |
| Level the car in the air and land a jump on its wheels | `air-level`, `jump-land` | S03, M03d |
| Get back onto the route from the verge, a ditch or a debris pile | `rejoin-route`, `debris-pile-exit` | S03, S04c |
| Regain control within ~1 s after a side hit or a T-bone that doesn't wreck the car | `control-after-hit` | S04a |
| Keep driving with one loose wheel; lose the car with two detached | `loose-wheel-drive`, `two-wheels-off` | S04b, S04c |
| Recover from a flip (assist or Recover) and from out of bounds, every time | `flip-recover`, `oob-recover` | S05 |
| Get the same result from the same tick inputs whether they came from touch, keys or a pad | `source-parity` | S02, C05 |
| Fire OI! and drop a cone only on purpose, never from a cancelled touch | `utility-intent` | S08 |

Each row also gets the §13b.1 four-step check when its tuning changes.

### 7.3b Skill payoff: duels

The affordance bank proves a player *can* do things; the duels prove that doing them **well pays off,
doing them badly costs, and none of them dominates** (owner, 2026-10-02: "the drifting player around a
corner beats the normal player"; "the forward/back wheelie beats players when executed perfectly vs
not"). Each duel runs identical cars on the same greybox segment from the same state with scripted
inputs: a **plain** line, a **well-executed** technique (its timing found by `jj sim --sweep`, then
frozen in the fixture) and a **botched** one (too early, too late or held too long). The assertion is
an ordering on time to a gate after the segment, with TUNE margins. Mash never wins any duel.

| Duel | Expect | Owner |
|---|---|---|
| `drift-corner-duel` (hairpin at 18 m/s entry) | well-timed drift + its banked boost beats the brake-and-steer line; a mistimed drift loses to it or spins | S03 |
| `drift-boost-chain` (S-bend then a straight) | drifting both bends and spending the boost on the straight beats a grip driver over the sector | S03 |
| `drift-straight-penalty` | drifting down a straight is slower than driving it straight (drift isn't always better) | S03 |
| `wheelie-launch-duel` (from 0 and from 8 m/s) | a well-timed pull-release launch beats plain full throttle to a gate 40 m on; an early release is no better than plain; a late or held one is worse | S03 |
| `wheelie-hop-duel` (a kerb or a detached door across the line) | the hop clears it and keeps speed; plain driving hits it and loses speed | S03, S04b |
| `boost-placement-duel` | the same boost spent on the straight beats it spent into a corner | S03 |
| `air-control-duel` (greybox jump) | levelling the car lands on its wheels and keeps speed; no input lands nose-first and loses more; over-correcting is worst | S03 |
| `cone-defence` | a follower hitting a dropped cone loses a little time and is never wrecked | S08 |
| `mash-duel` | in each duel above, a mash script never beats the well-executed line | S03 |

L-plates (Full, R64) will reuse these duels with reduced payoffs for learners. Duels run in the
scenario bank like every other case; the owner's feel verdict decides the margins at playtests.

### 7.4 Recovery, out of bounds and flip assist

- **Flip assist** (load-bearing, per Spike C): when up·Y < 0.2 and speed < 2 m/s for 1 s, apply a
  visible self-right torque; if still inverted after 3 s, the car is wrecked (§6.3).
- **Recover** button on the controller: available when speed < 3 m/s for 1 s or inverted; 2 s
  penalty; respawn at the own anchor.
- **Out of bounds:** below the kill height or outside map bounds → wreck → respawn.

### 7.5 Race progress, placement and autopilot

- Route = the map's centerline with checkpoint gates (~every 40 m). Legal progress needs gates in
  order; the **recovery anchor** is the last gate passed, offset onto the centerline at a clear pose.
- **Placement service** (one service for start grid, respawn and drop-in): commit placements at tick
  boundaries against current cars and debris; 1.5 s spawn protection disables car/debris contacts
  (terrain and barriers stay solid) and only ends in a non-overlapping pose. **Start grid for any N
  without a cap or queue:** rows fill the map's declared start corridor back along the route; once
  the corridor is full, further cars are placed in it anyway under spawn protection (ghosted against
  cars and debris) and turn solid only when clear. Nobody waits, is refused or is dropped. A finite map
  can't hold a clear grid for every N, so the validator checks the corridor rule, not every N.
- **Drop-in (R63):** a new seat spawns ~3 s of route behind the last still-racing car, with that
  car's lap/gate state, marked as a late joiner. Reconnect and wreck use the seat's own anchor.
- **Autopilot:** pure pursuit on the centerline (look-ahead ≈ 0.8 s × speed), target speed from
  curvature × 0.7 (low skill), small noise, self-recovers when stuck 3 s. Visible badge "autopilot".
- **Race end:** 3 laps DEFAULT; 30 s window after the first finisher; absolute deadline
  `max(180 s, 2 × laps × refLap)`; finished cars stop colliding with racers and coast on autopilot;
  unfinished cars rank by legal progress (master §10.12 Race rules apply).

### 7.6 Utilities on the ACTION stick (DEFAULT for Playtest 1, no weapons yet)

The two-stick layout (R60) needs something on ACTION up/down before weapons exist:

- **Up (forward utility): "OI!" flash.** Headlights flash and a comic "OI!" pops over the car.
  0.5 s cooldown. Harmless; tests forward sector entry.
- **Down (rear utility): drop a traffic cone** 1.5 m behind the car, a light dynamic prop that
  persists (R58). 2.5 s game-time cooldown (a rule cadence, not a count cap). Tests rear sector entry
  and gives people something silly to do.
- Right/left: boost / handbrake drift (§7.3).

## 9. Session, round flow and players (`jj-session`)

- **Phases:** Lobby → Preparing → Countdown → Running → Finalising → Intermission → Preparing …;

- **Lobby:** big QR + code; player strip (number, name, colour, Ready, connection). Start policy:

- **Late joins** enter the running round immediately at the tail (§7.5). No queue, no "room full".

- **Leave / Sit out:** explicit, at a tick boundary; car withdrawn with a visible cue; debris stays;

- **Results:** in-memory session standings, Race points table from master §10.12. Nothing persists
  across host death (R84). The host page asks for confirmation before unload.
- **Names:** prefilled fun Aussie name, editable (≤ 32 graphemes, text only); colours from a

- **Per-tile LOD class** from tile height (DEFAULT: ≥ 540 px LOD0, ≥ 200 px LOD1, else LOD2).
- **Identity:** roof number, paint colour, nameplate over cars in other tiles, tile badge with
  number + name. **Identify** pulses the tile border and badge, outlines the car in every view and
  flashes the controller, ≤ 150 ms press-to-visible (R4). Auto-fires on join and respawn.
- **HUD per tile:** position, lap, boost meter, wreck/respawn countdown, connection state (autopilot,
  reconnecting). Host overlay: room code, connection diagnostics (direct/relay per seat, RTT).
- **Phone host / any aspect:** viewing-distance profiles (TV/desk/handheld); portrait grids stack
  vertically (R14).
- **Highlight reel** (P1-R09): the recorder keeps a ring of quantised transforms (30 Hz, ~20 s) plus
  retained clips around events (detach, wreck, air > 1.2 s, close finish; 3 s before, 2 s after),
  within a memory budget (R67, DEFAULT 64 MB). At round end it selects ~60 s, favouring players not
  yet shown, and plays it full-screen with a broadcast-style orbit camera and identity labels. It
  never touches live simulation.

## 13. Testing, evidence and the batch verifier

**Test style (owner, 2026-10-02): Physical Soccer's, not a pile of unit tests.** The two main layers
are **scenario banks** and **journeys**. A scenario bank is a Rust integration test per area
(`crates/<crate>/tests/<area>.rs`) that replays versioned JSON fixtures (`scenarios/<area>/*.json`)
twice bit for bit and asserts outcome envelopes; it prints one JSON line per case for comparison
and asserts known gaps explicitly, labelled as gaps, not passes. A changed profile versions its
fixtures and reruns the affected cases. A journey is a Playwright test that runs a real host plus
controller contexts through the real join path (QR decode or typed code, claim, real input reaching
the sim, HUD and results), locally against a dev server and, as the public smoke, against a preview
URL. Each behaviour is tested once, at the lowest level that shows it [PS "verify once"]; unit tests
are for codecs, goldens, pure kernels and reducer boundary tables, not for internals.

| Layer | What | Runs in |
|---|---|---|
| Scenario banks (main sim layer) | Feel, damage calibration (§6.3), recovery, placement, race rules, procgen seeds, determinism hashes; outcome signatures (§13b.1) | `cargo test -p <crate> --test <area>`; one case at a time with `jj sim` |
| Journeys (main web layer) | See the next rows: browser e2e, public smoke | Playwright |
| Rust unit/property (where it's the lowest level) | Codecs (+ goldens + fuzz), quantisation, layout kernel, reducer boundary tables, map and contract validators | `cargo test` |
| WASM parity | Same scenarios through the WASM build (Node); map bytes equality | wasm lane |
| Browser e2e journeys | Host + controller contexts over loopback WebRTC: join, drive, Identify, reconnect, drop-in, round loop. Controller specs also run in Playwright WebKit with mobile emulation (touch, viewport); real devices are the owner's playtests (P1-Q02 checklist, §15.0) | Playwright (on eris, §15.2) |
| Network qualification | Real phones on LAN, forced TURN UDP, TURN TLS 443, client-isolated Wi-Fi, loss/jitter | N08 harness + manual device rows |
| Perf | Host frame pacing at 1/4/8/16/24 tiles on Mac → TCL, worker cost, sim ms, draws/tris. Only on real GPUs in headed browsers, never headless/SwiftShader numbers | Q01 receipts |
| Visual | Captures: hero car, damage strip, 1/4/24-tile grids, identify, biomes. Structural captures may run headless; judged "looks" captures come from a real GPU (the Mac) | Playwright captures |

### 13.3 Tracing our own game

Physical Soccer debugged feel by tracing an instrumented copy of the original game and comparing it
row by row with the port. We have no original, so we trace **our own game** the same way: `jj sim
--trace` (P1-F05a) writes one row per tick (car poses, velocities, per-wheel contact/slip, inputs
applied, part states, events) as JSON lines, and `jj sim --compare` prints a side-by-side table: **ACCEPTED | CURRENT | TUNED**, where ACCEPTED is the trace from the last build
the owner accepted in a playtest (§13.4). Bug clips (§13b.6) replay into the same trace format, so a
playtest finding can be compared tick by tick with its fix.

### 13.4 The playtest loop: validated in the loop

What made Physical Soccer's feel work converge was a loop, not a ground truth: every owner playtest
produced a numbered round record (`docs/playtests/round-<date>.md`: what was understood, what was
investigated, what changed); each finding became a bead whose **probe reproduced it with numbers
before the fix** (Physical Soccer's "14 of 46 starts cycled before, none after"); the probe stayed
as a permanent scenario or journey; and the next playtest confirmed or reopened it. We do the same:

1. The owner playtests a preview and notes findings (a bug clip when possible).
2. The coordinator writes the round record with numbered findings and files a bead per finding,
   with its clip or scenario.
3. The worker writes the probe first (it fails, with numbers), fixes, and shows the same probe
   passing; the probe joins the affordance bank (§7.3a) or the journeys.
4. When the owner accepts a build's feel, its affordance-bank signatures and traces are saved as the
   **accepted baseline** (`scenarios/accepted/<preview-id>/`). Later changes compare against it
   (§13.3), and a regression against an accepted baseline is a failing test unless the owner accepts
   the new feel.

**Batch verifier:** `scripts/beads/batch-verify.sh` must learn the 0.2 layout (P1-F02): `crates/**`
→ cargo lanes, `web/**` → web build + unit + Playwright smoke, `tools/**` → tool tests. Remove the 0.1
suites. Workers run whatever their own area needs while developing (§13b.5); the verifier runs the
full suites once per wave across all submitted changes, with the heavy lanes on eris (§15.2).

**Not everything closes on a wave run.** Today `batch-verify.sh close` only accepts a green wave
receipt that contains the bead's own commits in this repo. Three kinds of acceptance can't meet
that: owner verdicts, work in the `jammers-deploy` repo and hardware receipts. P1-F02 adds an
**evidence close** for them (§15.0). Real devices are not bead acceptance at all (owner ruling,
2026-10-02): beads close on CI, emulators and Playwright, and the owner playtests the lot.

**Evidence rules** (master §17, `BEAD-DEFINITION-OF-DONE.md`): behavioural acceptance observable in
the running game, not just unit assertions; receipts name hardware, browser/backend, build and
cohort; test cohorts are samples, never limits.

## 13a. Validation in the loop: introspection, stepping and fixtures (R90)

**Why.** What made the Physical Soccer process work was a game whose state could be read as data,
tools to step through that state, and fixtures that pinned behaviours down. The agentic game-dev
survey (pro-kb `agentic-game-dev-techniques-report.md`, 2026-10-01) found the same across projects:
structured state beats pixels for agents, determinism and replay make claims provable, an external
pass/fail signal beats self-assessment, and the strongest setups make **the game itself the test
surface**. It also found that good tools are *extracted* once a step repeats, not designed up front.
This capability compounds: every area that becomes introspectable makes later work on it cheaper.

**Rule (REQUIRED, R90).** Every distinct part of the game ships with a way for an agent to:

1. **See** its state as structured data (not pixels) at a given tick or moment;
2. **Set up** a state directly (spawn, place, configure, jump to a phase) without playing to it;
3. **Step** time deterministically (tick by tick, or until a condition) and **replay** a recorded run;
4. **Assert** behaviour with a saved fixture (setup + inputs + expected observations or envelopes)
   that fails loudly and prints what it actually observed.

**How** each area does this is the implementing agent's call: a test API on the worker, a `--json`
CLI, a scenario file, a debug channel, whatever fits. Keep it lean, and extract shared tooling only
when the same step shows up in two areas. Test-only surfaces are never reachable from production
controllers (master §15.1). Captures still judge looks; owner playtests still judge feel.

| Area (tasks) | Must be introspectable | Example fixtures (illustrative, not a checklist) |
|---|---|---|
| Rooms, seats, controllers (N03–N07, G02, G03) | seats, claims, assignment generations, per-source freshness, autopilot state, selected ICE path | 40 fake controllers join over WebRTC → 40 seats, no duplicates, 40 tiles; one drops → autopilot within 2 s, room never pauses |
| Grid, cameras, identity (R04–R06) | tile rects, the camera per tile (mode, target, FOV), LOD class per tile, identity overlays | fake players join one by one → each join creates exactly one tile and camera; existing tiles keep order |
| Vehicle feel (S03) | per-wheel compression, slip and contact; yaw rate; speed; the authority metric | cornering at 15 m/s full lock stays in its yaw-rate envelope; drift entry/exit angles |
| Collisions and damage (S04a–c) | contact episodes, part health/state/loose angle, debris bodies (dynamic, sleeping), mass totals | 12 m/s T-bone → that door detaches; the debris is still dynamic and wakeable at round end |
| Race rules, placement, autopilot (S05–S08) | progress, gates, anchors, placement decisions, autopilot targets, utility cooldowns | drop-in during lap 2 → spawn ~3 s behind the last car with its lap/gate state |
| Round flow (N07b–c, G01) | director phase, presentation-clock timers, ready cohort, results | jump to 1 s before intermission ends; force-start with one not-ready seat |
| Controller input (N06, C02, C05) | sent records and bytes, detected actions with IDs, applied/expired results | a pointer cancel mid-wheelie fires nothing; press + release between two sends yields one action |
| Procgen (M01–M09) | the map document, validator report, per-biome placements, generation timings | seed 42 → identical bytes native/WASM; houses stay clear of the route |
| Rendering and perf (R01–R02, Q01) | draws/tris per tile, frame timings, LOD choices | the 24×24 bench stays inside its envelope |
| Audio (A01–A03) | cue triggers, which clip played, mix state | a finish triggers the winner cue exactly once |
| Deploy (D01–D07) | the preview register, smoke steps | a publish adds an index row with its smoke status |
| Later, Full: L-plates and the like | assist parameters in force, reductions applied | an L-plate boost pays out the configured fraction of the full boost |

**Done-ness.** Every §15 task's acceptance must be checkable by an agent from that area's
structured state (plus captures where looks matter). A task that adds behaviour also extends its
area's introspection and fixtures; that's part of the task, not a follow-up.

## 13b. Working method: what we carry over (ideas only, R1)

Two sources feed this section. The pro-kb survey `wiki/articles/agentic-game-dev-techniques-report.md`
(2026-10-01) is a neutral survey; this plan adopts the parts below. Physical Soccer's own process
(its `AGENTS.md`, `infra/README.md`, `docs/visual-review-contract.md` and plan §6.6/§7.5) is the
rest. Ideas are re-expressed for Jammers; no code, scripts or skills are copied (R1). Tags: **[KB]**
survey, **[PS]** Physical Soccer.

### 13b.1 Measure the game, judge the feel by hand

- **One sim funnel [KB: IW4L].** Phones, pads, keys, autopilot, test bots and replays all enter as
  applied-tick inputs through `jj-input` → `jj-sim`. Nothing changes sim state except journaled F05
  setup commands, so every run, including a playtest, can be replayed. Identical tick-assigned input
  gives the same result whether it came from touch, keys or a pad [PS].
- **Scenario bank with outcome signatures [PS §7.5].** A scenario stores its setup (map, seed, poses,
  velocities, part states), its input timeline and an *outcome signature*: the numbers that say what
  happened (yaw rate, slip, airtime, part states, travel, recovery time, energy). Envelopes are
  tolerances on signatures, not on raw positions.
- **The four-step check for any feel or damage change [PS §7.5].** (1) Replay the same scenario to
  show determinism; (2) change one input timing or one parameter to show agency and a causal
  difference; (3) run debug-only ablations and solver stress (more substeps/iterations, high speed) to
  reject numerical accidents; (4) the owner playtests. Mash and no-input baselines must differ from
  deliberate driving.
- **Energy accounting [PS].** For damage springs, detach kicks, flip assist and debris piles, check
  `Δ(kinetic + potential) − authorised work` stays under a solver-calibrated tolerance. Positive
  residual is a bug candidate (it's how "joints inject energy" shows up as a number).
- **Medians hide hitches [KB: Claude-of-Duty].** Perf receipts report p50/p95/p99 and max frame time
  with hitch attribution (shader compile, upload, GC, sim step), and warm shaders before a round.
- **Bot playtests [KB: threejs-game-skills].** For every generated seed the autopilot reports stuck
  windows (softlocks), lap-time spread, recoveries and out-of-bounds count.
- **Owner judges feel and fun [KB, PS].** Agents measure and tune toward envelopes; they never chase
  a number for its own sake, and a change that improves the numbers but plays worse loses.

### 13b.2 The `jj` CLI: one front door for agents

**Every feature earns its keep (owner, 2026-10-02).** A command, flag, helper, skill or harness feature
exists only when a named task needs it now; otherwise it waits. Before adding one, name the two tasks
that repeat the step, or the closing acceptance that needs it [KB: tools are extracted after the
method repeats]. Scaffolding that stops earning its keep is deleted.

So `jj-tools` builds one small `jj` binary for the **native** side, with three commands:

| Command | Earns its keep because | Built by |
|---|---|---|
| `jj sim` | The front door for every sim and map task: load a map or fixture, spawn, step N ticks or until a predicate, dump state as JSON, hash. Flags, each added by the task that first needs it: `--trace` (one JSON row per tick, §13.3), `--compare RUN` (ACCEPTED \| CURRENT \| TUNED table against another run or the accepted baseline), `--sweep PARAM=A..B` (CSV, for tuning), `--replay CLIP` (bug clips, §13b.6) | F05a from S01's runner; `--sweep` S03; `--replay` F07 |
| `jj procgen --seed N` | Generate, validate and dump a map and seed-bank reports, used by M02–M08 | M03a |
| `jj validate FILE` | One validator for vehicle sidecars/GLBs and maps, used by V01–V03, M01, the bake and CI | V01 (M01 adds maps) |

Deliberately **not** in `jj`: scenario banks run as plain `cargo test`; journeys, captures and perf
receipts are helpers inside the Playwright harness (F05b, F10), not CLI commands; publishing and
pinning are `jammers-deploy` workflows (D04, D06), so the game repo carries no deploy client; accepted
baselines are committed `jj sim --trace` outputs, not a command; no local-tunnel command, because a
preview exists from the first week (D04) and agents test on localhost; no scripted browser runner
beyond the journey helpers until two tasks need one.

Design rules [KB]: `--help` with worked examples; `--json` on everything an agent parses; each run
writes an evidence folder under `target/jj-runs/` (ignored) and exits non-zero with what it observed
on failure; **guardrails live in the tool**, not the prompt (the harness perf helper refuses
headless/SwiftShader browsers or an overlapping GPU job; test-only helpers refuse production URLs).
Skills call the tool instead of restating it; no MCP layer unless a terminal can't reach something.

**No per-bead scripts [PS].** Physical Soccer accumulated ~150 one-off `scripts/cNN_*` checks. Here a
bead's checks live as scenarios, fixtures and Playwright specs in the shared suites; probes stay in
scratch and are deleted before hand-off ("scaffolding out" [KB: IW4L]).

### 13b.3 Repo skills

Skills are written **after** their steps have repeated, and each points back to this plan and calls
`jj` [KB, PS]. Existing: `lowpoly-model-from-refs`, `vehicle-model-validation`, `game-model-prep`,
`threejs-primitive-modelling`. Extracted by P1-F09 from real use: `jammers-game-probe` (see/set/step/
assert, reproduce a bug clip, write a fixture), `jammers-visual-review` (capture → compare to the
named reference → review note), `jammers-ui` (operate the real UI at phone, laptop and TV sizes, the
UI states list, tokens; after Physical Soccer's UI skill) and `jammers-emulators` (the F08 lane). A01
writes `jammers-audio` from `tools/audio/README.md` (after Physical Soccer's voice/music skills). The
skills directory is also linked as `.agents/skills` so non-Claude agents see the same files [KB].

### 13b.4 Looks: captures and a fresh-eyes review

Looks acceptance (V03, R-tasks, M04–M07, C01, R07) uses the harness capture helper plus a **review note** written by
a fresh-context reviewer that isn't the implementing agent [KB: Gauntlet Loop, Anthropic evaluator;
PS visual-review contract]: the actual images opened at gameplay size (paths listed), the named
reference image, elements present/absent/ambiguous against it, the unaided first-look reading,
defects, and before/after for each repair. A fixture screenshot never claims a gameplay pass [PS].
Keep committed captures small: recapture only states a change affects [PS].

### 13b.5 Worker habits

- **Fresh context per bead** [KB, PS]: one bead per agent session; the coordinator starts a fresh
  agent for the next claim. State lives in the bead, git and evidence files, not in a chat.
- **Full development loop, batched verification (owner ruling, 2026-10-02).** A worker does whatever
  its bead needs to get the behaviour right: runs local or eris-hosted servers, sets up
  multi-controller and multi-device sessions, uses the emulators, debugs, inspects and sets game
  state through `jj`, writes and runs the scenario banks and journeys for its area, and loops on
  mechanics (control feel) or on a model (with visual inspection) until it meets the goal. Heavy runs
  go to eris. What a worker doesn't run is the batched verification: workspace-wide `cargo test`,
  whole Playwright suites, `batch-verify.sh` (the hook blocks those). It submits (commit + hand-off)
  without waiting for CI; the validator verifies many submitted changes in one wave, and a failure
  leaves the bead open and returns it to its agent with the failing note (code-first/batch-verify).
  A worker's own runs are development, never closing evidence.
- **Reuse statement** [PS]: a sim, feel, map or art bead names the existing fixture, trace, capture
  or spike it reuses and the exact gap it fills. No second toy or recapture of an unchanged baseline.
- **Repair beads reproduce first** [PS]: a bug bead first gets a probe, fixture or bug clip that
  fails, then the same one passes after the fix.
- **Bounded retries** [KB, PS]: after 2–3 consecutive failures of the same remote, CI or preview
  check, stop and reproduce in the smallest local harness; after three failed approaches to one
  problem, write what was tried into the bead and hand it back.
- **Learnings files** [KB: N64 decomp, `um` KB]: `docs/learnings/<area>.md`, append-only, one entry
  per non-obvious trap (Rapier footguns, Safari WebRTC quirks, TrueNAS behaviour). Skills link to them.
- **Honest labels** [PS, KB]: Playwright WebKit is "WebKit", not Safari; an iOS Simulator or Android
  emulator run is "emulator", not "device"; a value copied from a spike, the master plan or someone
  else's code is a *reference* until this code measures it.
- **One owner per coupled system** [KB: Claude-of-Duty, 66 → 26 defects]: the transport, the sim and
  the renderer each have one agent at a time (§15.2), not a fan-out.
- **Evidence per bead** [PS]: `docs/evidence/<P1-ID>/` holds a bead's committed evidence; a commit-msg
  hook rejects changes to another bead's evidence unless the message names it or says `Recapture:`.

### 13b.6 Playtest → bug clip → bead

The owner playtests the lot (§15.0), so playtest findings have to become reproducible work
[KB: IW4L `clip`]. On any host (previews included; it's host-only and saves a local file), a hotkey or
diagnostics button saves a **bug clip**:
build id, map bytes hash + seed, roster and the full applied-input journal from the start of the
current host session (free drive) or round (once rounds exist), plus the moment marked. `jj sim
--replay` re-simulates it and reproduces the end-state hash on the same target. The
coordinator files the bug bead with the clip attached (P1-F07); when a clip isn't possible, the bead
records the preview id, time and what was seen.
