# Telemetry plan: error reporting, health signals and game analytics

Status: **draft for owner review** (2026-10-20). Not yet a ruling; nothing here overrides R1–R139. Where this plan needs a
ruling it says so in §11. **Owner, 2026-10-21: Tier 0 is on by default with an opt-out** (§4, §11 item 1 settled).

Goal: agents keep the game bug-free on their own. Every failure a player can hit is detected, grouped, turned into a
reproducible bead and closed by an agent, and every structural weakness (a map family that empties rooms, a mode nobody
scores in) shows up as a number agents can act on. We collect only what fixes bugs or measures the game, store it on our
own hardware, and throw raw data away fast.

---

## 1. What we already have, and what it buys us

| Asset | Where | Why it matters here |
|---|---|---|
| Deterministic sim + applied-input journal | `jj-sim`, `web/host/src/clips/` (P1-F07) | A crash report can carry a **bug clip**, and `jj sim --replay` reproduces it bit for bit. Most products get a stack trace; we get the whole round. This is the centrepiece. |
| Session recorder (P1-F12) | `web/host/src/clips/session.ts` | Already records whole sessions locally; today it never uploads. Consented upload reuses it. |
| Frame meter | `clips/recorder.ts` `FrameMeter` | Long-frame counts for performance summaries. |
| Worker fault path | `worker/client.ts` (`kind: 'fault'`) | A sim crash is already a typed event. |
| Rate limiter | `jj-server/src/rate.rs` | Reused for the ingest route. |
| Build id in every bundle | `__JJ_COMMIT__` | Every event names its build; regressions are per build. |
| Previews tagged in git | `preview/<id>`, `release/<stamp>` (R117, P1-D08) | Telemetry joins to exactly what was deployed and where. |
| Maps are seeds | `jj-procgen` | "Map X empties rooms" names a seed an agent can regenerate and review. |

## 2. Principles

1. **Fixable or measurable, else not collected.** Every event type names the bug class or metric it serves (§5); one
   without a consumer is deleted.
2. **No personal data by default.** No IPs stored, no player names, no free text, no persistent device id, no verbatim
   user agent, no precise GPU string, no location. Ids are random per room and die with it.
3. **Consent at the moment it matters.** Rich reports (replay clip, breadcrumbs, the player's note) leave the device
   only after someone presses Send, or chose "always send" earlier (§4).
4. **Summarise on the device.** Phones and hosts send per-race summaries and histograms, never per-frame or per-tick
   samples (the existing logging rule holds: nothing logs per frame).
5. **Our hardware, our origin.** Ingest is a route on `jj-server` (same origin, so no new hostname, CORS or blocker
   trouble); storage is on TrueNAS. No third-party analytics, no runtime CDN (R70). The error UI is a self-hosted
   Sentry-protocol server.
6. **Raw data is short-lived; rollups are forever.** Raw events live days, rollups live indefinitely and are tiny.
7. **Agents act on triggers, not polling.** New or regressed problems fire a webhook; nothing spins an LLM on a timer.
8. **Synthetic traffic is labelled.** CI, smoke, Playwright and agent journeys hit previews constantly; their events
   carry `synthetic: true` and never count in analytics.
9. **Telemetry is testable (R90).** Each detector has a fixture or journey that triggers it and asserts the event.
10. **Budgets here are telemetry budgets, not gameplay caps.** Size limits on uploads and quotas on reports never limit
    players, controllers, cars, tiles or debris (the no-caps rule). If a report won't fit, the report is trimmed, not the
    game.

## 3. Architecture

```text
 host browser ─┐                       ┌─► spool/errors/*.ndjson ──► forwarder ──► GlitchTip (issues UI, grouping,
 controller ───┼─► POST /api/v1/t ─────┤                                            source maps, retention)
 server itself ┘   (jj-server)         ├─► spool/events/*.ndjson ──► nightly job ─► DuckDB: raw (14–30 d)
                   validate · scrub    │                                            + rollups (forever)
                   quota · append      └─► spool/clips/<fp>/<id>.jjclip (consented only)
                                                │
                       watcher (on ingest) ─────┴─► new / regressed fingerprint ─► Gitea workflow ─► br bug bead
```

### 3.1 Clients: one tiny reporter, `web/shared/telemetry/`

Own code, a few KB, shared by host and controller. No Sentry SDK: it auto-collects URLs, console text and DOM
breadcrumbs we don't want, and it's heavy for the controller route (controllers stay light).

- Queue in memory; flush every 60 s, at the end of each race, and on `pagehide` via `navigator.sendBeacon`.
- One envelope per flush: `{v, build, realm, surface: host|controller|landing, synthetic, room_session, events[]}`.
- **Dedup on device:** the first occurrence of an error fingerprint sends full detail; repeats in the same session send
  only a count.
- **Client token bucket:** a looping error can't flood; overflow becomes one `telemetry.dropped{n}` event.
- Stack parsing into frames (file, line, column, function) so the server side can symbolicate with source maps.
- Breadcrumbs: a ring of the last ~100 **structured game events** (phase changes, joins, leaves, respawns, ICE state
  changes), never console output or DOM.

### 3.2 Ingest: `POST /api/v1/t` on `jj-server`

- Rejects bodies over a size limit (clip uploads use a separate route with a larger one), unknown schema versions and
  builds that aren't a live preview or production.
- Applies `rate.rs` per source; the IP is used for that in memory and never written.
- Validates each event against the schema (§5.1); unknown fields are dropped, not stored.
- **Server-side fingerprint quota:** after N full examples of a fingerprint on a build (e.g. 20), later ones are
  counted, not stored. We already have enough examples to fix it.
- Appends NDJSON to an hourly spool file on a TrueNAS dataset. The server never waits on GlitchTip or DuckDB, so a
  telemetry outage can't hurt a game.
- The server reports on itself the same way: panics (panic hook), 5xx counts, signalling errors, TURN credential
  failures, room lifecycle (§5.3).

### 3.3 Storage and platforms

| Store | What | Why this one |
|---|---|---|
| **GlitchTip** (self-hosted TrueNAS app, Postgres + Redis, ~1 GB RAM) | Errors and crashes: grouping, source-mapped stacks, first-seen/last-seen per build, a UI for the owner, an API for agents | Speaks Sentry's protocol and API, so `sentry-cli` uploads source maps from CI and the standard tooling works. Built-in event retention (`GLITCHTIP_MAX_EVENT_LIFE_DAYS`). Self-hosted Sentry needs ~16 GB and a dozen services, too heavy; hosted Sentry puts player data off-box. |
| **DuckDB + Parquet** on the telemetry dataset | Gameplay analytics, health metrics, rollups | No daemon. A nightly job compacts NDJSON to day-partitioned Parquet, builds rollups and purges. Agents query it with plain SQL (`jj telemetry sql …` over `ssh truenas`). At our volume this is plenty. |
| Clip spool (`clips/<fingerprint>/`) | Consented bug clips and session recordings | Linked from the GlitchTip issue and the bead; copied into `docs/evidence/<ID>/` when a bead takes one. |

**Scale-up path, not now:** if raw volume passes ~1 M events/day, move events to single-node ClickHouse (TTL and
materialized-view rollups do the purge natively). Rejected: PostHog self-hosted (ClickHouse + Kafka, heavy, built for web
products, not game semantics), Plausible/Umami (pageviews, no game semantics), Cloudflare Workers Analytics Engine
(off-box, outside R79's approval).

**Volume estimate** (an upper bound so we know the purge is safe): 100 rooms/day × ~300 events × ~250 B ≈ 7.5 MB/day raw
NDJSON, ~1 MB/day Parquet. Errors are a fraction of that. Clips are ~50–500 KB each, stored at most a few per fingerprint.
A year of rollups is a few MB.

## 4. Consent: three tiers

| Tier | Contents | Default | How it's shown |
|---|---|---|---|
| **0: anonymous health** | Error fingerprints and counts, crash/fault types, detector hits (§6), per-race performance summaries, coarse device class (browser family + major version, OS family, GPU vendor/tier, screen class), gameplay events with no identities (§5.3) | **On**, with an off switch | One line in the host menu's diagnostics footer (R96): "Jammers sends anonymous crash and game stats. [Details] [Turn off]". The landing page privacy note says the same. Controllers send only Tier 0 and say so on the Join page. |
| **1: incident report** | Tier 0 plus the **bug clip** (names replaced by seat numbers), breadcrumbs, full detector context, optional typed note | **Asked when something goes wrong** | A footer toast, never over a player's tile and **never mid-race**: it waits for the results screen or lobby. "Something went wrong. Send a report with a replay so we can fix it? [Send] [Always send] [No]". Hotkey/diagnostics bug clips (§13b.6) get a Send button too. |
| **2: always send** | Tier 1 sent automatically on every incident; whole-session recordings on a crash | Off; on if the host picks "Always send" | Stored per device (`localStorage`, with try/catch); revocable from the same menu. The owner's own machines and playtests run with it on. |

The host's consent covers the room's sim data, because the clip lives on the host. A phone never uploads more than Tier 0
on its own; it can't, it has no sim.

**Why Tier 0 is on by default:** none of it identifies a person, and with it off we'd fix only what testers report.
§11 asks the owner to confirm this.

## 5. The semantic layer

### 5.1 Events are versioned data

`assets/telemetry/events.json` (data over code): each event has a name, version, fields with types and allowed values,
its tier, its **consumer** (which detector, metric or rollup reads it) and a sampling rule. A validator in `jj-tools`
generates the TypeScript emit helpers and the Rust ingest validator, and CI fails on an event without a consumer or a
field outside the schema. Renaming means a new version; the rollup job reads both during a transition.

### 5.2 Two categories, as the owner framed them

**A. Bugs and error conditions** (§6): something is definitely wrong. Each has a fingerprint and is a bug bead the moment
it's new. Easy to act on.

**B. Structural signals** (§7): nothing crashed, but the game is worse than it should be: rooms abandoned on a map
family, a mode nobody scores in, a join funnel leaking at the QR step. These are rates compared across maps, modes and
builds. Harder: they need enough samples, a baseline and judgement about whether to change the design.

### 5.3 Core events (Tier 0, anonymous)

| Event | Fields (abridged) | Feeds |
|---|---|---|
| `room.created` / `room.ended` | room_session, build, realm, host device class; end reason (`host-left`, `host-crash`, `idle`, `normal`), duration, peak players, races run | abandonment, session length, crash-free rooms |
| `player.joined` / `player.left` | seat, source (`phone`, `pad`, `keyboard`, `bot`), join time-to-ready, leave reason (`left`, `disconnect`, `ice-failed`, `timeout`), phase at leave | funnel, mid-race quit rate |
| `funnel.step` | `landing`, `host-open`, `qr-shown`, `join-page`, `join-submitted`, `webrtc-up`, `first-input`, `race-started` | where joining breaks |
| `race.started` | seed, map hash, track family, biome mix, length class, mode, players, bots, assists on | every per-map/mode metric |
| `race.finished` | per seat: position, finish time or DNF, laps, respawns, stuck count, boosts, drifts, items used, hits dealt/taken, parts detached; race duration; winner margin | competitiveness, mode health, mechanic uptake |
| `race.abandoned` | phase, elapsed, players left, last positions | abandonment by map/mode |
| `round.next` | rematch, new track, kept track (R125), back to lobby, room ended | the best fun proxy we have |
| `perf.race` | frame-time histogram (fixed buckets), long frames >33/100 ms, sim tick-time p50/p95, worker stalls, GPU tier, tiles, players, debris live at end | host performance per device class |
| `net.summary` (controller) | input-age histogram, RTT p50/p95, path (LAN / STUN / coturn / Cloudflare TURN), reconnects | connectivity health, TURN fallback rate |
| `tuning.changed` | which setting, from/to (owner tuning menu) | what the owner tunes, defaults that never survive |

Per-seat data is tied to a seat number for the race only, never to a person or device.

## 6. Detectors: catching things going wrong

Each detector emits a fingerprinted `error.*` or `anomaly.*` event. Hard failures always open a consent prompt (§4); soft
ones only count unless the same fingerprint repeats in a session.

**Hard failures (host and controller):** `window.onerror`, `unhandledrejection`, worker `onerror` and the sim `fault`
message, WASM panics (panic hook → message + location), WebGL context lost / WebGPU device lost, AudioContext failures,
asset load or decode failures (fetch non-200, GLB/texture decode), `securitypolicyviolation`, IndexedDB quota errors,
WebRTC: ICE failed, signalling errors, data channel closed unexpectedly, TURN credential fetch failed.

**Watchdogs and invariants (host):**
- Sim stall: no journal message for > N s while racing.
- Crash loop: host reloaded within 60 s of the last load in the same tab (a `sessionStorage` marker): reported as a
  crash even when nothing threw.
- Car stuck: speed ≈ 0 with throttle held for > N s and not respawned; fell below the world floor; respawn loop (k
  respawns in t s).
- Race invariants: lap faster than the track's physical minimum, checkpoint skipped, race over its time limit without
  finishing, NaN/inf in any body state, position order inconsistent with progress.
- Perf: sustained long frames (k frames > 100 ms in 10 s), memory growth across rounds where the browser exposes it.
- Input: input age over threshold for a seat, a controller sending nothing while connected and in a race.

**Server:** panics, 5xx by route, signalling relay errors, rooms with zero joins after N minutes (a QR or join-path
break), TURN issuance failures, rate-limit hits by route.

**Fingerprint** = surface + error type + top in-app frames after symbolication (or detector name + invariant + map
family for anomalies). Normalised so line numbers in a new build don't split an issue: GlitchTip groups on symbolicated
function names.

## 7. Structural analytics: the harder half

Nightly rollups (DuckDB views over Parquet), each with sample size and a confidence interval, sliced by **build, track
family, biome mix, length class, mode, player count and device class**:

| Metric | Question it answers |
|---|---|
| Room abandonment rate (ended before a race finishes) | Which tracks or modes empty rooms? |
| Mid-race quit rate | Which tracks frustrate? |
| Rematch / keep-track rate | Which tracks or modes do people want again? (best fun proxy) |
| DNF rate and finish-time spread | Too hard or unfair? Is catch-up (R125) working? |
| Winner margin, position changes per race | Are races close and lively? |
| Mechanic uptake (drift, boost, items) per race | Are players finding the mechanics? Is one dominant or dead? |
| Respawns and stuck count per km, by biome | Where is the track generator making traps? (names seeds) |
| Join funnel conversion by step and device | Where do players give up joining? |
| TURN fallback rate, ICE failure rate by network path | Is connectivity holding? |
| Crash-free rooms and races per build | Release health, the promotion gate (§8.3) |
| Frame-time p95 by GPU tier and player count | Do host budgets hold as rooms grow? (never a player cap) |

**Statistics, honestly:** a couch game has small numbers. Every rollup carries n; a comparison needs a minimum sample
(e.g. 30 races per slice) and uses Wilson or Beta intervals; the digest says "not enough data" rather than guessing.
Before/after build comparisons beat cross-sectional ones (fewer confounders). Playtests stay the qualitative check; these
numbers say where to look.

## 8. The autonomous loop

### 8.1 Bugs: fingerprint → bead → fix → regression guard

1. **Trigger, not polling.** The forwarder runs after each spool rotation (hourly) and fires a Gitea
   `workflow_dispatch` when it sees: a **new fingerprint**, a **regression** (a fingerprint marked fixed in build X
   reappears in a later build), or a **spike** (rate per room over k× its 7-day baseline).
2. **Deterministic filing (no LLM):** the workflow runs `jj telemetry triage <fp>`, which files or updates a bug bead
   with `external_ref = ERR-<fp>`: GlitchTip link, symbolicated stack, builds affected, rooms affected per day,
   device classes, breadcrumbs and the best clip if any. Priority comes from impact (crash-free-room loss), not volume
   alone. A known fingerprint just updates counts on its bead.
3. **Agents work it as normal bead work** (`br ready`, CI rule 8): with a clip, step one is `jj sim --replay` to
   reproduce; the fix commits **the clip as a scenario-bank fixture** so it can never return silently.
4. **Closing marks the fingerprint fixed in the build** (`close.sh` writes the build id to GlitchTip's "resolved in"
   via its API). A later occurrence is a regression and reopens the bead automatically.
5. **No clip?** The bead records the detector context and asks for one: the next occurrence on a Tier 2 device (the
   owner's machines, playtests) will usually bring one.

### 8.2 Structural: weekly digest → candidate beads

A weekly Gitea workflow runs the rollups and writes `docs/evidence/telemetry/<date>-digest.md`: top movers by build,
slices outside their intervals, worst seeds by stuck/respawn rate, funnel drop-offs. Agents may file **generator or
tuning beads** straight from it when the fix is data (a seed family's trap, a profile value), since those are reversible
and testable. **Design changes** (mode rules, mechanic changes) go to the owner as a digest line, not a bead: rulings are
the owner's.

### 8.3 Release health gates promotion

`scripts/promote.sh` already checks a preview before production (P1-D08). It also checks: crash-free rooms on that
preview (synthetic excluded) ≥ the production build's, and no new hard-failure fingerprint without a bead. The owner
still promotes by hand; this is information on the screen, not a lock.

## 9. Retention and aggregation

| Data | Kept | Then |
|---|---|---|
| Spool NDJSON | until compacted (≤ 48 h) | deleted |
| Raw events, previews | 7 days | rolled up, deleted |
| Raw events, production | 30 days | rolled up, deleted |
| Synthetic events | 48 h (debugging CI only) | deleted, never rolled up |
| GlitchTip events | 30 days | GlitchTip purges; issues (grouping, counts) stay |
| Clips, no bead | 14 days, at most 5 per fingerprint per build | deleted |
| Clips, linked to a bead | until the bead closes + 30 days | the ones that became fixtures live in git |
| Daily rollups | forever | (a few MB per year) |

The nightly job enforces all of it and writes a one-line receipt (rows in, rows rolled up, rows purged, disk used), so a
silent purge failure is visible. Disk alarm at 80 % of the dataset quota stops raw storage (rollups and errors keep going).

## 10. Build order (bead candidates)

Each is one session or less; acceptance includes a fixture or journey that fires the thing (R90).

| # | Bead | Acceptance in short |
|---|---|---|
| T01 | Event schema `assets/telemetry/events.json` + validator + generated TS/Rust types | CI fails on unknown field or consumer-less event |
| T02 | `jj-server` ingest route, scrub, quotas, spool | Unit + scenario: oversize, unknown build, quota overflow, IP never written |
| T03 | `web/shared/telemetry` reporter (queue, beacon, dedup, token bucket, stack parse) | Journey: forced error on host and controller arrives once with count |
| T04 | Hard-failure detectors (§6 first list) | Journey per detector via `__jjTest` fault hooks |
| T05 | GlitchTip TrueNAS app + forwarder + source-map upload in CI | A forced error shows a symbolicated stack in GlitchTip for that build |
| T06 | Consent UI: footer line, post-race prompt, always-send, Join page note | Visual self-review; no prompt mid-race (journey) |
| T07 | Clip upload route + name scrubbing + fingerprint link | A consented clip replays with `jj sim --replay` from the spool |
| T08 | Core gameplay events (§5.3) | Scenario fixtures assert the exact event set for a scripted race |
| T09 | Watchdogs and invariants (§6 second list) | Scenario-bank cases trip each one (stuck car, NaN body, crash loop) |
| T10 | Nightly job: compaction, rollups, retention, receipt | Fixture spool → expected Parquet, rollups, purges |
| T11 | Triage workflow: new/regressed/spike → bead (`ERR-<fp>`) | Synthetic new fingerprint files exactly one bead; repeat updates it |
| T12 | `close.sh` marks resolved-in-build; regression reopen | Fixed fingerprint in a later build reopens its bead |
| T13 | Weekly digest + promotion health readout | Digest from fixture rollups; promote.sh prints health |
| T14 | `synthetic` flag in Playwright, smoke and agent journeys | Smoke traffic never appears in rollups |

T01–T05 give error reporting end to end; T06–T07 make reports reproducible; T08–T10 start analytics; T11–T14 close the
loop.
