## 1. Executive summary and decisions

### 1.1 What 0.2 is

Joystick Jammers is a **couch-first car party game**: one host screen (a phone, laptop or 4K TV)
renders the world; everyone else plays with whatever they have — a phone, a gamepad plugged into any
device in the room, or a key cluster on a shared keyboard. People can drop in at any moment and be
driving within seconds. Races and derbies are physical, destructive and loud; cars shed doors and
wheels that stay on the track as obstacles; an Australian announcer calls it; the look is bold and
comic.

0.2 is a deliberate, significant rework:

1. **Rust server from day 0** (HTTPS room/signalling services), **WebRTC controllers**, a clean Rust workspace (§13).
2. **Controls become source-agnostic and twin-stick** (§4), with **identification** built in (§5).
3. **Dynamic grid** with drop-in and **per-car first/third person**, plus a **shared Overview** for
   arenas; **any screen size or aspect on one shared display**. Extra displays require separate
   owner approval and are not a reason to delay the single-screen game (§6, G-SCREENS).
4. **Suspension-forward, fun car physics** measured by a scenario bank (§7).
5. **Part-based destruction** with persistent debris and destructible environments (§8).
6. **Procedural Australian tracks** with real surface variety (§11).
7. **Comic-adjacent visual rebuild** through a contract-driven art pipeline; all models replaced (§12).

## 2. Fun pillars

Check every feature against these.

1. **Find your car in one glance** — at the smallest tile, from the couch (§5).
2. **Physical, not scripted.** Crashes, weapons, stunts and destruction are forces and contacts;
   multi-car chaos emerges. The *next* action should be legible from what you can see; the *outcome*
   may surprise.
3. **Low floor, high ceiling.** Driving within 10 s of joining; practice visibly wins (lines,
   drifting, boost timing, jumps, weapon leading, using debris).
4. **Nobody is out of the fun for long.** Drop-in, fast respawns, no derby knock-outs (R21), one-press rematch.
5. **Any controller, equal footing.** A phone player can beat a pad player.
6. **Bold, comic, juicy.** Significant hits have sound, a comic impact graphic and a camera response
   sized to the event; visual emphasis never freezes the shared live simulation.
7. **Zero-friction session.** QR → driving in < 20 s; setup never hides the QR.

Anti-goals: hidden catch-up; invisible timers that make identical situations behave differently;
cameras that thrash; art that only looks good in Blender; features copied from elsewhere without a need.

## 3. Vocabulary and roles

### 3.1 Authority and deployment roles

The **host** owns the room coordinator, membership/assignment decisions, game rules, physics and
scores. It runs in a browser on the main display device; a phone may be that device. The browser
main thread renders/UI; a dedicated simulation worker is the **recommended Jammers placement**.
This is not a claim that Soccer already uses that worker arrangement.

The **Rust room/signalling service** authenticates/fences its active host registration, maintains
ephemeral signalling routes and serves build metadata. Controller gameplay uses WebRTC to the host,
directly or through TURN; the Rust service is not a second room-state authority or mandatory input hop.
Cloudflare supplies STUN/TURN initially. It is a connectivity provider, not the room registry or game
server. A connection that selects a direct path sends its gameplay to the host without TURN relay.
Its small durable registration record (§13.3) preserves credentials/build binding and fencing across
server restarts; live sockets and routes are reconstructed. It contains no authoritative player
roster, physics or standings.
Ancillary server storage for reports/ratings is separate and never participates in a physics tick.

A **controller** sends controls and receives a lightweight HUD. A hub contributes independently
claimed gamepads/key clusters. Neither controller nor hub downloads the world renderer or sim.
**Hosted shared-screen play** is the 0.2 product. Do not call it offline Local mode. Separate remote
rendered views/extra displays require G-SCREENS; genuine LAN/offline operation remains deferred.
Neither is a joining prerequisite. Small core boundaries keep future work possible.

### 3.2 Typed identity

| Primitive | Meaning |
|---|---|
| RoomId | Stable party identity, distinct from a short invitation code. |
| EndpointId | A resumable browser/controller station; not a transient socket. |
| SourceId | A touch surface, gamepad or keyboard cluster within that endpoint. |
| SeatId / ControllerIdentity | Stable player identity, colour/pattern/number, preferences and score; owns one car. No global human account. |
| ChannelId | One authorised input stream to that seat's current car. |
| AssignmentGeneration | Fences old device/source bindings after replacement. |
| ConnectionEpoch / HostEpoch | ConnectionEpoch fences sockets; HostEpoch changes only on authorised host replacement, never ordinary reconnect. |
| CredentialRevision | Monotonic room credential-revocation counter persisted at the registration service and in checkpoints, preventing stale exports from silently restoring revoked seat proofs. |
| SessionRevision / CommandId / EventId | Orders accepted room changes and deduplicates commands and effects; independent of render frames. |
| PreparationId | Identifies one candidate map/rules/assets preparation; superseded jobs cannot commit. |
| RoundId / VehicleLifeId / EntityId | Separate match scope, respawn incarnation and simulated object identity. |
| DisplayId / TileId | Presentation identities, not gameplay ownership. |

One car has one active controller assignment. Reconnect changes a transport lease, not the player,
car, damage or score. A replacement device takes an existing seat only through an explicit authorised
handoff; its old sender is fenced. Do not use socket IDs, IP addresses, gamepad indices, names or
hardware serials as durable player identity. Dynamic collections have no participant-count maximum.

### 3.3 Topologies and voting

Ordinary phone play is **one phone controlling one car**. The split-phone-two-racers preset is removed.
Host-attached pads/keys and a hub's independently claimed controllers remain supported; built-in
preset examples are not a device/player maximum. An endpoint may expose as many independent
sources as the actual platform exposes, without the game imposing a smaller number.

**One ballot per joined controller identity**, retained across reconnect. A hub's independent pad
claims each get their own ballot; a hub browser is not one vote for all its players. A stale tab does
not add a ballot for the same identity. Do not build global-person tracking or anti-Sybil accounts.

### 3.4 Ordinary recovery versus break-glass

> **Deferred by R84 (2026-10-02).** Checkpoints, restore after host death, recovery exports and
> break-glass replacement are out of the Minimum build, possibly forever. A dead host ends the room.
> Kept: same-device seat resume and host re-registration after a server restart (Playtest-1 plan
> §2.2, §5.5). The text below is retained design reference for any future revisit.

Backgrounding the host preserves the current live world and pauses (§7.1); it does not reload it.
An actual page/process loss may reload the pinned build and recover settings, seats and committed
results from host storage. Restart only the interrupted round if its live world was lost, visibly.
Host replacement is an explicit emergency action using an authorised recovery capability and
available checkpoint. No automatic migration, periodic reload or routine failover is required.
A paired host-control phone can administer the room; it is not a second simulator. A short public
room code grants neither existing-seat ownership nor host-replacement permission.

**Recovery contract:** persist a versioned `RoomCheckpoint` containing realm/build, room identity,
seat assignments and credential verifiers, preferences, event standings, completed result IDs and
the interrupted round's map/rules/profile references. Commit a completed result and the resulting
standings together in one IndexedDB transaction, keyed by `RoundId`; retrying cannot score twice.
An acknowledgement of an in-memory change is distinct from confirmation that its checkpoint was
saved. Save at meaningful state changes, never rely on an unload handler. [S13]

Store the interrupted round's canonical map bytes with the checkpoint (a content-addressed record
in the same transaction is sufficient). Recovery export bundles those bytes and required non-bundled
profile data, plus hashes, rather than pointing a new device at the lost host's IndexedDB. Build-owned
assets/profiles resolve from the retained immutable build. Include CredentialRevision and the saved
ledger revision; do not label newer in-memory state as the last confirmed save.

On reload, restore the last confirmed checkpoint. An interrupted round is void and restarts with a
new `RoundId`, the same map/rules and no provisional points carried into standings. Completed results
contained in that checkpoint remain committed. Minimum does not promise live Rapier-world crash recovery. If storage is unavailable,
play may continue with an explicit “Progress cannot be saved on this device” state and retry/export;
do not claim that unsaved identities/results will survive page loss or block new entrants on disk I/O.

Emergency replacement needs **both** an authorised recovery grant and a checkpoint actually available
to the replacement device (for example an export saved before loss). Host-only IndexedDB is not
remotely readable. Show checkpoint time/revision, last included result and what will restart before
activation; an older export can lose later committed results, joins and assignment changes. State
that cutoff explicitly, then atomically advance host fencing at the registration service. Without a recoverable checkpoint, offer a new room and explain the loss rather
than inventing standings. End game preserves the party; Disband revokes registration/recovery grants,
clears resumable credentials and cannot be undone by a stale host reconnect.

### 3.5 State boundaries and clocks

| Owner | Authoritative state | Consumers / boundary |
|---|---|---|
| `jj-session` in host worker | Seats, assignments, seat/gameplay preferences, pause reasons, RoundDirector, committed results/standings | Serialises commands and consumes sim facts; emits revisioned UI state and storage intents. Device ergonomics/preferences remain controller-local (§10.6a). |
| `jj-sim` in host worker | Bodies, progress, damage, weapons, bots and current-round scoring facts | Steps at 120 Hz; emits ordered events once; cannot independently advance room phase. |
| Browser presentation | Cameras, interpolation, widgets, audio and GPU resources | Reads state/events; UI requests changes through commands, never mutates scores or physics. |
| Storage adapter | Last successfully saved checkpoint and optional replay data | Reports transaction success/failure; never decides gameplay. |
| Rust discovery/signalling service | Room locator/build binding, current host registration and credential fencing | Brokers authorised session establishment; issues temporary ICE configuration. No input/HUD forwarding, physics or game roster. |
| Cloudflare STUN/TURN initially | Connectivity allocations and their credentials | STUN assists address discovery; TURN relays encrypted peer traffic when selected. Neither decides game state. |

Gameplay timers use simulation ticks. Lobby/force-start/intermission/vote timers use a separate
host-owned **active presentation clock**, stopped by any room pause; hidden time never drains them.
Transport freshness/leases use the receiver's monotonic wall clock, and preview expiry uses server
UTC. Do not compare `performance.now()` values from different devices as if they shared an origin.
While the host is unreachable, controllers show “Reconnecting to host”; only confirmed host state
may say “Host paused” or “Room ended”. This distinction prevents a network fault from ending a party.

### 3.6 Entry, capabilities and host administration

**Minimum entry contract.** `ResolveRoom(code, realm)` returns the immutable build/route binding and
one of `available`, `host-unreachable`, `disbanded`, `expired`, `not-found`; a network error is a
separate retryable result. The code is a locator, never a credential. Load the bound controller
bundle before `Hello`; protocol/build mismatch offers a safe reload to that binding without claiming
a second seat. A missing retained build shows a service fault; never silently joins a different room.
The public Join area includes **room-code entry and a “Scan QR code” button together** (Minimum),
including when reached from the public landing page. Scanning is an optional way to join, not an
optional feature to defer. Paste/type code and opening the QR URL remain available without camera,
fullscreen, wake-lock, vibration, audio or persistent-storage permission.

Opening the scanner is an explicit user action: request video only, prefer the rear camera when
available, show a live preview with Cancel/“Enter code instead”, and keep any typed code on return.
Decode frames locally; do not upload camera images. Stop every camera track on success, cancel,
navigation or backgrounding; after backgrounding, offer an explicit resume. Deduplicate repeated
detections so one scan enters the normal room-resolution flow once, without claiming another seat.
Accept recognised public room URLs or valid room codes; validate origin/path and preserve the
preview realm/deployment binding. Never open arbitrary decoded URLs, interpret arbitrary text as
commands, or redeem host-control/recovery grants through the public join scanner.

Lazy-load a bundled, self-hosted QR decoder when scanning starts; a native `BarcodeDetector` with
QR support is an optional optimisation, not the only implementation. Denied/busy/missing camera,
unsupported capture or an insecure context gives a short explanation with working manual entry.
Camera capture requires a browser secure context; this does not solve future plain-HTTP LAN camera
access. Qualification covers iOS Safari/Android Chrome, decoder fallback, cancellation, repeated
detections, unrelated QR codes and production/preview links. See [camera requirements](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
and [BarcodeDetector compatibility](https://developer.mozilla.org/en-US/docs/Web/API/BarcodeDetector).
Use an unambiguous uppercase room-code alphabet excluding O/0 and I/1/L, with copyable code/link
and case-insensitive entry; illustrative ROO7 QR artwork is not the production encoding. Blind
mockup readers repeatedly read it as R007, so exact-code legibility is an explicit entry fixture.

Bootstrap uses `CreateRoom(RequestId)` and `ClaimSource(RequestId, EndpointId, SourceId)` with
retry-stable request IDs. The host acknowledges a claim with seat identity, grant, assignment
generation and session revision; it deduplicates the claim before issuing a car. Keep the same
request ID through loss of its reply. A memory-only endpoint can play but is told that closing it
can lose its resume proof. A non-rendering controller may use a small `jj-input` WASM module; the
route dependency test forbids `jj-sim`, `jj-procgen`, Rapier, Three.js and world/garage GLBs. Garage
previews are rendered stills/turntable images; no controller-side 3D turntable is implied.

Host setup probes WASM/worker and an actual supported renderer before advertising a playable room.
Missing WebGPU selects the qualified WebGL2 path; failure of both offers Join/use another host and
an actionable error. This is a capability failure, never a participant-count check. Audio failure
keeps captions; a required baseline asset failure keeps the room in Preparing with Retry/Lobby.
A phone host has distinct Host and optional controller surfaces; do not promise two full-size
touch sticks over a tiny shared world. It can play with a discovered pad or another controller.

**Capability format.** Use opaque cryptographically random secrets, carried over HTTPS or
authenticated WebRTC and stored as verifiers where possible. Every grant includes a unique ID, realm/room, scope, issuer
`HostEpoch`, assignment generation where relevant, expiry/revocation and intended endpoint/source.
The authenticated current host installs the verifier/signalling permission at the service; do not invent
a client-signable grant or rely on unsigned URL fields. Never log grants. Pairing links carry the
secret in the fragment, redeem once through the authenticated protocol, then remove it from history.
Control and recovery redemption use atomic request-ID deduplication and reject expired/wrong-realm
proof. V2-02 fixes wire encodings and checked integer/length handling, including JS-safe ID encoding.

**Paired host-control phone (deferred by R84; was Minimum).** The host opens a separate pairing QR, valid for two minutes,
and confirms the displayed pairing phrase/device. The resulting revocable `host-control` grant
allows pause/resume, settings, force-start, End and Disband through the host reducer. It neither
creates a seat/ballot nor contains a recovery grant. Losing it does not pause play. End and Disband
each show their actual consequence and require confirmation; repeat delivery is idempotent. If the
host is unreachable, administration is disabled with reconnect status, not optimistically applied.
Pairing and permission denial are testable without real game simulation in V2-122.

**Device handoff and emergency host recovery (deferred by R84).** An existing seat approves a one-use handoff from its
current controller, or the active host explicitly authorises its replacement. Without either, offer
a new seat; never recover by matching a name. Handoff increments the assignment generation and
neutralises old inputs before accepting the new source. Resume proof alone reconnects the existing
endpoint/source assignment; changing to a different active source requires confirmation.
Host setup separately offers a downloadable recovery package: versioned checkpoint, build binding
and a distinct recovery secret whose verifier is in the server control record. Warn that possession
grants emergency control; keep it out of public links/reports. Import validates schema/build/realm,
shows the saved cutoff and obtains a fresh epoch by registration CAS before activating restored state.
Two importers cannot both win. Rotate the recovery secret on replacement. Old exports may restore
older state only when their still-valid grant is accepted; revoked grants never revive a room.
After replacement, saved seat proofs are revalidated by the new host and receive new-epoch routes;
seats absent from the checkpoint need a new claim, with the disclosed loss of old progress.

These defaults use bearer capabilities because there are no accounts. They supply concrete proof
and fencing semantics without promising recovery after all copies of state and secrets are lost.

**Recovery transaction and anti-rollback contract (G-RECOVER; deferred by R84):**

1. Ordinary bridge reconnect uses the current host credential and `HostEpoch`; it increments only
   `ConnectionEpoch`/bridge nonce. Same endpoint/source/assignment resume likewise replaces its
   previous socket, including a duplicate tab; notify the losing tab and neutralise old input.
   Changing the endpoint/source is a handoff, requiring consent and a new assignment generation.
2. A replacement claimant generates proposed new host/recovery secrets **before** sending the CAS,
   retains them through retry, and sends their verifiers with request ID and payload digest. CAS
   atomically checks the expected host epoch/recovery verifier, advances HostEpoch, rotates **both**
   host and recovery verifiers, and records the winning request/outcome. Fence all old routes.
   Lost reply/restart retries prove possession of the winning proposed credential and retrieve the
   same outcome; conflicting request content fails. A receipt for an older, subsequently replaced
   or disbanded epoch returns superseded/ended and cannot reactivate it. The old host credential
   can never reconnect as the new epoch. A host receiving `HostFenced` enters a terminal replaced
   state and stops accepting local gameplay/admin input, rather than trying to seize the room back.
3. Use the same proposed-secret pattern for source claims/control pairing: the client keeps its
   secret and the host authorises its verifier. The deduplicated reply needs only identity/grant
   metadata, not recovery of a discarded plaintext secret. Bind request IDs to requester and payload
   digest. Save claim outcomes with checkpoints; a claim newer than the last durable checkpoint
   remains subject to the already-disclosed unsaved recovery limitation.
4. Before acknowledging a handoff or credential revocation, durably advance `CredentialRevision`
   at the registration service with an idempotent request. The host then applies/saves its matching assignment
   revision. This scalar has no player roster or score authority. On **any** checkpoint restore,
   compare its revision with the value returned atomically by replacement CAS, or a serialised
   restore barrier on ordinary reload. If older, remove **all inherited assignment verifiers** from
   restored authoritative state and save seats as unassigned identities awaiting host approval.
   Preserve preferences/standings; do not retain revoked secrets as a shortcut to later resume.
   Only newly approved assignments receive fresh verifiers. Re-saving with the current counter
   cannot make discarded proofs valid again. Do not guess which prior assignments were revoked.
   Current checkpoints can reinstall their still-valid verifiers under the new host epoch. A registration-service
   outage during revocation leaves it visibly pending; never claim durable revocation succeeded.
5. Recovery export/issue/revoke is **local-host-only** in Minimum. A paired control phone cannot
   upgrade itself. Portable recovery proof has room/realm/build scope with endpoint unbound until
   redemption, then the outcome is bound to the winning credentials. Control phones re-pair after
   replacement. Expiry rules differ by scope: pairing/handoff offers expire after two minutes;
   established seat/host/control/recovery grants last until explicit revocation/Disband (preview
   deletion may end their realm). Short connection freshness never expires the underlying seat.
6. Validate import version/build/realm, canonical map/profile availability and replacement renderer
   before CAS. After winning, install only the disclosed imported ledger, void the interrupted
   round and allocate a fresh globally unique RoundId, not a rolled-back counter. Attempt to persist
   the new checkpoint/epoch; if saving fails, expose unsaved state and a fresh recovery download.
   Never undo fencing or restore old credentials because local saving failed. State the checkpoint
   cutoff and **possible** later loss, not an exact count of results the replacement cannot observe.

Combined acceptance: export → commit another round → hand off a seat → import old export → lose
successful CAS reply → restart registration service → retry → attempt old-host/old-seat/old-export redemption.
Expect one authority, one result per restored RoundId, visible cutoff, no silently revived revoked
assignment and no duplicate car. Save/reload the imported state before approving any seat; old
proofs must remain rejected. Race a revocation against CAS/restore to prove the comparison is atomic.
The same test applies stale-checkpoint protection to local reload.

## 4. Controls — two sticks, explicitly taught

### 4.1 Input protocol

Continuous state is replaceable; deliberate actions are not. Send shaped steering/drive/held action
state promptly with sequence/connection/assignment identifiers. Maintain a small acknowledged,
idempotent action stream for discrete actions such as wheelie, camera toggle and recovery request.
Repeats, coalescing or reconnect cannot lose a valid short action or execute it twice. Expired actions
never execute late. On cancellation/visibility loss, neutralise; do not interpret cancellation as a
release stunt. Gameplay cadence is enforced by the weapon/rule, not by packet count.

Define terminal action results (`applied` with tick, `expired`, `rejected` with reason) separately
from receipt. Deduplicate by seat/assignment/action ID across transport reconnect; do not mint a new
action ID when retrying. A short discrete weapon-sector entry is also an action, not just a held
sample. Record its direction and validated preload/intent so a later neutral sample cannot erase
it. Round/life changes, pause and source cancellation explicitly invalidate unexecuted gameplay
actions. Durable UI commands such as Ready/vote have their own revision rules and are not expired
as driving gestures. Bounded action retention must return a visible terminal outcome, never silently
discard an acknowledged action. Tests cover a press and release entirely between two state sends.

`DriveIntent` is source-blind: vehicle-relative steering/throttle/brake, or an explicitly selected
Overview desired-heading preset resolved from authoritative car state. Source type is diagnostic
metadata only. Camera changes must not silently reinterpret a held direction.

### 4.2 Recommended default layout for the first controller playtest

**Two large floating joysticks; no accelerometer, tap-to-fire, flick-to-boost or action-button forest.**
The precise axis mapping is RECOMMENDED and is qualified through the tutorial/playtest, not an
additional owner ruling.

| Stick | Ordinary behaviour | Advanced behaviour, taught later |
|---|---|---|
| Left: DRIVE | X steers; up accelerates; down brakes, then reverses near rest. | A deliberate deep backward pull past the ordinary braking zone visibly preloads suspension; release performs a wheelie when the physical state permits. |
| Right: ACTION | Up uses the weapon/utility forward; down uses it rearward. | Right holds boost; left holds handbrake/drift, if that car/ruleset offers them. |

Axes/regions are shaped independently so diagonal steering does not unintentionally reduce full
throttle. Weapon direction is **car-relative**, not screen-relative. Cards declare directional or
self-use behaviour: a shield/EMP can use either vertical direction with the same displayed meaning.
Forward/back use shares the same item/ammunition; this is not two compulsory weapon slots.

Weapon-sector hysteresis and a neutral re-arm avoid accidental direction switches. Discrete weapons
fire on intentional sector entry; continuous weapons fire while held according to their card. The
same stick is not simultaneously a rear-fire pull and a wheelie release: wheelie belongs to DRIVE.
Its deep-pull preload is visually distinct from normal braking; ordinary full brake must remain
available before the stunt detent. Pointer cancellation, device disconnect and pause never trigger it.
Boost is a visible held direction, not an inertial or accelerometer gesture. No secret boost flick.

Identity, camera, settings/help and manual recovery remain small **secondary** controls outside the
thumb travel areas. Display current weapon direction, preload/re-arm and utility availability next
to the sticks. Portrait has an intentional layout/rotation mapping, safe areas and tested hit regions.
One-thumb accessibility can be a separately tested preset; split-phone multiplayer is not a goal.

### 4.3 Pads, keys and tutorials

Pads/keys express the same gameplay actions with familiar bindings; native stick/trigger ergonomics
need not copy the touch surface literally. Digital steering has rate shaping. Standard presets are
examples, not a cap on sources or simultaneous players. Claim-by-press creates no phantom seats.
Expose actual OS/browser input discovery limitations honestly without turning them into game limits.

**Interactive tutorial (Minimum build):** learn steering/acceleration, brake/reverse, forward/back
weapon use, then optional wheelie/boost/drift. Teach by a brief safe practice/ghosted entry using the
real mapping and physics, with matching phone instructions and TV identity. It is skippable,
repeatable from Help, and never pauses other players or becomes a mandatory slot queue. A late joiner
may start driving immediately with contextual prompts. Do not require gaze-heavy reading mid-race.

Minimum uses contextual prompts on the real host-controlled car plus a harmless front/rear test
utility; it does not wait for the eight Full weapons. A separate practice scene, when used, runs on
the host through the same core and uses a separate score namespace. The controller stays lightweight.
Help and skip remain available during preparation, driving and intermission without holding up a round.

Tutorial acceptance measures accidental actions, eyes-down time, intended front/rear use, brake versus
wheelie mistakes and independent driving without verbal coaching. Final mapping follows playtesting.

### 4.4 Input lifecycle and autopilot

Track transport freshness, physical-source availability and deliberate activity separately, per
channel. A healthy hub does not hide one unplugged pad. Constant held input is not inactivity.
Stale controls neutralise promptly; confirmed disconnection hands to a visible low-skill autopilot
within about 2 s. The longer connected-idle timer only applies to genuinely idle/stuck behaviour.
Returning fresh deliberate input reclaims control; a heartbeat/noisy axis does not. No room pause.

Disconnected seats retain identity/car/score and their visible autopilot treatment. **No automatic
parking during a round.** Leave or “Sit out” is explicit, takes effect at a tick boundary, invalidates
pending gameplay actions and withdraws the car with a visible exit cue. Existing detached debris
remains dynamic. Preserve that seat's round ledger and legal recovery anchor; a return during the
same round restores that anchor with the normal recovery penalty, never last-place inheritance.
After sitting out a whole round, return uses the new-entrant placement policy for the current round.
Leave releases the active source assignment but retains limited same-seat reclaim proof; Sit out
keeps that assignment dormant. Both retain preferences and exclude the
seat from Ready/ballot cohorts and reflow its tile. Standings never lose earned results. A disconnected
seat is parked between rounds only after five minutes without fresh source traffic (wall time), with
the reason shown on return; this is absence handling, not capacity reclamation. Reconnect restores
participation immediately. No slot needs to be made available first.
Wake lock and supported haptics are enhancements, not joining conditions.

Initial freshness profile: coalesce changing axes into a 60 Hz send schedule, dispatch critical
neutral/cancel/unavailable transitions promptly, and refresh unchanged state at 20 Hz (§13.3a).
Changed-state sends satisfy the refresh deadline; do not add a second 20 Hz stream on top.
Neutralise state older than 250 ms at the receiver and enable dropout autopilot after 2 s without a
valid source refresh. Deliberate input beyond the calibrated dead zone, or a button edge, reclaims
control; never replay the stale held state. After 15 s of connected, neutral inactivity, show a
3 s takeover cue, then autopilot; meaningful constant held input resets that idle timer. Gameplay
takeover/handback executes on a tick boundary; during pause only freshness is updated, and neutral
re-arm is required on resume. These are versioned latency/tuning defaults to measure on direct LAN
and Internet/relayed paths, not per-room rate limits. An unplugged source sends unavailable even if
other hub sources live. Input sampling, send cadence and fixed 120 Hz physics are separate clocks.

## 5. Identification

Readability pillar #1, and the top playtest complaint (R22): in a 24-player grid or a busy Overview, "which one am I?" must be answered in under a second. Car *size* is the other half of the complaint; see §6.4.

### 5.1 Identity kit (every car, every surface)

| Element | Screen | Controller |
|---|---|---|
| **Number** (stable increasing display label, not capped at 99) | Huge roof number, number badge on the tile corner, number on the nameplate above the car in other tiles/Overview | Big number in the identity chip |
| **Colour + pattern** (curated palette of 16 colours × distinct pattern: stripes, checks, flames, dots, zigzag…) | Car paint, tile border, trail tint | Chip background + pattern; controller UI accent |
| **Name** | Tile label; Overview nameplate (scaled to stay ≥ 28 px at 4K) | Header |
| **Source icon** | Small icon on the tile badge: 📱 / 🎮 / ⌨ | Shown for hub/pad seats (a pad seat on a phone shows "🎮 #7") |

Colour-blind safety comes from pattern + number, never colour alone. Reuse palette/patterns as needed; a finite palette never limits admission. Tile order in the grid follows
seat order (join order), never race position — you learn where you are on the TV.

### 5.2 Identify button

- Press **Identify** (controller button / pad Select / key) ⇒ for ~1.5 s: the player's tile border and
  number badge pulse and scale up, a comic "#7 THAT'S YOU!" burst appears over their car, their car
  gets a bright outline visible in *other* tiles and in Overview; the controller flashes the same
  number/colour full-screen (and vibrates where supported).
- Auto-fires once on join and on respawn, so newcomers get it without asking.
- Rate-limited (e.g. once per 3 s per player) so it can't be used to obscure others.
- Test: capture scenario `identify-24` asserts the tile pulse belongs only to that seat; the intentional world outline is also visible in other views.

## 6. Screens and cameras

### 6.1 Camera modes

| Mode | For | Behaviour |
|---|---|---|
| **Dynamic Grid** | Races and any mode | One tile per car; the grid resizes as players join/leave; each car chooses first- or third-person. |
| **Shared Overview** | Derby/arena maps | One camera framing the action, no split. |
| **Auto** (default) | — | Arena maps default to Overview; tracks to Grid. |

The host can switch Grid ⇄ Overview **at any time, including mid-round** (R23; ~300 ms animated transition) (arena maps only for Overview; on
track maps it's disabled with an explanation — a course doesn't fit one readable frame).

### 6.2 Dynamic grid layout

Pure function in the render layer: `layout(displayRect, safeArea, cars[], prefs) → tiles[]`.
Evaluate balanced-row layouts as well as rectangular grids; maximise useful gameplay area before
large filler panels. Batch near-simultaneous joins, preserve seat order and never truncate the list.
The test matrix is illustrative: the algorithm accepts any finite N the machine can represent.

- Choose rows × cols with rows·cols ≥ N, minimising unused area, subject to each tile's aspect staying
  in a playable band (target ~1.2–2.0 for third person; first person tolerates a little narrower).
- Works for **any display aspect**: a portrait phone host gets a vertical stack (1×2, 2×2, 2×3…); an
  ultrawide gets more columns. Nothing assumes 16:9.
- Spare cells show a **filler**: QR "join now", mini-map, leaderboard or kill feed. Never black.
- **Resizing is animated** (~300 ms ease) when N changes; existing tiles keep their relative order.
  During a round, tiles never reshuffle because of position changes — only joins/leaves reflow.
- **Disconnects:** the autopilot retains its seat/car/tile during ordinary reconnect. Explicitly parked or departed seats reflow; no eviction is used to make room.

Reference numbers at 3840×2160 (for budgeting, not a fixed table):

| N | Grid | Tile px |
|---|---|---|
| 4 | 2×2 | 1920×1080 |
| 6 | 2×3 | 1280×1080 |
| 9 | 3×3 | 1280×720 |
| 12 | 3×4 | 960×720 |
| 16 | 4×4 | 960×540 |
| 20 | 4×5 | 768×540 |
| 24 | 4×6 | 640×540 |

For N = 2, evaluate horizontal and vertical splits with actual camera framing and gameplay captures.
Do not automatically shrink both players into a four-cell layout merely to satisfy a rigid aspect rule.
Playable area and own-car readability outrank filler panels; aspect bands are soft preferences.

### 6.3 Per-car view: first person or third person

- **Third person (default):** spring-damped chase with speed-scaled look-ahead, collision-aware pull-in,
  FOV/pitch by tile-size class (tune distance/FOV/pitch together to preserve own-car projected size, not automatically wider FOV).
- **First person:** bonnet or cockpit camera from a `cam_fp` node in the car model (contract §12.4),
  with head-bob from suspension (subtle, comfort-limited), speed FOV kick and a visible bonnet/wheel
  edge so you feel the car. Damage is visible (cracked-glass overlay, flapping bonnet).
- Toggle any time from the controller; remembered per seat/device preference, without a human account.
- Both cameras show **threat arrows** at tile edges (incoming missile, car close behind) and the
  off-screen arrow to your car if the camera ever loses it.
- On respawn: cut, not swoop. Heavy hit: trauma shake scaled to tile size.

### 6.4 Shared Overview (arena)

**Cars must be big (R22).** Playtests found cars too small even with lots of empty screen. Fixes, in
priority order:

1. **Arena size scales with the car count.** The derby generator (§11.4) sizes the arena for the
   expected N and the camera never frames empty arena: it frames the *cars' bounding box*, not the
   arena bounds.
2. **Car-size target, not a visibility sacrifice:** tune framing/arena dimensions for large readable
   cars. Every human-controlled car remains visible in Overview; do not crop outliers merely to pass
   a median-size target. A difficult spread produces a non-blocking Grid suggestion, never a refusal.
   Pixel targets are measured per viewing-distance profile, not claimed for arbitrary N/aspect.
3. **Screen-filling framing:** frame to the display's aspect (no letterboxing); HUD in thin edge bands.
4. **Consistent physical scale:** approved derby profiles may differ, but dynamic camera adaptation never changes colliders or vehicle scale mid-round.
5. **Host override:** zoom bias slider and instant switch to Grid (R23).

Acceptance: scenario `derby-overview-24` and `derby-overview-8` assert median car height ≥ target and
unused ground area outside the cars' padded screen-space envelope ≤ 35% of the gameplay frame
(initial framing target); record the metric mask and viewing profile. All-car visibility takes
precedence over these provisional targets, and any failure is reported rather than cropping a car.

- Frames all alive cars plus margin, clamped to arena bounds, fixed pitch (≈ 55–65°), never rotates,
  critically damped zoom. At high N it settles at "whole arena" and stays — stability beats tightness.
- Identity: nameplate + number + colour ring under each car, scaled by camera distance.
- No live killcam/PIP/interstitial. Wrecks are recorded for the end-of-round reel (§10.3).

### 6.5 Drop-in flow

1. Scan QR → lightweight room preview with prefilled optional name/car → **Join the race**.
   Opening the URL alone never claims a seat. Submit one idempotent claim; host acknowledgement
   assigns the number/identity and enters the running round immediately. Show “Joining…” until
   acknowledged, then “You're #12” plus Identify. A valid existing proof resumes its seat instead
   of showing a new-player form. If the round ends during entry, go to intermission with the same
   identity; never promise a spawn in an already-finalised round. The optional pre-join control
   guide is a local diagram/input pad; it creates no seat and loads no world renderer.
2. Host reserves a tile immediately (grid reflows) showing "#12 GET READY" with the identity kit.
3. Car spawns **behind the last still-racing entrant by the join gap** (race) or at a safe edge pose
   (derby), with about 1.5 s spawn protection and the Identify pulse. Protection disables car/debris
   contacts and damage/pickup exploitation; terrain, road and barrier collision remain active.
4. Scoring: race: they're classified from where they actually finish; derby: see the late-join
   fairness rules in §10.9. Next round they're a normal starter (R5).
5. **No slot limit, ever (R36).** There's no queue and no "room full". The grid just grows (§6.2); on a
   weak host may have smaller tiles or lower presentation fidelity; Overview is available for arenas, not a universal race fallback. No count-derived admission limit, hidden array limit or temporary MVP cap is permitted. Technical faults are faults to fix, not permission to introduce a participant quota.

Use one placement service for initial entry, respawn and recovery, with explicit policies for legal
race progress. Commit simultaneous placements serially at tick boundaries, using current occupancy,
car footprint and moving debris, not just an exported list of points. Never enable contacts in an
overlapping pose when protection expires. If the ordinary pose search fails, the entrant still gets
an immediately controllable protected car and a visible safe-entry state; it earns no score or race
progress during that exceptional state. Reposition at the same legal entry progress to complete
insertion, with clear cues and no impulse launch. This is not a hidden waiting slot. Crowded-space
qualification must demonstrate prompt full participation; indefinite protection is a failed design
case to resolve (§19.3), not a claim that finite arenas have unlimited disjoint space.

### 6.6 Any host, any aspect, future extra displays

- Everything on screen is laid out from the display rect: HUD, grid, fillers, overlays. UI scale uses
  viewing-distance profiles (TV / desk / handheld), with a sensible default and host override; browser pixels are not a reliable physical-size/distance measurement.
- **Phone host:** landscape preferred; portrait works with the vertical grid; small N or Overview by
  default. Fullscreen + wake lock requested from a user gesture; iOS gets the Add-to-Home-Screen hint.
- **One screen first (R78):** Minimum/Full have one display. Prioritise readable Grid/Overview,
  responsive controls, clear identity, smooth joining and good driving/round flow on a big screen.
  Keep seat/display identity separate from within-screen layout, using only the boundaries this
  single-screen implementation actually needs.
- **Additional screens require G-SCREENS.** This is a high-effort project with low near-term reward:
  world replication or duplicate physics, baselines/deltas, loss/rejoin, per-screen assets, layout
  redistribution and mixed-device performance all need design and qualification. WebRTC connecting
  two browsers does not implement those systems. Do not build or benchmark them speculatively.
  Arena/mode/theme work and single-screen playtest improvements proceed independently. Their
  completion, or reaching Full/Stretch, never substitutes for explicit owner approval of this project.
- **Hardware target (R47):** GPU-capable phones and laptops, typically a laptop driving a TV. Weak
  hosts adapt presentation and expose genuine overload as specified in §7.1; no player limit.
  A manual fidelity settings menu is **deferred**; automatic adaptation is qualified in G-PERF.

### 6.6a Add another screen — owner-gated future design reference

**G-SCREENS is closed until the owner explicitly approves a named scope.** Everything in this
section is retained design/research material for that future decision, including the codec
comparison in §13.5. It is not a Minimum/Full deliverable or an automatically scheduled post-playtest
task. Approval for a bounded spike does not approve the full implementation. Once approved, select
one measured replication approach; supporting multiple compatibility modes is not a default promise.

**There is no fixed players-per-screen answer.** A screen's useful tile area depends on aspect,
viewing distance and framing; 4K alone does not mean it should take four times the players of a 1080p
TV. Each display reports its CSS/output size, safe area and measured rendering performance and has
an explicit TV/desk/handheld viewing profile. Suggested layouts are tested for readability, never
used as a capacity/admission test. The host can see and change the proposed distribution.

Start similar TVs with equal layout weight regardless of 1080p/4K resolution; use aspect ratio and
profile-scaled projected car/text sizes to score candidate partitions, favouring the smallest readable
tile before total area. A small handheld display normally takes a smaller share. Show actual proposed
counts (“6 here, 2 on Screen 2”), with player/group moves, rather than asking the host to configure
maximum capacities. Those counts describe an assignment and automatically accommodate later joins.

1. The new device uses the **same room QR/link/code**, chooses **Join as another screen**, opens the
   pinned build/realm and receives a display-scoped grant plus a stable label (“Screen 2”). No host
   confirmation or new lock-screen controls are required. It selects its viewing profile; it is not
   a player or ballot and cannot send host administration or simulation changes.
2. The display loads the required self-hosted assets and a full presentation baseline before declaring
   Ready. Existing views continue meanwhile. On readiness, the host automatically commits a sensible
   proportional assignment and gives moved players a brief “You're on Screen 2” cue on their
   controller and both screens. Optional manual proportion/player edits show current and proposed
   assignments, labelled “Layout preview — not applied yet”.
   **Apply this layout** submits its base assignment revision and ready-display set; only an accepted
   host revision moves tiles. **Cancel changes** keeps the current assignment. A join/loss while
   editing invalidates the draft; rebase visibly and require Apply again, never overwrite newer state.
3. In Grid, the host-owned assignment function partitions fielded seats among ready displays,
   balancing projected usable tile space in viewing-profile units, then applies §6.2 on each display.
   Preserve seat order and prefer minimal moves; do not redistribute on race position or transient
   frame-rate changes. Automatic assignment handles new seats; established assignments change only
   for display join/loss, explicit moves or a sustained host-approved rebalance.
4. Players may request a preferred screen from their controller; the host can move a player/group
   or restore automatic placement. Preferences guide placement without creating a waiting list.
   Every fielded seat has one primary driving tile in Grid. Optional mirrored Overview for an arena
   is a shared companion view, not a second controller assignment. Screen number accompanies
   identity/Identify, so players can find both the right screen and their car.
5. On display disconnect, return its seats to the host/remaining ready displays and reflow. Their
   car, input, score and camera preference do not change; gameplay never waits for a viewer. A
   returning screen must become Ready again before seats move back. Losing the simulation host
   still follows §3.4; an extra screen does not silently become a replacement host.

Readiness is scoped to `RoundId`/required-asset manifest/baseline revision, not a permanent property
of the socket. Prepare viewers for the next round alongside the host. At round commit, any viewer
missing required assets or a consistent new baseline loses its assignment temporarily to the host
or ready displays; show the move and continue the round. It may regain seats only after readiness
and a fresh assignment revision. Optional higher-detail downloads do not withhold readiness.

`DisplayAssignment { revision, displayId -> SeatId[] }` is session state. Camera/LOD/interpolation
are display-local presentation, and controller steering remains vehicle-relative across moves.
The current display baseline uses host-authored snapshots and entity/damage lifecycle. Compare its
optimised delta path with exact simulation replicas under §13.5, only after G-SCREENS approval,
before settling the wire protocol; a replica remains a non-authoritative consumer, never an
automatically elected host.
A future display distributor, if selected after G-SCREENS approval, forwards a display-scoped
stream without simulation authority; the initial Rust discovery service does not implement it. Join/gap recovery needs
a consistent baseline plus subsequent revisions; a slow viewer coalesces state or resynchronises
without backpressuring the host tick. Local buffers alone (§13.4) do not implement this network path.

**Snapshot delta candidate (qualification, not a measured bandwidth promise).**

- Send a versioned render baseline, then tick-stamped binary changes. Quantise presentation values
  with measured visual error, use compact orientations and small relative deltas with absolute-value
  escape encodings. Quantisation never changes authoritative Rapier state or clips gameplay ranges.
  Choose sparse changed-entity IDs versus change masks by actual encoded size. Assets travel through
  the pinned bundle, not repeated transform packets.
- Encode against a baseline that this receiver has acknowledged **decoding and retaining**, not
  simply the previous packet sent. Identify room/host epoch, round, entity generation and baseline;
  retain a bounded history by bytes/time and explicitly rebaseline when it expires. A lost delta
  must not make every later packet undecodable. With partial snapshot chunks, acknowledge the
  reconstructed scope exactly; never treat a partly received world as a complete baseline. See
  [snapshot compression](https://gafferongames.com/post/snapshot_compression/).
- Separate durable lifecycle/assignment changes and chunked baselines from supersedable transforms.
  Gate transforms on their lifecycle revision; a newer packet cannot revive a removed incarnation.
  For WebRTC, evaluate reliable delivery for lifecycle/baselines and unordered, zero-retransmit
  delivery for disposable state. Pace transfers and coalesce unsent stale state: channels share
  congestion capacity, so a second channel alone does not protect controls from a large checkpoint.
  See [WebRTC data-channel transport](https://www.rfc-editor.org/rfc/rfc8831.html).
- Reuse acknowledged sleeping transforms until wake/change. Scope rendering data to the union of
  assigned cameras with a tested entry margin; Overview may need the whole world. No count truncation
  or deletion of live bodies. Relevant hazards must remain visible. Network/render cadence is
  independent of the fixed 120 Hz simulation. Render from tick-stamped samples with a measured
  jitter buffer; reset interpolation across respawn/teleport. Compare 30/60 Hz publication and visual
  input age, rather than accepting a low-bandwidth stream with poor driving response. The established
  distinction between persistent replicated state and one-shot events is illustrated by
  [Unity's snapshot documentation](https://docs.unity3d.com/Packages/com.unity.netcode@1.4/manual/ghost-snapshots.html).

Measure simple packing/deltas first. Prediction-residual or entropy compression is a subsequent
candidate only if the saved wire bytes justify encoder/decoder CPU and buffering. RaptorQ/FEC is
loss repair rather than compression; evaluate it separately, principally for bulk checkpoint loss.

After G-SCREENS approval, qualification covers mixed-size TV/phone screens, concentrated preferences,
sparse/crowded layouts, long names, Identify during a move, asset failure, latency/gaps, screen loss/rejoin and
host backgrounding. Measure host serialisation/uplink and each viewer's render cost independently.
Comfortable distribution and move-animation tuning remain playtest questions; no preset becomes
a players-per-screen maximum.

### 6.7 Concrete renderer recommendation (G-PERF)

Use current-stable **Three.js WebGPURenderer + TSL/node materials**, WebGPU preferred and its
WebGL2 backend qualified explicitly. This is a new renderer pipeline, not preservation of old GLSL
patches. Keep gameplay CPU-side in the Rust/WASM sim; GPU rendering is a separate concern.

1. Update scene transforms once from the published snapshot pair. Render each seat's camera into
   its viewport/scissor in a shared output target; cull and select LOD per view. Never omit a player
   because N exceeds a test value. Reusable instancing/batching grows to the actual scene.
2. Start with toon-ramped semantic materials, silhouette ink, graphic lighting and emissive masks.
   Add depth/normal/object-ID detail only where its measured visual value warrants the attachments.
   The goal is excellent comic rendering, not a deferred-renderer research project.
3. Shadow work is scheduled once per relevant light/coverage update, not accidentally once per
   camera. A compact arena may share one fitted coverage region; a long course may need separately
   fitted regions/cascades or simpler distant shadows. Do not claim one tiny shadow map fits all maps.
4. A **tile-aware** post pipeline composites the frame. All sampling passes—including every bloom
   downsample/upsample level—respect tile IDs/bounds or padded tile regions. Border drawing alone
   does not isolate kernels. Depth reconstruction uses each tile's camera parameters.
5. Vignette, speed lines, impact distortion and similar view effects use tile-local coordinates;
   shared colour grade is truly output-wide. Paint HUD/text/identity/QR at output resolution after
   resolution-scaled world/post work. No chromatic/impact effect obscures identity or the road.
6. Use automatic render-scale/effect-detail/LOD adjustment with hysteresis when GPU-bound; profile
   CPU submission and shader compilation independently. Reduced visual detail cannot alter contact
   geometry, authoritative hazards, vehicle bodies or number of playing seats. Sleeping debris
   reduces solver work without becoming static; visual instancing does not merge physics bodies.

Asset detail is selected by projected screen size **per view**, then adjusted to measured host
render cost (§12.4); do not classify assets solely by “phone” or “PC”. The same car can need a close
LOD in its owner's tile and a simple LOD in a distant rival's tile. Select for each pass without
leaking one camera's choice into another. Share geometry/textures, not mutable per-view LOD state.
Batch capacity is growable allocation, not an entity limit; qualify identity, per-part deformation
and detach with the selected batching path instead of assuming `BatchedMesh` handles them. [S14]

Prewarm the next round's materials/shaders and release old GPU resources explicitly. Gate captures
exercise dynamic joins, mixed camera views, missing/lost GPU contexts and forced WebGL2 fallback.
Record CPU sim/submission time, GPU time, all-view draw calls, frame p50/p95, memory and thermal soak.
Test increasing and irregular N on the Mac/TCL plus a phone; test numbers are never gameplay caps.
On device/context loss, compose a `renderer-unavailable` pause while recreating presentation resources
from the current authoritative world. Resume only after a visible frame is ready; do not reload the
host or reset scores to change renderer backend. WebGL2 fallback must render the same supported
material/asset contract; inability to restore is an explicit fault with recovery controls.

## 7. Vehicle physics — suspension, fun and robustness

### 7.1 Timing, pause and physical ownership

**120 game-time steps per second, `dt = 1/120 s`; normal game-time scale = 1.0.** Render frames use
actual elapsed monotonic time with interpolation between completed snapshots. Cameras/UI use
proper delta-time damping (for example `1 - exp(-rate * frameDt)`), not per-frame constants. A
30/60/144/240 Hz display changes the number of physics steps between frames, not the physical laws.
Soccer's source-specific 0.85 scale is not imported into this car game. [S1–S4]

There is one simulation-time owner. The worker accrues active elapsed time and consumes it in
complete fixed steps; the main thread requests presentation independently. Timers for respawn,
weapons, races and chaos advance with game ticks. Socket freshness uses monotonic wall time.
Intermission/UI deadlines are separately defined and do not accidentally consume hidden-tab time.

**Named pause reasons:** `manual`, `host-hidden`, `host-suspended`, `renderer-unavailable`,
`performance-stall`, `fault`.
Reasons compose: returning to visibility removes only the visibility reason, never a manual pause.
The browser lifecycle adapter and a foreground-presentation heartbeat stop the sim if the display
is hidden/frozen. Release local and remote held states, retain the exact world, and resume through
a brief visible countdown after rebaselining clocks and input. No hidden interval is accumulated
or replayed. A process kill is recovery, not ordinary backgrounding. [S2]

**Degradation:** drop optional visual cost/render cadence first. Normal low render FPS is not a
physics failure if the worker still keeps pace. Schedule catch-up in yielding time slices; do not
hard-code a player-dependent limit or an eight-steps-per-render-frame rule. Do not enlarge dt,
silently halve physics rate, skip competitive ticks, delete debris or suppress joins. If simulation
lag becomes persistently unplayable, enter the explicit performance pause at the last completed
tick and rebaseline on resume. A delta-time formula cannot manufacture missing compute capacity.
The same room/host is preserved; host replacement remains break-glass. Test the pause threshold
as a responsiveness parameter, not a content/admission cap. [S1]

**Rapier integration:** direct `rapier3d` inside `jj-sim`, initially its raycast vehicle controller.
Document each API's units, force accumulation/reset ownership and phase order against the pinned
version. Integrate sustained forces with dt exactly once; apply one-shot impulses once, without
another dt multiplier. Braking impulse and engine force are not interchangeable units. Simulate
actual suspension compression/rebound; the renderer follows it rather than adding duplicate full
chassis motion. Use appropriate contact filters, collision proxies and CCD. If raycasts cannot
meet a required curb/debris/jump affordance, change the controller implementation with evidence;
the old "never change suspension" implementation ban is not authoritative. [S3–S5]

For the inspected Rust 0.36.0 controller, `update_vehicle(dt, QueryPipelineMut)` updates velocities;
wheel `engine_force` is a force while `brake` is a maximum impulse. Its suspension and engine paths
already multiply by dt. Build one tick-phase fixture: consume commands → set controls/query filters →
update vehicles against current query data → step Rapier → derive damage/progress → commit ordered
facts. Refresh queries after world/shape changes according to the pinned API. JS wrapper signatures
and older numerical recipes are not the Rust integration contract. [S5]

There is no generic low speed/energy clamp to erase legitimate jumps or pile-up launches. Diagnose
non-finite state, deep penetration or solver-created energy; preserve physically caused spectacular
motion. Vehicle power/drag, weapon strength and recovery rules are versioned gameplay tuning, not
count-based resource controls. Fault recovery is visible and records its cause.

### 7.2 What "more fun to drive" means (targets for the feel reference)

| Feel | Mechanism |
|---|---|
| **Visible, bouncy suspension** | Longer travel, softer springs with strong damping; body roll in corners, squat on launch, dive on braking; wheel placement and body pose from actual suspension; any extra squash is presentation-only. Landing a jump compresses, rebounds once, settles. |
| **Drifting that's controllable** | Rear friction-slip reduction on handbrake with a smooth recovery curve; counter-steer works; drift builds boost. |
| **Airtime that's satisfying** | Mild in-air pitch/roll control (small torque from steer/throttle while airborne) so you can level a landing — skill, not auto-leveling. |
| **Weight you can feel** | Archetypes (light/medium/heavy + oddballs) with different mass, grip, suspension and knockback resistance. |
| **Surfaces matter** | Per-surface grip/rolling resistance/particles/sound (§11.3): tarmac, dirt, sand, mud, grass, gravel and wet variants; hail is a temporary event. |
| **Derby punch** | Ramming transfers momentum convincingly; front bumpers are stronger than doors (§8); T-bones matter. |
| **Wheelies and stunts** | The intentional wheelie input (existing 196.x work) kept, measured and rewarded in Stunt Arena. |

### 7.3 Robustness catalogue (each = scenario + invariant)

| Failure class | Fix direction | Scenario / invariant |
|---|---|---|
| Escaping the bowl / OOB | Lips, CCD, OOB reset | `bowl-rim-ram`: 200 seeded rams → 0 escapes |
| Flipped and stuck | Rounded cabin collider so cars roll back; gentle, visible self-right torque only when inverted and slow; respawn button after 2 s | `flip-recover`: from 12 inverted poses, ≥ 90 % upright within 3 s without input |
| Tunnelling at boost speed | CCD on chassis and fast debris; min wall thickness in the map validator | `boost-into-wall` over speed × angle |
| Pile-up instability | Contact geometry, joint/mass validation and solver convergence; no blanket 3:1 ratio or arbitrary low speed clamp | Increasing-N piles distinguish legitimate transferred energy from numerical growth |
| Suspension pogo / jitter | Pinned controller damping semantics and measured compression/rebound settle | `idle-settle`: no-input car rests within the approved envelope |
| Debris traps | Plausible part geometry/mass, sleeping dynamic bodies and visible recovery | Ordinary piles are driveable; pathological traps have the normal recovery action, never count-based deletion |
| Weapon control loss | Tune card impulse/torque and recovery against playable outcomes; preserve valid spectacular launches | §9 |
| Non-determinism | Seeded RNG, stable iteration order, no wall clock in sim | `replay-identity`: same inputs + seed ⇒ same trace hash (same build) |

### 7.4 Controllability metrics and invariants

Per scenario and archetype: 0–60 % top-speed time, top speed, stop distance, turn radius vs speed,
slalom success, drift entry/exit angle and speed retained, wall deflection, jump airtime and landing
stability, suspension settle time, wheelie envelope, recovery time after a hit, knockback per weapon,
"authority" (heading change from full steer in 0.5 s at 5/15/30 m/s), surface deltas.

Invariants: inputs matter in every grounded state; idle cars go quiet; no dominant mash (boost-forever
isn't the best line); ordinary stuck states have a fast visible recovery, without pretending arbitrary physical traps self-resolve; mirrored scenarios mirror;
archetypes occupy distinct regions on the balance chart. Numbers are tolerance envelopes around the
owner-accepted feel reference, plus owner judgement. No single "fun score".

### 7.4a Desired affordances are the new physics truth

The scenario bank specifies what players can cause—not how closely the new code matches the old
Jammers trace. Save full state + applied inputs + rule/profile/map versions for: progressive braking,
reverse without accidental stunt, slalom/counter-steer, controllable drift entry/exit, suspension
compression and single-settle landing, deliberate wheelie and failed attempt, ramp launch with air
correction, curb/debris traversal, front/side/rear impacts, wheel loss, double-car collisions and
legitimate pile-up throws. Preserve failed tricks as well as successful ones.

Vary only timing, input magnitude or contact pose to demonstrate agency. Compare intentional driving
with mash/hold/no-input baselines. Use solver-stress/geometry ablations to expose numerical tricks.
Run identical tick inputs under 30/60/90/120/144/240 Hz presentation and induced hitches; compare
same-target hashes and cross-target envelopes separately. Cameras/render FPS never retune the car.
Owner playtests judge whether the next action is readable and practice helps. Optimisers propose
profiles within these affordance envelopes; they do not optimise one aggregate "fun score".

## 8. Destruction

### 8.1 Car anatomy

> **Interim (R82, amended by R86):** until the owner revisits damage, cars ship the simplified set `core`, `front`,
> `back`, `door_FL/FR/RL/RR`, `wheel_FL/FR/RL/RR`, each intact → **loose** (hanging/wobbling on its hinge, still
> attached) → detached (a dynamic body left on the track). No denting. Contract: Playtest-1 plan §6.3.
> The anatomy below and §8.2's localized accumulation are the later target, not Minimum requirements.

Every car model is authored as parts (contract §12.4):

```text
chassis (core, never detaches)
├── body_front / body_rear (bumpers)      detachable
├── bonnet, boot                          detachable (hinged first, then detach)
├── door_L, door_R                        detachable (hinged first, then detach)
├── wheel_FL/FR/RL/RR                     detachable (loss = handling change, not instant death)
├── glass (windscreen/windows)            shatter → particle + decal only
├── spoiler / roof rack / scoops          detachable (archetype flair)
└── lights (head/brake)                   break → emissive off
```

Each part has: hit points, the collider it contributes while attached, its debris collider/mass when
detached, attachment type (fixed → hinged → detached), and which zone of the chassis it protects.

### 8.2 Part deformation, damage and scoring

Several independently damaged parts visibly deform: bonnet, doors, front/rear body panels, bumpers
and selected chassis zones. Damage is not merely swapping a pristine car for a different complete
mesh. Author localized crush/bend morphs or a coarse deformation cage per part; accumulate local
impact position/direction/severity so two hits need not produce the same generic dent. Wheels and
hardpoints expose handling-relevant damage separately. Each archetype declares available parts.

Use stable coarse collision proxies tied to documented damage stages; do not remesh a detailed
render mesh's collider every frame. Update a collider only at a safe simulation boundary when the
physical consequence warrants it. Detaching preserves the part's deformed appearance and velocity
(including angular contribution at its attachment point); restore total mass accounting deliberately.
Moving/hanging parts must not inject energy through newly penetrating joints. Full soft-body vehicle
physics is not a prerequisite; it is an alternative only if the affordance/performance evidence wins.

Construct collision episodes from contact data with explicit units: closing speed, impulse,
location/normal and accepted damage. Do not multiply an already-derived impulse by mass and speed
again without a calibrated reason. Exclude resting suspension/support forces, aggregate multiple
contacts belonging to one impact, and emit one committed `DamageApplied` event for integrity removed.
Events include event/round/life/part IDs, source and credited instigator. A wreck or detach bonus is
awarded once; damage, score, audio, awards and replay read the same event. Debris paint ownership is
not automatically blame for whoever later pushed that debris. Weapons use this same damage path.
Capture control mode/team/assist attribution when the causal action occurs; returning from autopilot
or changing a team cannot retroactively change credit. Define a short, game-time attribution window
for secondary debris impacts, then treat unattributed damage as environmental. Derby autopilot credit
is 50% (§18 V2-105), applied once to credited points, never to physical damage or by current connection
status. Quantisation/rounding and chain bonuses are ruleset data with event fixtures.

Handling consequences stay readable and playable: missing wheel limp, unprotected zone, smoke and
physical drivetrain impairment. At chassis zero, wreck, retain the debris and respawn after roughly
2 s: at the racer's own legal recovery anchor or a clear derby edge. Preserve earned score/progress.
New-entrant last-place placement is a different operation (§10.9). Spawn protection prevents both
incoming damage and offensive/pickup exploitation; transition out only in a non-overlapping pose.
There is **no live replay**. Optional mayhem remains a simple telegraphed action during the wait;
it cannot delay respawn, steal live view or reward deliberate self-wreck farming.

### 8.3 Persistent, dynamic debris — no count quota

Detached parts and physical environmental fragments remain **dynamic rigid bodies for the whole
round**. Sleeping is allowed: sleeping bodies retain their dynamic type and wake when disturbed.
Do not convert them to static/kinematic scenery, delete the oldest, stop generating fragments above
N, or introduce a "temporary" dynamic-body budget. Replay storage policy cannot touch live debris.

Optimise unchanged behaviour first: physics sleeping, broad-phase locality, well-authored collision
proxies, reusable storage, draw batching/instancing, visible LOD and change-only replay records.
Do not aggregate live physical piles as an assumed default; major pile-up mitigation is deferred
until a measured memory/problem case and a new owner decision. Mesh batching is not physical merging.
Parts retain colour/pattern and deformed shape. The field keeps its history through the round.

Ordinary piles should be escapable by throttle/steer. No guarantee is made for every possible
geometric trap; the normal visible recovery action is the escape hatch, not invisible deletion.
The no-cap policy is normative in AGENTS.md, `docs/policies/owner-direction-2026-09-29.md` and tests.

### 8.4 Environmental destruction

- Destructible props per theme (§11): fences, signs, bins, eskies, surfboard racks, water tanks,
  road cones, wooden posts, bus shelters, stacks of tyres, market stalls, and the **wheelie bin** (green body, **red lid**; on impact the lid
  flaps open and it sprays rubbish debris: crushed cans, pizza boxes, banana peels and **nappies**. The
  nappies are light, squashy debris that stick to windscreens for a second. Comic, not gross-out:
  cartoon-styled, no realistic textures).
- Each is a contract asset with pre-fractured pieces (authored or Voronoi-fractured in Blender by
  script), break threshold, piece masses and a "damage to car" factor — **heavy things damage cars
  realistically** (a water tank or concrete barrier hurts; a cardboard sign doesn't).
- Pieces become dynamic debris under the same persistence/no-cap rules.
- Some props are **hazards by design** (rolling barrels, falling signs) — CANDIDATE per theme.

### 9.2 Card schema

The example below illustrates effect fields, not a complete contract. V2-70 defines validated
`activation` (sector-entry/held), `direction` (forward/rear/self), ammo/energy, cooldown, arming,
expiry, pickup compatibility, source/team credit and cleanup rules for all eight cards. Reject a
card without these fields or without counterplay. All cars have **one usable item slot in Full**;
mount size changes appearance/approved tuning, not an unimplemented slot-selection control.
Additional simultaneous slots require a later explicit control design.

**Pickup look (R94, owner 2026-10-03):** every pickup is the same cardboard delivery package/box with
the contained weapon's image printed on its sides, so players read which weapon is inside while all
pickups stay one recognisable family. Generate reference sheets for the eight weapons and the box
through the art pipeline before modelling them (code-built per R81's method).

Pickups are map-defined replenishing stations with deterministic card draws from the approved pool,
independent of race position. Entering a live station with an empty slot consumes it; a held item is
never silently replaced. Station recharge starts at 5 s game time and is visible. Spawn-protected
cars cannot collect/use offensive items. Ammo/cooldown and effects reset by the card's life policy;
respawn clears held items, giving no free pickup. Fired ordnance retains its causal identity through
the shooter's respawn and expires naturally or at round end. Round-end cleanup removes effects in
the retired world, never live debris during a round.

The horizontal ACTION boost uses a rechargeable vehicle meter; the **Nitro Boost item** is an
explicit one-shot refill of that same meter on vertical activation. It cannot stack another hidden
multiplier. Shield/EMP are self-use in either vertical direction; mine/oil deploy ahead or behind;
missile/rail/flame aim along the chosen car-relative direction. A failed use keeps the item and
reports empty/cooldown/blocked as appropriate. No valid target for a homing missile means it flies
straight along that direction. These defaults remove ambiguity while card strengths remain tuning.

{

### 10.4 Interesting clips within a memory-sensitive replay store

Use a short rolling state history and event-triggered retained clips with pre/post-roll. Store binary,
quantised transforms for moving bodies, keyframes and explicit spawn/damage/deform/detach/despawn
state. Sleeping bodies can store one pose until they move again. Map/version references reconstruct
unchanged scenery. Record important actor trajectories rather than re-simulating an approximate
world and inventing a different kill. Cosmetic particles/dust may be regenerated deterministically.
The playback world is separate from the authoritative live/next-round world.

Every retained clip owns a self-contained baseline at its start, including already-detached parts,
sleeping debris, active effects and accumulated deformation needed to explain the event. Clip
references keep assets/map data alive until playback finishes; evicting the rolling history must not
orphan a clip. Temporal downsampling keeps event boundaries and causally important transforms. If
recording loses an interval, mark that interval unusable and choose another clip; results/awards and
next-round progression still work. Replay capture/compression may degrade within its own budget,
but it cannot block simulation or consume the authoritative event stream before scoring reads it.

Select clips online by marginal value per byte: event intensity, visible causality, rarity, stakes,
multiple involved players, underrepresented identities and diversity from already-retained clips.
Merge overlapping clips; reserve coverage opportunities without promising unlimited distinct footage
inside a finite intermission. Compact records and simplify **replay-only** detail before dropping an
interesting event; never cap live players or debris to make replays cheaper.

Replay capacity is explicitly permitted by R67. Track owned buffers and measured host performance;
use available coarse memory hints cautiously, since browser APIs do not expose universal exact free
RAM. Storage quota estimates are disk/origin storage, not free memory. Start with bounded in-memory
clips. OPFS/IndexedDB spill is an optional measured optimisation using a separate storage job; it
never blocks simulation, has quota/error handling and an in-memory fallback. Do not build a paging
engine before the clip-selection/compression approach is tested. [S6–S8]

The reel plays by default during intermission, skippable by host or the defined controller vote.
Its timing remains the intermission policy, not a delay inserted into each two-second respawn.
Compression/deformation fidelity and event causality get automated fixtures plus owner review.

- Under the armed ready-based start policy, the round starts when **all active controller seats are ready** (3-2-1 countdown, cancelled if
  someone un-readies).
- Returning to Lobby via End, finite EventEnd → Lobby, or an empty-party settle disarms automatic
  start and clears Ready. Say “Waiting for the host — no automatic start”. The host explicitly
  starts with current choices or arms “Start when everyone is ready” for the next event; old Ready
  messages cannot restart it. Initial room setup may select/arm the ready-based policy. Ready is
  scoped to the current start/intermission revision, not a persistent player preference.
- **Host force-start:** host presses **Start now**. If anyone isn't ready:
  1. A **10 s "Starting soon" warning** begins (host-configurable 5–15 s). Not-ready players' controllers
     flash an orange full-screen banner "Host is starting in 10 — tap READY or use your current car",
     with a **vibration pattern** via feature-detected vibration/gamepad haptics where available;
     visual cues always work and sound follows audio permission. Their card on the
     host screen pulses.
  2. At zero: not-ready players get **their current selection** (or the default available car if none) and drop
     straight into the round. Nobody is ever left behind.
  3. Host can press **Start now** again to skip the countdown.
- **Mid-round drop-ins** (§6.5) skip mandatory garage/Ready steps: the prefilled join form supplies
  the default name + the current/last-used or clearly labelled automatic car,
  and can change car at their next respawn from the controller's garage button.
- **Between rounds:** players can change car/name while the results play; the next round follows the preset policy in §10.8. Party Mix uses its visible timer;
  ready-based tournament starts use the shorter default warning (5 s).

UX acceptance: from QR scan, a newcomer can name, pick a car and ready up in ≤ 30 s; a host with 12
players waiting on one can force-start and that player gets the warning on their phone within 150 ms.

### 10.6a UX action, preference and acknowledgement contract (r10)

The [eight-screen study](ux-study-2026-09-29/README.md) contains five host and three phone concepts,
two blind first-look rounds with six fresh low-context Luna reviewers, and retained failure evidence.
Its [flow contract](ux-study-2026-09-29/flows.md) specifies adjacent states, error copy and acceptance
fixtures. Images explore visual direction; they are not production assets, real game captures,
human usability evidence or owner approval. This plan and the owner policy win over image mistakes.

**Personal controller settings (Minimum).** Floating/fixed stick placement, steering-response shaping,
vibration and reduced motion are persistent device preferences, not room rules. Keep two sticks and
the §4.2 action vocabulary in both layouts. Default floating; response maps the full normalised
input range monotonically without changing force, speed, brake authority or stunt thresholds.
Expose source-appropriate pad/key presets on those sources; do not silently reuse a pad calibration
on a different discovered source. Camera preference targets only that seat's host-rendered tile;
phone reduced motion targets its own HUD. L-plates and other gameplay assists remain separate,
visible host-permitted settings with §10.8's next-life/round effect, not a “gentle controls” shortcut.

Use a versioned `ControllerPreferences` record per browser origin, production/preview namespace and
local source profile. Persist layout, approved response preset, source bindings/calibration,
haptic/motion preference and preferred camera; no seat grants, votes, Ready or scores in this record.
“Remember on this device” defaults on and explicitly means across rooms until Reset or browser data
clear. With it off, apply only in memory for this page session and remove any saved record for that
profile so old preferences cannot reappear next visit. **Reset controls** restores defaults for this
profile after confirmation; it never clears identity or room membership. Storage failure applies the
settings for this session and says “Applied for now — this browser couldn't remember your settings”.
Version migration validates known fields; unknown/invalid values use visible defaults. No account
sync, device fingerprinting or server preference dependency. Missing haptics disables that toggle
with a reason, never the controller. Explain these details in a small “How saving works” expander.

Opening personal Settings/Help sends neutral/cancel and a sequenced personal-menu intent. The host
activates that car's weak autopilot; until acknowledged show “Opening controls…” (or Reconnecting),
not a false “Autopilot is driving”. Everyone else keeps racing. Draft edits and **Test these controls**
operate on a local input pad with no game actions. **Save and return to driving** validates/applies
the profile and saves according to the checkbox; **Cancel** or browser Back discards edits. Both
close the menu, require all controls neutral, and reclaim only on subsequent deliberate input.
Releases caused by cancel, navigation or layout change never fire, boost or wheelie. During a room
pause, show the host's pause reason; closing a personal menu cannot remove it. Lost transport uses
the ordinary freshness/reconnect rules, with the same identity and no speculative claims of saving
host state. Preference drafts may remain local while disconnected.

**Settings scopes.** “Only this screen” is immediate presentation state; “Your controls” affects
that source; “Your camera” affects its seat tile; “Next round — everyone” stages room rules via
host acknowledgement. Show a pending/accepted revision and effective boundary beside staged edits.
An accepted room-rule edit is retained when the settings drawer closes; it is not a local draft
requiring an undisclosed Save. Reject stale or unauthorised edits visibly. Paused settings use the
composed pause reasons, so Resume removes manual pause only and explains any remaining blocker.
Opening the separate Screens manager does not itself pause the round.

**Room actions.** **Return everyone to lobby** is `EndEvent`, with a confirmation stating whether
the unfinished round will be void; already committed results remain. **Close room** is `Disband`,
with a distinct confirmation saying controllers disconnect and the join link stops working.
Neither is a regular player's exit button. **Sit out** parks only that seat and preserves room/
standings; **Leave room** affects only that player, retains the return proof and standings under
§4.4, and returns to entry. Both require personal confirmation while driving and never create a
free repaired car or inherited tail progress on return. After host End, controllers show “Back in
the lobby — you're still connected”, own identity, car/controls and the host-wait status; no timer.

**Phone administration.** Label pairing “Manage room from a phone”; its next panel says “The main
screen keeps running the game. This phone gets room controls, not a player seat.” Show the separate
two-minute QR/phrase and confirmation from §3.6. This is not host transfer. Extra-display pairing
is not implemented before G-SCREENS; its future role choice on the ordinary room join path and
readiness sequence are described in §6.6a.

All host/seat commands carry the existing epoch, target and idempotency/revision fields. The UI
shows pending status, reads the acknowledged reducer state and makes retries safe; it never starts
a second countdown, seat or score transaction from duplicate taps. All entry/exit/confirmation
panels preserve focus, support keyboard/pad navigation and have a useful Cancel/Back action.

### 10.7 Solo, teams, events and scoring (R32)

**Solo or teams** is a lobby toggle for every mode:

- **Solo:** everyone for themselves.
- **Teams:** common presets offer two, three or four teams without imposing a team-count ceiling; players pick a team in the garage (or host auto-balances by count / by standings).
  Team colour shows as a **tile-border stripe and car roof band**, but personal identity (number + colour
  + pattern) stays; teammates' nameplates get a team icon. No friendly-fire damage points (damage to
  teammates still happens physically, scores nothing). Team score = sum of members' round points
  (race: points by finishing position; derby: damage points). King uses its shared team-zone ledger
  instead of multiplying points by the number of occupants (§10.12).

**Event formats** (host picks):

| Format | How it works |
|---|---|
| **Quick Match** | One round, results, rematch. |
| **Series** | N rounds (3/5/7) of one mode or a host-built playlist (e.g. Race → Derby → Race). Championship points per round; standings between rounds. |
| **Cup** (tournament) | Series with a finale: last round worth double; all eligible controller identities retain a map ballot. No elimination or privileged top-player electorate. |
| **Knockout Cup** (large groups) | No fixed-size heats or count-based waiting. STRETCH only; any format must keep everyone playing with unbounded roster structures and explicit qualification rules. |

**Scoring:**

- **Race points** follow §10.12's complete position/finish formula, including the tail at any N.
  Fastest lap, most damage and biggest air are awards, not additional championship points in the
  initial ruleset; this keeps mode-to-mode standings understandable. Drop-ins classify normally.
- **Derby points** = damage points (damage dealt, part detaches and wrecks caused; no initial combo multiplier), converted to
  championship points by rank at the end of the timed round.
- Team: sum member raw round points for Race/Derby/Stunt; King uses its team-zone ledger. Convert
  team rank to championship points as specified in §10.12, preserving separate individual standings.
- Standings screen between rounds: animated bars, movement arrows, "on the podium" callouts, announcer
  line. Session leaderboard persists locally on the host until the room ends. Server `jj-store`
  receives only deliberately submitted support/rating data (§17.3); session analytics are deferred.
- **Awards** at the end of a Series/Cup: Most Wrecks, Biggest Air, Most Doors Lost, Ute of the Day, etc.
  Comic trophy cards; shareable screenshot.



### 10.8 Party flow: auto progression, voting, Party Mix (R38, R39, R50)

**The loop runs itself.** Nobody needs to touch the laptop for a party to keep going.
One host-owned RoundDirector drives Lobby → Preparing → Countdown → Running → Finalising →
Intermission; pause reasons compose with these states. Menus read it instead of inventing timers.
Ballots close visibly before final map warm-up; stale generation jobs cannot overwrite the winner.
The all-ready cohort consists of source-fresh, non-parked human seats and must be nonempty; bots
and disconnected seats cannot hold that start policy open. Reconnect preserves the same ballot.
Every setting declares immediate/next-life/next-round effect; round commit includes the selected
map, rules, roster/progress and prepared assets. Never start a zero-player auto-round loop.

The state sequence is an initial Lobby → Preparing → Countdown → Running → Finalising → Intermission
loop, followed by Preparing/Countdown for the next round, or EventEnd when a finite event completes
(§10.12). Preparation work may run in the background
during Intermission; only the director can commit it. Make these boundaries explicit:

| Boundary | Commit rule / failure behaviour |
|---|---|
| Ready/countdown | Freeze a start cohort when countdown begins. New seats join immediately with current selection and do not restart it; an original seat unready cancels a ready-based countdown. Force-start overrides Ready only, never asset/physics readiness. |
| Vote close | Ballots are editable until a published close deadline (initially 10 s before auto-start). One per eligible joined identity, including disconnected-but-not-parked seats; changes are accepted by host receipt order. Parked seats/bots do not vote. Freeze electorate/options at close; record the seeded tie-break and any host override. |
| Early start | All-ready or host **Start next round now** closes voting first, uses the recorded winner/default and waits for its preparation. Only this action advances the director; the explicit ready-policy override retains §10.6 warnings. |
| Replay visibility | Host **Hide replay** or a majority playback-skip vote ends only playback and keeps results/ballot visible. Intermission/vote deadlines continue unchanged; it neither closes voting nor requests an early start. **Show replay** can restore the reel during the same intermission. |
| Preparing → Countdown | Match `PreparationId`, rules/map/asset hashes and required host readiness. Use latest roster with the committed rules; late joins cannot invalidate the map job. If still loading at timer zero, show progress while garage/help remain usable. Failure retries/falls back per §11.2a, with a visible reason. |
| Running → Finalising | Freeze one result at the final tick; reject later round/life-scoped commands. Commit score/standings once (§3.4), select available highlights, and publish results even if replay or ancillary upload fails. Storage failure shows unsaved status, not an endless Finalising spinner. |
| End / Disband | End cancels pending jobs and voids any unfinished round, then shows committed event standings and returns to Lobby. Disband additionally revokes room credentials and routes. Old job completions and retries cannot start another round. |

With no active human seats, finish the current policy-controlled activity and settle in Lobby;
bots do not keep an empty party auto-starting. Manual/hidden/fault pauses freeze countdown, vote and
intermission remaining time (§3.5). A reconnected seat retains its selection, ballot and score.
Name/identity/Identify/camera changes are immediate; car/profile and assist changes apply at a safe
next-life or next-round boundary; mode/theme/team/scoring changes are next-round settings. A garage
car change never grants a free repair or changes the current life's collider. Revalidate the selected
asset before applying it; an unavailable choice shows the explicit current/default fallback.

```text
Round ends ─► Highlight reel (plays by default, ~60 s timer, skippable by vote/host)
   │            • side panel: round results, soft-competition awards (§10.10)
   │            • BIG QR + short URL: "Jump in! jammers.dilger.dev/j/ROO7"
   │            • controllers: vote for next map/mode, change car/name, ready up
   │            • host device: generating next map (§11.2a)
   ▼
Next round auto-starts when the timer ends (or earlier if everyone has readied)
```

- **Timer defaults:** highlight/intermission 60 s on the active presentation clock; start early when the eligible Ready cohort is ready or
  the host chooses **Start next round now**; ready-up is *optional* in Party Mix (nobody is warned or forced, they simply play with
  their current car). The already-visible automatic timer is distinct from a host overriding a
  ready-based start; that explicit force-start uses §10.6 warnings in any format.
- **Voting:** each joined controller identity gets 2–3 ballot options for the next round (mode + theme/map seed, shown as
  cards with a thumbnail). Most votes wins; ties use the recorded session RNG; the host can veto or pick directly before countdown, invalidating superseded preparation.
  In tournament formats voting is limited to the map, since the mode is fixed.
- **Presets (tailor to the group):**

| Preset | What it is | For |
|---|---|---|
| **Party Mix** (default) | Voted mix of race, derby, stunt and king-of-the-bowl rounds, running party scoreboard, soft awards, chaos events on | Mixed groups, house parties |
| **Derby Tournament** | Series/Cup of derby rounds, standings, voting on arena only | Groups who want to smash things properly |
| **Race Tournament** | Series/Cup of races, standings, voting on track only, chaos events optional | Groups who want to race properly |
| **Custom** | Everything from §10.7 and host settings | Organisers |

- **End game and Disband (R36):** the host can **End game** (show the final standings, awards and the
  night's reel, then return to the lobby with everyone still connected) or **Disband room** (everyone's
  controller shows a friendly "Thanks for playing" with the final standings, and room credentials are
  cleared). No automatic Disband follows an ordinary connectivity gap. After 30 minutes in Lobby
  with no active human source on the active presentation clock, End the event once and display the
  invitation lobby; retain room credentials and results. This does not create a repeated auto-round
  loop. Preview expiry is separate and may still end a preview room (§16.2a).
- **Host settings with defaults** (all in one place, remembered on the host device): intermission
  length, race finish timeout, finish bonus, derby length, chaos events on/off/frequency, L-plates
  allowed, family-friendly mode, voting on/off, team mode and autopilot behaviour. Dropout autopilot
  remains the R45 default; an off switch must not contradict that ruling without owner direction.

### 10.9 Late joins, recovery and race completion

**Race (R63): join last, a few seconds back.** For a genuinely new seat, locate the last still-racing
entrant's validated unwrapped route progress. Use a short history of that progress to select a safe
spawn about **3 seconds behind** (initial tuning value), or a conservative equivalent route-distance
gap when history is insufficient. Assign the new entrant the matching lap/checkpoint/branch state.
This is intentional drop-in progress inheritance, not an undisclosed teleport advantage: mark them
as a late joiner. They race the remaining event normally and can catch up/win from there.

Never use raw nearest-spline projection at crossings/shortcuts. Choose the correct route branch,
legal checkpoint interval and non-overlapping egress. Before enough race history exists, place after
the actual last entrant near the start. A stationary last racer still gets a safe positive spatial
gap behind them. Do not delay joining while waiting for an ideal gap. If all cars finished or the
round is already finalising, join the intermission/next-round preparation immediately.

**Reconnect and wreck are not new entry.** Reconnect restores the same car/progress. Wreck/manual
recovery returns to that seat's own valid anchor, not to the pack or last-place inheritance policy.
Fastest-lap awards require a fully driven valid lap; inherited progress is not a completed timed lap.

After the first finish, use the configured finish window (initially 30 s); rank unfinished racers by
validated progress when it expires. Crossing within the window earns the configured finish bonus.
Also provide a visible map-appropriate absolute round deadline if nobody finishes. Race clocks pause
with game time; intermission has its own explicit lifecycle policy.

**Derby:** unchanged R56: three minutes, ranked by raw damage points; late joiners simply had less time.
They still score and feature in awards/reels. Autopilot damage points remain reduced per the approved
rule; no hidden per-minute normalisation or forced learner result.

### 10.10 Soft competition, L-plates, "Surprise me" (R40–R42)

**Soft competition (R42):**
- Every round aims for **5–8 comic award categories** (a pacing target, not a limit on recipients) spread across as many different players as possible:
  Most Doors Lost, Best Crash, Biggest Air, Most Scenic Route, Longest Wheelie, Friendly Fire Champion,
  Slowest Finisher Ever, Autopilot Enjoyer, Most Debris Dropped, Roo Magnet, **Latest to Rock Up** (latest drop-in), plus the Australianisms from the research pass below. An award picker prefers
  players who haven't received one recently.
- **The reel aims to include every player with a notable event**, using group clips where useful and the permitted adaptive replay budget;
  the reel director (§10.4) reserves slots for players not yet featured.
- The winner still gets the podium and the announcer's big line: the competitive edge stays.

**L-plates (R40 amended by R64):**
- Keep visible front/rear L-plates and a badge. Assistance improves controllability, recovery and
  learning: selectable auto-throttle/steering help, clearer cues and easier recovery, not invulnerability.
- Learners **may win**. No blanket top-speed limit, "skilled always wins" assertion or score
  suppression. Instead (R64 clarified) **L-plates reduce the payoff of advanced mechanics**:
  smaller boost gain and shorter boost, gentler drift boost/speed retention, and a softer
  wheelie/hop (lower lift and launch) from the DRIVE-stick pull-release. The exact reductions are
  versioned tuning data (starting point: ~50–60% of the full payoff), tuned so learners enjoy the
  mechanics while skilled players gain a clear edge from mastering them. Tune against novice and
  experienced playtests in Race, Derby and zone/stunt modes; practice should produce a meaningful
  average edge.
- Do not silently add knockback/armour bonuses that dominate a non-racing mode. Assist parameters
  change only at an explicit permitted boundary and remain visible; accessibility/reduced-motion
  settings are separate from competitive vehicle tuning.

**"Surprise me" (R41):** one button in the garage for name and car; the result is shown with a
**"🎲 Picked for you"** tag and can be changed with one tap. A mid-round drop-in gets this automatically,
labelled the same way.

**Australianisms research pass (R53):** before copy is written, a short research task collects
Australian slang and cultural references suitable for award titles, announcer lines, car blurbs, chaos
warnings, UI copy and generated names, e.g. "Latest to Rock Up", "Flat Out Like a Lizard Drinking",
"Carked It" (most wrecks), "Dropped a Clanger", "Fair Dinkum Finish", "Couldn't Organise a Piss-up…"
(family-friendly variant needed), "She'll Be Right" (most repaired damage), "Maccas Run" (fastest lap),
"Bogan of the Day", "Chucked a U-ey" (most reversing), "Servo Pie" (most damage taken).
Output: `docs/copy/australianisms.md`, a table with the term, meaning, where it fits, a family-friendly
flag, and a regional/cultural sensitivity note (avoid slurs and anything punching down; Indigenous-derived
Australian slang is welcome per R114). The owner reviews the list; the approved subset feeds the award table,
announcer script (R55) and name generator.

### 10.11 Chaos events (R43)

Short, telegraphed, whole-room moments that reshuffle the pack and make everyone yell together. Each
is a data-driven event card (like weapons) with a warning phase (announcer line + on-screen banner +
visible signs in the world), an active phase and a clean-up. Mostly in **race** modes; a few derby-safe
ones.

| Event | Where | What happens |
|---|---|---|
| **Flash flood** | Race (Red Centre first) | Creek crossings flood (§11.5); current pushes cars, splash-downs on ramps |
| **Cyclone** | Race (coastal themes) | Strong crosswind gusts that push cars and lift light debris; rain makes surfaces slick; spinning debris |
| **Roo stampede** | Race + derby | A mob of kangaroos bounds across the track (soft collisions, big comic reactions) |
| **Dust storm** | Race | Visibility drops to near-field; headlights and emissive underglow matter; announcer loses it |
| **Road train** | Race | A giant road train thunders across a crossing; timing the gap is the game |
| **Hailstorm** | Race + derby | Dents everything a little, ice on the track briefly |
| **Bushfire front** | Race (grassland/forest) | Smoke and a creeping fire line that cuts a shortcut or opens a new one (never traps cars) |
| **Magpie swooping season** | Race + derby | A magpie harasses the leader (small steering nudges, loud) |
| **Drop bear** | Race | Joke event: something falls on the leader's roof |

Frequency: 0–2 per round (host setting: off / some / lots). Rules: always telegraphed ≥ 3 s ahead;
never places a car out of bounds; every card has scenarios (§15) like weapons; they are chaotic but
have measured disruption/recovery envelopes; the leader is slightly more likely to be the target (a mechanical,
visible event-card rule, not hidden ongoing speed/score catch-up). Record the target rule in the
telegraph and scenarios so the competitive effect is reviewable.

### 10.12 Complete initial rules, result data and participation boundaries

These are **engineering defaults for the first versioned ruleset**, not claims of balanced gameplay.
Changing them creates a new rules hash and new fixtures; changes apply next round. Minimum ships
Race/Quick Match with automatic rematch and a running session ledger. Party Mix and its additional
modes are Full. Hide unavailable choices with an honest preview scope description; never implement
fake votes for modes the build cannot prepare.

**Race.** Start with three laps, a 30 s first-finisher window, and an absolute deadline of
`max(180 s, 2 × laps × referenceLapSeconds)` from countdown completion. The generated map stores
`referenceLapSeconds`, derived from segment lengths and a versioned reference speed/curvature model;
offline bot laps qualify that estimate. The clock is visible from the start. At finish, a car becomes
non-scoring and non-contact with racers/debris, retaining terrain collision and its tile; a visible
cool-down autopilot takes it around the course. No finished racer can sabotage the remaining race.
End at the earlier of the active deadline or all current entrants finishing/withdrawing, after
processing the complete final tick's events. Late joins
before Finalising do not extend either deadline. If nobody remains racing, new seats enter intermission.

Finish ordering uses the authoritative tick plus interpolated checkpoint crossing fraction; an
exact tie shares place/points, with stable seat order only for display. Unfinished entrants rank
after finishers by legal unwrapped progress, then the tick at which that progress was reached;
equal values share place. Entrants still withdrawn at finalisation retain frozen progress and get
DNF, never a finish bonus; returning before finalisation resumes the same unfinished result record.
A finished seat cannot use Leave/return to become an unfinished racer or earn another finish bonus.
Seats that never entered have DNS and zero. Award valid timed laps only when every required interval
was actually driven; recovery or inherited progress invalidates that lap's timing.

**Championship conversion.** For ordinal rank 1–10 use `[25,18,15,12,10,8,6,4,2,1]`; every later
classified rank receives 1, so there is no truncated scoring array. A Race finisher earns +5 by
default (host-configurable next round); DNF earns its placement points only. Tied entrants receive
the points of their shared competition rank (1,1,3, not 1,1,2). Derby/Stunt/King convert their raw
rank through the same table without a finish bonus. Bots appear in round classification but have
separate bot standings; human event ranks/points are computed among humans, so filler retirement
cannot alter a person's event history. Race/Derby/Stunt team round rankings use summed member raw
round scores (Race uses individual placement/finish points); convert that team rank once through the championship table. King uses
its team-zone ledger. Keep personal standings separately; team ties compare sorted member results,
then remain shared if identical. Event ties compare
round wins, then counts of second places and so on; an identical record shares the podium.

**Derby raw points.** Each accepted HP of opponent damage gives 1 point, a detach gives +5 and a
wreck +20, once per part/life event. Self, friendly-fire, spawn-protected and environmental damage
give zero. Use integer damage units of 0.001 HP and score units of 1/2000 point: normal damage earns
twice its damage units; bonuses are exact integers. Autopilot halves that credited event once, so a
10 HP + detach + wreck episode gives 35 human points or 17.5 autopilot points. The sim records control
mode/team at the causal action, not at score display time. Secondary debris attribution expires
after 3 s game time since the last qualifying instigator impulse; otherwise environmental. Combo
callouts are presentational in v1, with no multiplier until a later tuned ruleset. Equal raw scores
share rank. Keep raw totals visible; championship conversion does not normalise late-join time.

**Stunt Arena.** Initial round length 180 s; score only validated landed stunts. Start an airborne
episode after 0.2 s without grounded wheel contacts; on stable landing award 10 points per airborne
second and 25 per completed signed-axis 360° flip. Wheelies earn 5 per second after 0.3 s of valid
front-wheel lift and rear-wheel ground contact; commit on controlled front-wheel return. Losing the
life/OOB invalidates the pending episode. A near miss needs a different live car, positive closing
speed ≥ 5 m/s, clearance < 0.5 m and no contact; award 5 once per encounter, rearming after separation
of more than 5 m. Record episode IDs; resting, suspension jitter and repeated boundary samples do not score.
Destruction uses the Derby damage ledger without a hidden combo multiplier. All thresholds are
versioned hypotheses qualified against intentional/mash/no-input scenarios and learner profiles.

**King of the Bowl.** Initial round length 180 s; one clearly marked moving zone follows a validated
seeded path, with its next move telegraphed 3 s in advance. Eligibility uses chassis-centre inclusion,
with 0.25 m exit hysteresis. Award 1 raw point per second, integrated in fixed ticks, to the sole
occupying competitor; in Teams, credit that rate once to the uncontested team's zone ledger,
not multiplied by occupants. Team King ranks teams on that ledger and
converts team rank directly to championship points; participant contribution is informational.
Two opposing competitors/teams contest it and stop zone scoring. Wrecked,
protected, withdrawn or finished cars are ineligible. Autopilot can contest/score by the same physical
rule; only Derby damage credit has the 50% modifier. The zone never moves into an unreachable region.

**Mayhem.** In a ~2 s derby wreck wait, ACTION aims a local ground marker and vertical sector entry
requests one barrel/bin action per `VehicleLifeId`; DRIVE remains inactive. A 0.75 s visible warning
precedes the effect. Respawn never waits for it: the accepted action carries the wreck-life ID and
may execute after respawn, but only in that still-running round. Reject overlapping protected spawns,
OOB placements and stale-round requests with a visible outcome. First qualify rolling barrel and
red-lid wheelie-bin variants; more variants reuse the same contract. Mayhem damage may earn at most
2 points per action with no detach/wreck bonus; physical fragments still persist dynamically. Only
an opponent-credited wreck grants a scoring mayhem action; self/environment wrecks get a harmless
visual action, preventing self-wreck farming. A mayhem-caused wreck grants no scoring mayhem reply.
Small honest points can decide a tie; the previous promise that they cannot decide a winner is removed.

**Teams and fillers.** Existing team assignments freeze at countdown; pending team changes take
effect next round. New mid-round team entrants join the least-populated active team, using seeded
ties, and receive that assignment before spawning. Teams of one/unequal sizes work; present raw
sum scoring honestly rather than promising equal odds. Filler target N means `max(0,N-humanCount)`
bot entrants at preparation, not a human admission limit. Human joins never wait for bots. Reconcile
excess fillers at the next round boundary, not by deleting a racing car or its debris. Bot identity
is visibly marked, has no ballot and never counts towards the nonempty human start condition.

**Votes and events.** Generate three distinct qualified options where available, otherwise display
the actual smaller set. Zero ballots uses the displayed default; ties use recorded session RNG.
Each eligible joined identity can edit one ballot until close. For reel-skip, freeze the displayed
eligible cohort on the first skip vote; threshold is `floor(cohort/2)+1`, with no-vote never counted
as assent. Expire this cohort with the intermission; reconnect does not duplicate it. Ready resets
at each new intermission, preventing previous-round Ready from instantly skipping every reel.
Host **Start next round now** starts next-round preparation; **Hide replay** and controller-majority
playback skip leave the ballot/deadline unchanged (§10.8). Series defaults
to three rounds; other positive lengths work. Cup doubles final-round championship points, including
the finish bonus; raw in-round physics/scoring is unchanged. At a finite event's end, stop auto-next
in EventEnd with standings and Rematch/Lobby. Rematch creates a new `CompetitionId` with zero event
points, preserving night/session history. End game closes that event; it does not disband the room.

**Data and commands.** Add `CompetitionId`, `RulesetId`, `VoteId` and `ResultId` to the typed vocabulary.
`RoundResult` contains round/competition IDs, final tick, map/rules/profile/build hashes, starter and
late-entry flags, frozen team membership, finish/DNF/DNS, legal progress, raw points, classification,
converted points and award facts. `CommitResult` is idempotent by `RoundId` and rejects a conflicting
payload for an already committed result. Store the result and recomputed event/session standings
atomically; display separate in-memory and saved revisions. Retry saves the current ledger containing
all unsaved results, rather than overwriting a newer checkpoint with an old asynchronous callback.

`SetPreference`, `SetReady`, `CastVote`, `LeaveSeat`, `RequestRecovery`, `EndEvent` and `DisbandRoom`
are reducer commands with command ID, expected scope/revision and authenticated actor. Return applied
revision or a stable reason (`stale`, `wrong-phase`, `not-authorised`, `asset-unavailable`, `ended`);
receipt is not application or persistence. Mutations of independent seats need not fail because
another seat changed; use scoped revision checks. Freeze finalisation once and let upload/replay
failure degrade only those features. Fixtures must cover simultaneous finish/wreck/leave/vote-close
and retry after a result commit; these rules define which outcome wins before a UI is built.

## 11. Procedural Australian tracks

### 11.1 Themes

**First theme (R25): Red Centre, the outback around Uluru and Kata Tjuta.** Every generator feature is built and tuned here first (§11.5). **Build order:** Red Centre → Beach → Outback grassland → Forest → City → Desert dunes. Theme notes: Beach (Gold Coast / Bondi feel), Forest (eucalypt, tall timber), City (Sydney/Melbourne laneways,
harbour), Outback grassland (red dirt, spinifex, windmills), Desert (dunes, salt flats, Uluru-style
monoliths in the distance), plus candidates: Great Ocean Road cliffs, Snowy Mountains (dry alpine),
Tropical north / rainforest, Mining town, Wine country. A theme is a **presentation + surface + feature
palette**, not new code.

### 11.2 Generator architecture

**Procedural first, authoring possible (R24).** Every map, race or derby, is a **map document**
(`jj.map.v1`, schema in `jj-contracts`): course graph/arena shape, terrain parameters or heightfield,
surface map, feature list, dressing rules, spawns, checkpoints, water events. The generator is a
function `seed + theme + constraints → map document`. The game only ever loads map documents. So a
hand-crafted map later is just a map document written by hand or with an editor, or a generated one
that was pinned and edited. Both go through the same validator and scenarios. No separate code path.

Separate **structure** from **presentation**: authoritative route/collision/surface data is one
versioned document; mesh/lighting/dressing choices consume it without changing its gameplay hash.
Route shape is designed first: flowing corner rhythm, readable elevation, alternative risk/reward
lines, recoverable landings and useful overtaking—not noise with a road painted over it. Compose
validated feature families (entry/exit/landing envelopes) into a fresh route and validate the result.
Provide a driveable standard line; difficult jumps/shortcuts are opt-in rather than compulsory failure
for beginners. Roads may be formed/tarmac, graded dirt or rough connecting sections with deliberate
surface transitions and appropriate side barriers/structures. Fictional red-rock gorges, ledges,
bridges and creek jumps are first-class structural pieces, not random decorations. Spectators,
stands, pit areas, safety fencing and crowd audio appear where the venue plausibly supports them;
remote outback routes do not get identical grandstands pasted along every metre.

Generation stages:

1. **Course graph:** closed loop (race) or bounded arena (derby) from a seed + constraints: length,
   corner mix (hairpins, sweepers, chicanes), elevation budget, width variation, overtaking zones,
   shortcut branches (risk/reward), crossovers/bridges (CANDIDATE).
2. **Terrain:** heightfield per theme — dunes (sand), rolling grass, rocky outcrops, beach slope into
   shallows; the track is carved into it with banking where the corner wants it.
3. **Surface map:** on-track (tarmac, dirt, gravel, sand-packed) and off-track (soft sand, mud, grass,
   shallow water, scrub) painted by rules (theme + curvature + elevation), each with a physics
   material (§11.3).
4. **Features:** jumps (with landing zones verified by simulation), dunes, whoops, ramps, water
   splashes, narrow bridges, tunnels, destructible prop clusters (§8.4), hazards.
5. **Dressing:** curated, validated kit pieces per theme (fences, signs, trees, buildings, landmarks)
   placed by rules, never arbitrary.
6. **Validation:** port useful existing validator invariants into the Rust contract: drivable width, wall thickness, jump landings
   (bot-simulated), no unreachable checkpoints, spawn placement for arbitrary actual N; N = 24 is one test case, camera clearance for chase
   and first-person cams, lap-time target band (bot laps), overtaking opportunities count.
7. **Fun scoring (for curation, not generation truth):** bot-race metrics — lead changes, pack
   spread, number of jumps/surface transitions, crash rate per corner. Seeds that score badly are
   rejected; seeds that play well in rounds are **pinned** as a curated seed list per theme.

### 11.2a Runtime generation in the browser (R26)

- The generator is a **Rust crate `jj-procgen` compiled to WASM**, run in a **Web Worker** on the host.
  The same crate runs natively in CI and in the `sim`/sweep tools. Shared source alone does not prove
  identical maps: canonical gameplay map bytes must agree across targets for the qualified seed bank,
  with specified RNG, ordering, float/quantisation rules and generator features. Store the canonical
  map for reproduction; a seed is a recipe, not a substitute for versioned output evidence.
- Output is a `jj.map.v1` document (plus meshes/heightfield buffers passed as transferables). The host
  builds render meshes and Rapier colliders from it. Generation runs **during the lobby, results or
  countdown** for the *next* round, to overlap preparation with non-driving time; the lobby shows a live preview of the
  upcoming map with a **Reroll** button for the host.
- **Budgets (targets, measured in G-PERF):** generate + validate ≤ 1.5 s on this laptop, ≤ 4 s on a
  phone host; peak worker memory bounded. If a phone host is too slow, the generator uses a lighter
  detail level for the same seed rather than a different layout.
- **Runtime checks vs offline checks:** the fast structural validator (width, walls, landings by
  ballistic check, spawn clearance, reachability) runs in the browser on every map; a failing seed is retried within a preparation deadline, then a conservative validated procedural recipe is used. There is no endless silent reroll loop. Full **bot fun-scoring** is too slow for runtime; it runs **offline** in CI/sweeps
  to tune the generator's parameters and constraints, so runtime maps land in the fun zone by
  construction.
- **Seeds are shareable:** a round's seed + theme + generator version is shown on the results screen;
  "play this map again" reuses it. Players can **rate a map** (👍/👎 on their controller after a round);
  ratings go to the server (§13.6, FrankenSQLite) and feed generator tuning. A hand-crafted or pinned map
  (R24) is just a stored map document the host loads instead of generating.
- Generator versions are pinned per build; a seed reproduces only with the same generator/constraint
  and gameplay profile versions. Hash canonical map data. Separate structure and dressing RNG streams.
- Preparation includes generation, validation, collider construction, resource upload and shader warm-up.
  Publish a Ready result only when all are complete; atomically replace the old round. Cancelled/stale
  jobs cannot win a later commit. Measure overlapping map/replay memory, not only worker generation.
  `PreparedRound` carries `PreparationId`, generator/map/rules/profile/required-asset hashes and separate
  worker-world/host-render readiness. The procgen worker produces data; the sim worker owns collider
  construction and the main thread owns GPU upload. Prepare within measured memory, retaining the
  old presentation until the new one is usable. Optional higher LODs and audio do not hold Ready;
  missing required geometry/colliders do. If the conservative recipe also fails, show Retry/Return
  to lobby and retain the room/results; never load an invalid map or silently reroll forever.
- Lower visual detail must preserve the same gameplay map/colliders. Crowd/background LOD and props'
  rendering detail do not justify deleting authoritative objects or reducing the number of players.
- Arena count is snapshotted for initial generation; mid-round joins never queue for capacity or
  trigger unsafe terrain reshaping under cars. Allocate safe spawn poses dynamically; regenerate
  a suitably sized fresh arena between rounds.

**Minimum geometry is real gameplay data.** Include tarmac/packed-dirt/off-track surface IDs and
the associated baseline grip/resistance in the Minimum loader/profile, even though the full surface
library and presentation are V2-51. Red Centre greybox needs distinguishable road/terrain, a normal
line, a jump with safe bypass/landing, legal checkpoints and identity-friendly light, not six final
art kits. `jj.map.v1` includes quantised coordinate/height units, route-edge/branch/checkpoint IDs,
surface IDs, spawn/recovery corridors, reference lap estimate, bounds and hazard declarations.
V2-55 must reject missing/unknown gameplay fields; canonicalisation/rounding is specified before
native/WASM fixtures, rather than relying on serializer float formatting.

“Play this map again” pins the **canonical map document plus generator/constraint/profile hashes**
within this room/build; it does not merely reuse a seed with a different count-sensitive recipe.
Explicit rematch may reuse that map at the new roster size, using dynamic placement; ordinary fresh
rounds may regenerate for the new roster. Validate compatibility before offering a saved map in
another build. Unsupported versions show an explanation/export option, not a silently changed map.
The host can reroll during preparation; each reroll increments `PreparationId`, cancels old work
and preserves already committed results. A seed/map share contains no room or seat capability.

### 11.4 Derby arena generation (R24)

Derby maps are generated as proper derby arenas, not race tracks with a camera change:

- **Shapes:** bowl, stadium oval, figure-eight crossover, quarry pit, multi-level (ramps up to a
  plateau), island (water moat), each sized to the expected car count (§6.4).
- **Features:** centre mound or pillar clusters to ram around, ramps and kickers for aerial hits,
  destructible props at the edges, soft walls (tyre stacks, hay bales) vs hard walls (rock), debris
  catch zones that don't trap.
- **Rules:** no dead corners (bots must reach every region), sightlines for the Overview camera, extensible safe spawn placement for actual N, with no fixed 24-slot ring, validated lips (no escapes).
- **Fun scoring:** bot derbies measure hits per minute, how spread out the hits are (not one choke
  point), wreck rate and time spent stuck.

### 11.5 First theme: Red Centre (Uluru and Kata Tjuta)

- **Look:** red sand and ochre dirt, spinifex, desert oaks, salt pans, huge sky; Uluru-like and
  Kata Tjuta-like domes on the horizon and as landforms the track sweeps around.
- **Track features:** tracks weave between clusters of red domes (Olgas-like) through canyons and
  gorges; **crazy jumps** over dry creek beds, dune kickers, rock ledges and road-train crossings.
- **Water that flows sometimes:** seasonal creeks and **flash floods**. Creek crossings are dry on
  most seeds. On some seeds, or partway through a race, water flows through them: shallow water
  surface (slow, splash), a moving current that pushes cars sideways, and some ramps turn into
  splash-downs. Telegraphed (rumble + announcer + a water front you can see) so it's a fun hazard, not
  a gotcha. Built as a map-document "water event" so any theme can reuse it.
- **Derby:** quarry pit and dry claypan bowl arenas ringed by red rock.
- **Cultural respect:** Uluru and Kata Tjuta are sacred to the Anangu traditional owners (climbing
  Uluru has been banned since 2019). The game uses **fictionalised, inspired-by** red-rock landforms,
  doesn't use real names on in-game sites, and never has cars jumping off or driving over the real
  monoliths. The real silhouettes, if used at all, are distant scenery. Check with the owner before any
  marketing uses the real names.

**Spike first, owner-observed (G-PROCSPIKE).** Once the engine re-architecture is in place (Rust/WASM

**Structure of the work.**

1. **Seed and terrain core (one cut, first).** The seed mechanic and RNG-stream split (structure vs dressing),
   the biome-agnostic course graph, heightfield undulation (noise/spline algorithms chosen and recorded with
   evidence), features-as-first-class pieces (jumps with entry/landing envelopes, whoops, crests, creek dips),
   **seeded dressing scatter** (spinifex, trees, shrubs, rocks, bins: placement density and layout come from the dressing RNG stream through a smart noise/point-distribution algorithm, so clumps, clearings and spacing look natural rather than uniform; keep clear of the route, surfaces and spawns, and stay deterministic native/WASM), the biome selector/transition rules, the `jj.map.v1` biome/feature fields, and the structural validator
   (§11.2). It ships with a trivial placeholder biome so the engine is testable alone.
2. **Four parallel biome cuts** (town, rocks, outback dirt, outback bitumen), each consuming only the core's
   interfaces: its own surface mapping, dressing rules, kit pieces at playtest scope, and a capture + scenario.
   They share no files beyond the core's trait/data interfaces, so they can run as separate swarm tracks.
3. **Derby** (V2-56) is separate: arena shapes from §11.4 with the rocks biome's vibe (red domes, quarry
   walls, boulders). It reuses the rocks kit but not the race route code.

**Signs (owner ruling, 2026-10-02: new signs permitted within a faithful style).** Real Australian signs
are the style source: <https://en.wikipedia.org/wiki/Road_signs_in_Australia> (images on Wikimedia Commons;
`generated/wikimedia-commons-sign-sources.webp` shows the pieces worth pulling). Invented signs are allowed
and encouraged, e.g. a yellow warning diamond reading "BLOODY BIG JUMPS AHEAD" or "DANGER!", provided each
follows a real sign family's **grammar**:

- **Warning:** yellow rotated-square diamond, black border and black legend or pictogram; short, upper-case,
  road-sign phrasing with the joke in the wording, not in a broken layout.
- **Direction/route:** green rectangle, white legend, route shield (e.g. A87 / STUART HWY), distances and arrows.
- **Tourist/information:** brown rectangle, white legend.
- Standard post mounting, sizing and placement (ahead of the hazard, at junctions), and highway-style
  sans-serif lettering that stays legible at the smallest camera tile.
- Pictograms drawn from real symbol conventions (jump/crest, steep descent, unsealed road, animals).

New text and symbols are authored as data (sign family + text + pictogram), rendered from one code-drawn
sign kit, so adding a sign never needs new geometry. Record each sign's family and, for any real sign
copied, its Commons source and licence in the asset sidecar. Do not invent new shapes or colour families
(the "incorrect signs" sheet shows the failure). Place names and jokes may be fictional, per §11.5's
cultural note.

## 12. Visual style and the art pipeline

### 12.1 Direction: bold comic

- **Look:** cel/toon shading with 2–3 tone ramps, **thick ink outlines** (screen-space edge detection on
  depth + normals + object ID, run once in post), halftone dots in shadows, bold flat colours with a
  saturated curated palette, comic speed lines at high speed, impact words ("KRUNCH!", "BOOF!") as
  sprites on big events, squash on landings (visual only).
- **Cars:** chunky exaggerated proportions (big wheels, stubby bodies, oversized archetype flair) so
  they read at 40 px; faceted/polygonal geometry at every detail tier (R81); paint from masks (player colour + pattern); decals and huge roof numbers.
- **Worlds:** Australian themes rendered as comic panels — strong silhouettes, graphic skies,
  stylised foliage cards, limited-palette ground textures per surface.
- **UI:** hand-inked feel — panels, buttons and borders with **slightly irregular, not-quite-straight
  edges** (procedurally jittered SVG paths or 9-slice textures with a subtle wobble, consistent per
  element, never animated jitter), bold display type, sticker-style badges, comic speech-bubble
  callouts. Tasteful: wobble is a few pixels at TV scale, text stays crisp and straight.
- **Readability rule:** comic effects never cover identity (number/colour) or the road ahead.

### 12.1a Shaders: comic + a bit of Mad Max, with emissive everywhere (R34)

The comic base (toon ramps, ink outlines, halftone) gets a **post-apocalyptic, sun-bleached, hot-metal**
layer, with **emissive highlights** so everything pops at night and in the grid:

| Shader / effect | What it does | Notes |
|---|---|---|
| **Car paint** | Toon-ramped paint from masks + identity colour, **rust and scorch creep** driven by damage (mask B), edge-worn bare metal on corners (curvature bake), dust layer by surface driven over | Ramp stays bold so identity reads |
| **Hot metal / exhaust** | Exhaust tips and turbo pipes **glow orange→white** with RPM and boost; heat-shimmer (screen-space distortion) behind cars at high revs | Distortion only in larger tiles / Overview |
| **Emissive kit** | Headlights, taillights, **light bars and roo-bar spotlights**, underglow in team/identity colour, glowing roof number option at night, weapon charge glows | Selective bloom (existing emissive-only bloom) run once in post |
| **Boost flames** | Stylised comic flame sprites + emissive cone; blue at full boost | |
| **Sparks and embers** | GPU particles on scrapes, part detaches, wreck bursts; embers linger on the track | Per-view effect detail; no live gameplay-entity quota |
| **Damage glow** | Heavily damaged cars show glowing cracks and smoke; wrecks leave burning husks with flickering emissive for a few seconds, then smoulder | Debris stays (§8), glow fades |
| **Sky and light** | Harsh sun, long shadows, heat haze on the horizon, **dust storms** as a theme weather event; dusk/night variants with orange sky and emissive-lit tracks | Fog gradient per theme |
| **Ground** | Sun-cracked clay, red dirt with tyre-track decals that accumulate, sand with wind ripples; wet surfaces get specular sheen | Tyre tracks persist like debris |

### 12.3 Contracts between art and game (R17)

The principle (informed conceptually by how studio art-loop tooling works — the exact linked tooling from the Spider-Man demonstration discussed with the owner — not by copying scripts): **the game declares what it needs as a
machine-readable contract; the art pipeline produces assets that prove they meet it; CI checks the
proof.** Artists/agents can change anything that keeps the contract.

Concretely:

- `art/contracts/*.schema.json` — one per asset class (vehicle, destructible prop, kit piece,
  surface texture set, UI element, comic effect sprite).
- Each exported asset ships a **sidecar** (`*.asset.json`) declaring contract version, node names,
  parts, budgets, textures and bake provenance.
- `tools/validate-assets` (Rust CLI in the workspace, §13.2, plus a Blender-side pre-export check)
  validates GLB + sidecar against the schema and budgets; runs in CI and as a pre-export hook.
- The game loads assets **only through the contract**: it reads the sidecar, not guesses from mesh
  names. A contract version bump is a deliberate, reviewed change on both sides.
- Asset **preview captures** (§15) are part of the contract evidence for vehicles and destructibles.

> **Art-pipeline spike (2026-09-29): GO.** See `spikes/art-pipeline/SPIKE-REPORT.md`. Blender 5.2 headless +

> triangles (LOD0/1/2), one material and a code-drawn atlas, weighted silhouette IoU 0.947 against the owner's

> InstancedMesh per part type gives 216 draws and 3.6 ms per frame at 1080p (5.1 ms at 4K), versus 3,602 draws

### 12.4 Vehicle contract (V2-61 creates `art/contracts/vehicle.schema.json`)

- Units metres, one documented forward axis, origin at ground between axles.
- Archetype-specific optional parts per §8.1, each with its own stable semantic ID, mesh/deformation data, collider proxy `col_<part>`, attachment
  point, hinge axis for hinged parts, mass fraction, damage-stage variants (`<part>_dent`).
- `wheel_*` pivots at hubs; `cam_fp` (first-person camera), `cam_tp_target`, `com`, `exhaust_*`,
  `light_head_*`, `light_brake_*`.
- Materials by semantic name: paint, tyre, wheel, glass, plastic, metal, headlight, brakelight,
  interior, decal, underside. UV0 main, UV1 bakes. One mask texture (R paint, G pattern, B dirt/damage,
  A emissive) + palette/ramp; comic style keeps texture budgets small.
- The source is the model script, its parameter file and the reference sheets (R81); the same script emits
  LOD0/1/2, with triangle/texture/draw budgets qualified by G-LOOK/G-PERF. RECOMMENDED: bake the script's
  output to GLB + sidecar so the §12.3 validator inspects real data; building at runtime from the script is the
  alternative V2-61 evaluates. Author enough detail for the silhouette and close view; a higher-detail source may
  bake into simpler meshes, but is not automatically the shipped gameplay mesh.
- Physics sidecar: archetype, mass, suspension hardpoints; references the vehicle profile.
- Localized deformation states/cage or morphs, stable part IDs across LODs, and detached deformed variants.
- `lplate_front`/`lplate_rear`, identity and camera anchors are chassis-stable through part loss.
- The validator inspects exported GLB data, not just sidecar claims. Validate mass accounting,
  collider shape, draw/material cost and decoded resource usage; performance targets are not player caps.
- Round-trip: the baked GLB reloads in Three.js (GLTFLoader) with identical nodes and bounds; a Blender round-trip
  is optional for R81 vehicles.
- R81 vehicles carry paint as an **atlas paint key** (pure-white texels are tinted by the player colour, so glass,
  lamps and livery keep their colours) instead of a separate paint-mask channel; pattern and dirt/damage channels
  remain open for V2-61.

**Detail strategy (owner follow-up):** use one semantic vehicle asset family with multiple geometry
and texture variants, not unrelated PC/phone models. Start by testing roughly **1–3k triangles** for
the close gameplay mesh, **500–1k** for medium views and **150–400** for distant/small views, including
wheels and visible attachments. These are hypotheses, not hard ceilings or historical claims about
Mario Kart. Increase detail where close-view captures show a worthwhile improvement and measured
cost allows it; reduce it where the projected silhouette and deformation read just as well. A
single-car hero/first-person view can justify richer detail than distant cars in a crowded grid.

**Measured starting point (R81, Spike J):** ≤ ~1.3k / 0.9k / 0.6k triangles for LOD0/1/2, all faceted. Every grid
tile renders the field, so cost scales with cars × tiles: RECOMMENDED one InstancedMesh per part type across all
cars (draws per tile constant in N; a dented part is an instance of that part's dented mesh, a detached part an
instance with a physics-driven matrix), with the shadow map updated once per frame rather than per tile. These are
G-PERF inputs, never player or debris caps.

Spend geometry on silhouette, wheel rotation/suspension and targeted crumple regions. Use masks,
colour/normal detail and a few deliberate panel vertices for small features instead of subdividing
every face or modelling invisible bevels. Author/validate LODs with matching part IDs, anchors and
damage meaning; generic decimation must not erase dents, move pivots or restore a detached door.
Collision proxies and mass remain the same across visual LODs. Measure triangles submitted across
**all** views, material/draw counts, morph/instance cost, texture residency and shader cost together.

Ship a validated baseline variant for every required asset, with higher detail available by immutable
self-hosted URLs when useful. Choose projected-size LOD per view, with hysteresis, and select texture
resolution/residency from measured rendering pressure. Coalesce shared loads and release unused high
detail; a failed optional upgrade leaves the baseline visible. No browser GPU/free-RAM API is assumed
to provide a universal asset budget. Controllers still load no world assets; phone hosts and laptop
hosts run the same adaptive path. Art-source detail and runtime resource choice are separate decisions.

## 13. Architecture — new core, not a preservation exercise

### 13.1 Selected direction and runtime ownership

**RECOMMENDED implementation of the new owner direction:** build the authoritative gameplay and
session core in Rust, compile it to WASM for the browser and native for tests/tools/future hosts.
Use Rapier directly within `jj-sim`; do not retain a second authoritative JS vehicle simulation.
Three.js is the presentation choice, not the owner of physics or game rules. Neither the old Jammers
implementation nor Soccer code is a dependency. [S1, S3, S4]

```text
Controllers / independent hub sources / host-local pads and keys
                         │ normalised state + deliberate commands
                         │ remote: WebRTC data channels, direct or TURN
                         │ host-local: direct adapter, no network round trip
                         ▼
Browser host (one shared game display)
  Main thread: input adapters, transport, DOM/UI, Three.js rendering, audio
                         │ commands / lifecycle / reusable state buffers
  Simulation Worker: jj-session + jj-sim (Rust/WASM, Rapier, 120 Hz game time)
                         │ snapshots, committed gameplay events, storage intents
  Browser storage adapter: IndexedDB room identity + completed results/checkpoints
  Procgen Worker: jj-procgen (Rust/WASM) → versioned map document + buffers
  Replay recorder: compact state/events → retained clips → end-of-round presentation

Rust HTTPS service: pinned bundles + room create/join/resume + authenticated signalling
                   + host-generation fencing + short-lived TURN credentials
Cloudflare STUN/TURN initially: connectivity assistance/fallback; no game authority or display fanout

Same jj-sim / jj-session / jj-procgen sources
  → native scenario runner, parameter sweeps, CI, future native host adapter
```

The worker is a Jammers recommendation for separating heavy 3D simulation from UI/render work,
**not a claim that Physical Soccer already uses a simulation worker**. Its inspected browser plan
starts with simple threading and adds workers after profiling; its shared Rust core and explicit
lifecycle are the useful reference. Worker transport cost must be measured. Keep the scheduler
adapter thin enough that in-process headless tests and a future native host use the same core. [S1]

A native simulation binary is not automatically a native graphical application. A future desktop
shell may embed the self-hosted web renderer; a fully native renderer needs its own adapter. These
are deployment options enabled by the core boundary, not additional 0.2 release requirements.
WebGPU accelerates presentation here; it does not imply Rapier has moved onto the GPU.

### 13.3 Protocol and live input

**Required transport direction (R77).** Controllers connect to the browser host using WebRTC data
channels. ICE prefers viable direct paths; TURN provides relayed connectivity within the same API.
Prefer UDP, but qualify TURN TCP/TLS fallback for networks that block it; this is not a separate WSS
gameplay scheme. Record the selected path, including the client-to-TURN transport. The Rust HTTPS
service still creates/resolves the shared room code/URL, authenticates join/resume/host ownership,
exchanges offer/answer/ICE and issues short-lived scoped TURN credentials. Authorise signalling
before disclosing peer candidates. Public bootstrap remains required even if gameplay stays on LAN.
Neither RaptorQ nor a native Rust WebRTC endpoint is required for this browser-to-browser path.

**Direct connectivity from the first slice (R79).** Use native `RTCPeerConnection`,
`iceTransportPolicy: "all"` and trickle ICE. Exchange candidates as they arrive; do not wait for all
STUN/TURN gathering to finish or impose a serial “try LAN, wait, then try cloud” timeout. Keep host,
server-reflexive and relay candidates eligible, including browser-provided mDNS host candidates and
IPv6 where supported. Do not force relay mode in production, strip local candidates, request media
permissions to reveal addresses, or require users to disable browser privacy settings. Browser ICE
selects the path; `all` alone is not proof that LAN was selected. Measure and investigate unexpected
relay use on the reference LAN. “Same Wi-Fi” cannot guarantee direct reachability through guest
isolation, VLANs, VPNs, firewalls or browser policy. Keep TURN available during negotiation. [S20]

Use one peer connection per remote browser endpoint: its phone touchscreen and any hub sources
share the connection/channels while preserving independent source claims and freshness. Host-local
pads/keys bypass networking. Controllers do not form a mesh. Pick one negotiation initiator (the
controller endpoint) and tag offers/candidates with connection/negotiation generations; coordinate
ICE restarts through the same signalling route and reject stale negotiations. Reuse connections
across rounds. A network change may require a paced restart, not a new seat; avoid restart loops or
periodic churn of a healthy direct connection. Qualify reconnect after background/resume.

**Cloudflare first; provider substitution later.** Use standalone Cloudflare STUN/TURN with native
WebRTC; neither RealtimeKit nor the media SFU is required. Rust keeps the provider API key secret and
exposes an authenticated `IceConfigProvider` result containing standard `iceServers` plus expiry.
Issue temporary credentials per authorised endpoint; namespace issuance/accounting by deployment
realm without making TURN itself the room authoriser. Return supported UDP and TCP/TLS alternatives,
including TLS on 443; filter browser-blocked URLs rather than hardcoding provider IPs. Credential
refresh is a lifecycle operation, never a tick/input request. Refresh before expiry and qualify
`setConfiguration()` plus any necessary ICE restart on actual browsers; an expiring TURN credential
must not impose a maximum room duration. Cloudflare documents that expiry can disconnect an active
allocation. A credential/API failure should leave a viable direct connection usable and report
relay unavailability; it must not manufacture a seat limit or tear down healthy direct play. [S19]

Keep room resolution/signalling independent of the provider credential request: fetch ICE credentials
concurrently and allow direct negotiation to proceed if issuance is slow/unavailable. Adding fresh
TURN configuration later may need a coordinated ICE restart; qualify that recovery rather than
claiming that changing configuration alone necessarily repairs an existing allocation.

Observe relay incidence, connection failures, latency and Cloudflare usage during playtests. Coturn
on TrueNAS/elsewhere is a later provider/configuration adapter if reachability, cost or operations
justify it, not a required parallel implementation now. Keep endpoint credential exchange neutral
so that change needs no control-packet or game-logic rewrite. Standard coturn credentials differ from
Cloudflare's issuing API; preserve this one small server boundary, not a general provider framework.
Current allowance/pricing is operational context, not a performance assumption or room-size policy.

**Rust's required networking responsibilities are limited to:**

1. Serve pinned bundles and resolve/create the existing room code/URL/QR locator; bind realm/build.
2. Authenticate host ownership, join/resume scopes and explicit replacement/revocation using the
   small durable registration record below. The host still grants seats and owns the live roster.
3. Route authenticated offer/answer/ICE and restart messages using HTTPS POST + SSE, one signalling
   stream per endpoint rather than one per pad; bound/expire obsolete negotiation data.
4. Issue/refresh temporary ICE configuration through the chosen provider and expose health and
   aggregate operational diagnostics. Keep long-term credentials out of browser bundles and reports.

It does **not** decode, batch or forward input/HUD samples, run an SCTP/DTLS gameplay endpoint,
step physics, synchronise extra displays, or write per-tick data. No per-input Rust request or
Cloudflare API call is permitted. Other named static/reporting functions remain separate. Signalling
loss affects new establishment/recovery; it does not by itself terminate a healthy peer connection.

`Hello` declares protocol/build/capabilities. A room is pinned to an immutable release and deployment
realm. Joining issues a stable controller/seat identity and assignment lease. Resuming changes the
connection epoch, not the car/score. Replacement atomically grants the new assignment and rejects
the old sender. Administrative host grants are separate from public join links.

The host authorises seat/source grants using client-proposed secret verifiers (§3.6). The service
validates room/realm/host-generation scope for signalling; the host also validates it on every
gameplay connection, since direct traffic does not traverse the service. A new join is an idempotent
request until the host accepts it; a lost reply cannot create two cars. Existing-seat resume requires
its secret capability, never SeatId/name/code alone.
Duplicate tabs must not share one live endpoint claim without arbitration: a fresh connection fences
the old one, and replacement of a still-active physical source is explicit. Host-local pads/keys
enter the same worker command validator directly; they need not round-trip through the network.
Connection establishment alone is not a seat claim. Fence stale controller connections and host
generations at the endpoints; TURN connectivity never grants game authority. Explicit host transfer
requires the service to commit a new generation; old-host recovery cannot reclaim it silently.

**Restart-safe registration:** persist only room locator/build/realm, host credential verifier,
current host generation, recovery verifier, CredentialRevision, lifecycle request receipts and
ended/revoked status in a small server control record. Use atomic
compare-and-swap for reconnect/replacement, with retryable request IDs; return a fresh bridge nonce
after restart. Route tables remain ephemeral. A stale host must not regain authority just because
the registration service restarted or rolled back its process. Registration writes happen on
lifecycle boundaries, not input ticks, and do not depend on the Full ancillary reporting database. A missing/corrupt control
record fails visibly into recovery rather than accepting an unverifiable old host. Back up that
record; a stale backup cannot be brought online without invalidating affected grants or reconciling
the latest fencing generation. Test reconnect races and Disband followed by server restart.

For Minimum, `RegistrationStore` is a dedicated `jj-server` interface backed by per-room durable
files, independent of the Full reporting DB. One server process owns the backend volume, with an
exclusive writer lock. Lifecycle CAS serialises writes, writes a checksummed versioned temporary
record, flushes and atomically replaces it, then confirms durability before acknowledging a new
host epoch/revocation. Qualify crash points and filesystem semantics on the actual mounted volume;
an unqualified mount fails service readiness. Multi-writer/replicated service needs a real shared
CAS store later, not a second process guessing from the same files. Persist pairing/recovery verifier
scope needed for server restart; socket routes remain ephemeral. This concrete first adapter keeps
reporting storage from becoming a hidden prerequisite of every join.

Continuous input/HUD/snapshots are supersedable state; discrete actions and durable commands have
IDs, acknowledgements and idempotency. Handle sequence wraparound, stale actions, neutral re-arm and
old round/vehicle-life references explicitly. Apply accepted gameplay input at a recorded simulation
tick. A pressed action cannot disappear merely because its containing sample was coalesced.

Keep transport queues fresh by replacing obsolete state, separating bulk reports/media from input,
and giving each channel fair service. Parser/credential validation is required, but no participant
count, aggregate message-rate setting or queue configuration may become a concealed room-size cap.
Do not promise zero latency: measure source-to-apply and visible response on the advertised public
path. Malformed traffic handling is not a reason to refuse valid additional players.

**Message meaning selects delivery, not one global reliable/unreliable switch.** Start with two
small data channels per controller endpoint (hub sources share that endpoint, retaining independent
source sequencing): `state` is unordered with zero retransmits; `commands` is reliable and ordered.
These are transport classes, not player-count limits. Controllers never choose networking modes in
the UI. Delivery class belongs to the protocol message, so game logic does not branch on provider
or selected direct/relay path:

| Message class | Initial delivery policy | Application correctness |
|---|---|---|
| Continuous stick/held state and disposable HUD updates | `state`: `ordered: false, maxRetransmits: 0` | Send complete state per included source, with connection-bound identity and increasing source sequence. Drop older arrivals; coalesce unsent samples; repeat current state at the qualified cadence. Freshness timeout neutralises input and invokes existing autopilot policy; lost release must not leave throttle/action stuck. |
| One-shot gameplay actions, e.g. fire or wheelie release | Small reliable command channel, initially ordered | Stable ActionId, round/life/assignment scope, prerequisite state/revision and host-validated expiry; host acknowledges applied/rejected, deduplicates retries and never executes an obsolete action after reconnect. Do not infer edges solely from a lossy held-state stream. Cancellation never becomes a release action. |
| Join/resume, Ready, choices, Leave and authorised room commands | Reliable command channel after establishment; HTTPS for bootstrap/signalling | Request IDs, idempotency, expected revision and application acknowledgement. Reliable delivery does not prove that the host applied or persisted a command. Order only within this channel; prerequisites across channels must be explicit. |

Reliable WebRTC data channels normally also use SCTP/DTLS over UDP; reliable does not mean TCP.
The initial two-channel policy is deliberately small. If measured action latency under loss needs
improvement, evaluate recent-action redundancy/application acknowledgement over the fresh-state
path without weakening deduplication/expiry; no custom reliability stack or FEC is required first.
See [WebRTC data channels, including UDP-like service](https://www.rfc-editor.org/rfc/rfc8831.html).

Observe `RTCDataChannel.bufferedAmount`, acknowledgement age and per-source fairness. Coalesce
**before** sending; bytes already queued cannot be replaced. Channels in one association share
congestion capacity, so separating them does not reserve bandwidth. Keep bulk reports/media off
the input association; there is no world/checkpoint stream to controllers. Use host-authorised
freshness windows/clock-offset estimates with uncertainty rather than raw cross-device timestamps.
On recovery rebaseline current state with a fresh epoch and replay only still-valid discrete
commands. Qualify reordering/loss, lost release/cancel, reconnect duplicates, stale commands, slow
consumers and real independent controller cohorts over direct and forced TURN paths. [S18]

### 13.3a Efficient controller and hub transport (required from Minimum)

**Optimise bytes, packets and input age together (R80).** The small protocol below is the initial
implementation, not a later scalability exercise. It applies to phone touch, gamepads, keyboard
clusters and hubs; source device details end at the normalised input boundary. `jj-protocol` owns
encoding and delivery-class metadata; `jj-input` owns shaping and latest state; the browser adapter
owns scheduling/queues. The Rust discovery service never handles these packets.

- **Compact, independently usable records:** binary fields, compact connection-bound source handles,
  quantised axes (start with signed 16-bit values), button/availability flags and per-source sequence.
  Validate neutral, full-range and threshold/edge behaviour after quantisation. Send a complete
  current record for each included source, not a dependency chain of deltas requiring retransmission.
  Do not resend player names, full UUIDs, room metadata, raw DOM events or physics state every sample.
  Omitted sources in a batch are unchanged, not disconnected; only their own refresh renews freshness.
- **Cadence:** sample input at the device/browser's useful cadence, flush changing state up to an
  initial 60 Hz and refresh unchanged available state at 20 Hz, as in §4.4. Coalesce noisy axes after
  calibration/quantisation; an unchanged source's refresh still carries its complete state. Sampling
  and sending are not coupled to 120 Hz physics or a 144/240 Hz renderer. Do not add the refresh rate
  on top of change sends. Promptly flush neutral/cancel/source-unavailable transitions and send
  one-shot commands without waiting for the next periodic batch; keep their cancellation/expiry
  semantics explicit. Existing full-state refresh and timeout recover a lost neutral transition.
- **Hub batching:** one connection and two channels per browser endpoint. Put all currently due
  source records into compact batches sharing an envelope; send more batches as necessary. Start
  around 1,000 application bytes per state message, below typical transport fragmentation sizes,
  and qualify actual browser packetisation. This is a message-size target, never a source-count
  limit. Fairly service every source without truncating arrays or waiting for every pad to change.
  Batch only records already due; do not add a long aggregation window. Each disconnected pad is
  reported independently even while other pads/keyboard clusters continue.
- **Fresh queues:** retain only the newest unsent state per source. Use `bufferedAmount` and low-water
  notifications plus an age budget to stop building stale queues. Prioritise neutralisation and
  short commands; resume with fresh state rather than bursting missed frames. Persistent congestion
  triggers truthful degraded/reconnecting status and the existing freshness policy. Never omit a
  participant, suppress valid actions or silently reduce physics fidelity to meet a byte target.
- **Small return path:** update HUD on change with lightweight periodic resync, batching per endpoint
  and piggybacking applied-input acknowledgements where useful. No reliable acknowledgement round
  trip is required before the next state sample or simulation step. Critical outcomes have reliable
  command acknowledgements; expiry/rejection is explicit. No full-world stream, redundant heartbeat
  service, media tracks, compression dictionary or RaptorQ encoder belongs on controllers.

**Initial efficiency target:** at most 2,000 application bytes/s per continuously changing source
for ordinary 60 Hz input state, counting its share of batch headers. Measure commands, HUD return
traffic, setup and transport overhead separately. This is a codec/engineering target, not a sender
quota: a failure requires explanation/tuning, never dropping valid controls or refusing more sources.
Start with the two channels above; consider reliable-unordered events, repeated action records or
different cadences only when real loss/latency traces show a net benefit worth their added ordering,
deduplication and debugging complexity. WebRTC already supplies congestion control and reliability.

For scale intuition only, an illustrative 8-byte envelope plus 16-byte source records gives the
following **input payload** rates at 60 Hz (decimal units; not measured or a final wire layout):

| Connected input arrangement | State messages/s | Input payload bytes/s | Input payload Mbps |
|---|---:|---:|---:|
| One phone/source | 60 | 1,440 | 0.01152 |
| Four independent one-source browsers | 240 | 5,760 | 0.04608 |
| One hub carrying four sources | 60 | 4,320 | 0.03456 |
| 48 independent one-source browsers | 2,880 | 69,120 | 0.55296 |
| Twelve hubs carrying four sources each | 720 | 51,840 | 0.41472 |

Unchanged-state refresh at 20 Hz is one third of those payload rates. Actual wire traffic adds
DTLS/SCTP/UDP/IP, acknowledgements, ICE/consent and any TURN encapsulation; tiny-packet overhead can
dominate. Batching saves packet overhead as well as envelope bytes, but measure the browser's actual
packets rather than assuming one `send()` equals one datagram. These cohorts illustrate scaling;
they are not supported-count limits. Lower bytes alone cannot justify older or missing controls.

**Qualification and playtest receipts:** use real independent connections as well as hub sources.
Report input sample-to-send delay, host-applied input age and action age (p50/p95/p99), RTT/jitter,
sequence gaps/reordering, stale-input/dropout incidents, payload bytes and actual wire bytes/packets
per direction, endpoint CPU/allocations and host ingress across growing cohorts. Record batching
delay and quiet/held/changing/button-burst cases. Measure scheduled state flush delay against a
one-60-Hz-interval target under healthy foreground operation; stalls are reported, never hidden in
an average. Browser stats do not universally expose wire-level totals or SCTP loss, so label counter
layers and unavailable fields; use controlled packet capture for overhead qualification. Never
equate application bytes with billed relay usage. Low-frequency aggregates go into the existing
playtest/diagnostic report, not per-tick logs or a new analytics database.

Log selected direct/relay candidate types, `relayProtocol` where available at both endpoints, and
path changes using the selected candidate-pair stats. A direct path is not proof of LAN locality;
claim LAN from the controlled test topology. Redact raw SDP/IP addresses/credentials/invitation
secrets from shared receipts. Observe connection success, join time, direct/relay fraction and
Cloudflare billed usage; don't assume that most parties will be direct until playtests show it. [S20]

Minimum tests: trusted same-LAN Wi-Fi and Ethernet↔Wi-Fi, mixed phone/desktop browsers with mDNS,
host-local and remote hub sources, cross-network/cellular, client-isolated Wi-Fi, forced TURN/UDP,
UDP-blocked TURN/TLS, loss/jitter/reordering, one unplugged pad, expired/refreshed credentials and
signalling outage with an already-established direct connection. Test the direct LAN path with
Cloudflare configured as in production; investigate avoidable relay use. All-path failure is an
honest connection error/retry, not a promise that TURN defeats every firewall. Offline room creation
remains deferred even when an established local connection survives loss of Internet access.

### 13.4 Browser placement and state publication

Main-thread responsibilities: source adapters, pointer/pad lifecycle, WebRTC/signalling I/O, DOM/UI,
Three.js scene, audio and snapshot interpolation. Worker responsibilities: own the authoritative
simulation tick/accumulator and serialised gameplay/round commands. Browser storage callbacks return
commit outcomes to the session reducer; membership/results are durable boundaries, physics input is
not a database transaction every tick.

Exchange reusable typed buffers with sequence/tick stamps. Publish a bulk snapshot, not one
JS↔WASM call per wheel/contact. A dropped presentation snapshot never drops physics input or a game
event. Previous/current snapshots support interpolation; discontinuities such as respawn use a cut.
The worker owns its scheduling while active; main-thread lifecycle messages and a freshness handshake
prevent it running a hidden host. Rebase both adapters when a frozen browser resumes unexpectedly.
A worker cannot outlive an OS-suspended/discarded page by assumption.

Define the worker ABI before rendering grows: version, session/round revision, tick, simulation time,
pause state, entity/life IDs, transform/wheel state, damage stage and input/action acknowledgements.
Pair snapshots from the same round/life using their timestamps; allow non-adjacent published ticks.
Choose a presentation delay sufficient to bracket interpolation and clamp at the latest completed
state if the worker falls behind; do not extrapolate collisions or interpolate across respawns.
Publish at a measured presentation cadence independently of 120 Hz stepping.

Transfer pooled ArrayBuffers with explicit return/ownership; transferring detaches the sender's
buffer, so never transfer Rapier/WASM linear memory itself. Grow packet capacity for actual entities. [S17]
If no buffer is returned, skip obsolete *presentation* publication rather than allocating an unbounded
queue or blocking physics. Reliable entity/session revisions and ordered event batches have their own
acknowledgements; on a consumer gap, send a complete current baseline and discard stale audiovisual
cues. Authoritative scoring already consumed the facts in the worker. Replay continuity is tracked
separately (§10.4), so a renderer stall cannot silently corrupt scores or manufacture a highlight.

Use transferables first. SharedArrayBuffer/cross-origin-isolated threading is a later measured
optimisation, not a join condition. Replay/procgen work yields to live simulation and rendering.
A paused host may still service membership/help, but cannot accumulate gameplay time or fire held
weapons on resume. Multiple pause reasons compose; clearing visibility does not clear manual pause.

### 13.5 G-SIM: qualify the selected Rust core

Measure native and WASM scenario throughput, worker snapshot cost, gameplay latency, thermal drift
and actual frame pacing. Native and WASM use the same rules, profiles, seeds and applied-tick inputs.
Exact hashes are required on a qualified same-target build; native↔WASM tolerances/bit identity are
separate tested claims. Pin physics revision/features, dt, map/profile hashes and ordering.

Use full authoritative state hashes for same-target reproducibility, including RNG, pending effects,
damage/progress and control state. Quantised transform-only hashes are useful diagnostics, not proof
of identical simulations. Qualify Rapier's `enhanced-determinism` and the actual selected features;
canonical initial geometry and deterministic math outside Rapier matter too. Do not infer cross-target
bit identity merely from a shared Rust crate or a passing one-car trace. [S15]

**Owner-gated display replication comparison (§6.6a; G-SCREENS).** Do not run or implement this
comparison as part of G-SIM, Minimum/Full, or automatic post-playtest work. Only after explicit
owner approval of this scope, replay the same crowded race, collision burst,
sleep/wake and growing-debris traces through packed absolute snapshots, acknowledged delta snapshots,
and a complete checkpoint plus applied-command replica. Keep camera coverage, visual precision and
displayed input age comparable. Report steady/p95/burst wire bytes including acknowledgements,
transport/TURN overhead, lifecycle traffic and amortised baseline/checkpoint repairs; also report
host encoding, receiver decoding/full-simulation CPU, memory, thermal behaviour and join/catch-up time.
Exercise LAN and relayed latency, jitter, packet loss, missing baselines and background/resume.

Separate changed-body count from total resident bodies. An illustrative 30 Hz stream averaging
10 bytes per changed body plus a 1,000-body change mask costs about 2.43 Mbps when all 1,000 change,
or 0.27 Mbps when only 100 change; sparse IDs can change that result. These are arithmetic assumptions,
not a proposed codec or achieved rates, and exclude other traffic. Do not count sleeping-body savings
twice when comparing against an estimate that already included only moving bodies. Compare against
an equally compact command log, including its checkpoints and loss repair. Extra displays never
backpressure host physics; no sampled player/debris cohort becomes a gameplay cap. Choose a default
from these measurements; supporting both receiver modes is an explicit maintenance cost.

Delete the old rule “stay in JS unless a laptop sweep exceeds five minutes”. Architecture is chosen
for clean authoritative ownership and deployment flexibility, not an arbitrary sweep cutoff. Rust
is not claimed faster for every workload; evidence determines layout/implementation optimisation.

### 16.2a Isolation and retention (R52 clarified, R72)

Each preview gets its own server container, configuration, secrets and ancillary-data volume.
**Origin isolation is between production and previews (R72 clarified):** production runs on
`jammers.dilger.dev`; all previews share `jammers-preview.dilger.dev`. Host-only credentials, explicit
allowed origins, no parent-domain (`.dilger.dev`) cookies and no service worker spanning previews.
Previews can never read or write production credentials or data. Between previews, isolation is by
separate backend containers/databases plus build-namespaced browser storage keys; that's acceptable
because previews are all ours, throwaway and rebuildable. If a preview ever needs full origin isolation,
it can be given its own first-level hostname (config only).

Namespace preview credentials and browser stores by immutable deployment ID **and** build/room, not
build alone: two backends may run the same bytes. Cookie paths/names must not collide, but paths are
not a security boundary between same-origin previews. Validate the realm/audience on every grant;
no production parent-domain cookie or origin allowlist wildcard may undermine R72.

The reconciler applies this ordered policy hourly and on publish:

1. Owner-pinned previews survive until explicitly unpinned.
2. The latest preview survives regardless of age.
3. Other unpinned previews older than 24 hours expire.
4. Retain at most the three newest unpinned previews; pins are additional.

Publishing/removing is idempotent. Preview UI shows expiry and build; pin an active review that must
survive expiry. Before deletion, preserve required bug reports/owner feedback as evidence artefacts.
Stop/remove container, route and disposable volume; retain the registry/evidence record. Restore
from the immutable candidate where available. A source rebuild restores software, not deleted data.
Expired preview links explain expiry and offer stable/index navigation, rather than a broken socket.

The **three-preview policy is explicitly authorised**, unrelated to forbidden gameplay/player caps.
Infrastructure headroom checks apply to deploying containers, never to admitting another player.
