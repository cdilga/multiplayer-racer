# Owner direction for Joystick Jammers 0.2 (2026-09-29)

**Status:** normative. Implementation agents, bead authors and reviewers must follow this document.
The full rationale lives in `docs/plans/v0.2-revamp-plan-2026-09-28.md` (rulings R1–R94). What the
first playtest builds, and in what order, is `docs/plans/v0.2-playtest-1-plan.md` (the bead source
for the Minimum build). The design brief is `docs/plans/v0.2-experience-direction.md`.

## Precedence

1. The latest explicit owner ruling (this document and the plan's rulings table).
2. The v0.2 plan and the policy/design contracts it references.
3. Reconciled beads.
4. Existing code, tests and older docs.

A bead, test or older doc **cannot override** a ruling. If a bead, an old test or an older section of
`AGENTS.md`/`README.md`/`docs/` contradicts this document, this document wins. Flag the conflict; don't
"fix" the ruling to match the code. Existing code is evidence to inspect, not a constraint.

## Hard rules (short form)

| Area | Rule |
|---|---|
| Separation | Joystick Jammers is completely separate from Physical Soccer: no shared code, crates, repos, deploy repo or imports. Borrow ideas only. (R1) |
| Server | Rust replaces the Python game server from day 0; Asupersync, no Tokio. Python stays for Blender/offline tools only. (R2) **Licence (owner, 2026-10-03):** Asupersync's MIT + OpenAI/Anthropic rider is accepted, GPL-3.0 position included. **Approved absolutely and finally: R112 (2026-10-04).** The opaque-dependency handling is lifted (R115, 2026-10-07): any agent may read, build and test it. |
| Simulation | Authoritative game simulation is Rust (`jj-sim`, native `rapier3d`) compiled to WASM for the browser host and native for tests/tools. 120 Hz game time, interpolated rendering, named composable pauses. (R61, plan §13) |
| **No caps** | **No arbitrary gameplay-count limits anywhere**: players, seats, controllers, tiles, fielded cars, live debris. No temporary/MVP/intermediate limits, queues, truncated arrays or count-triggered refusal. Test cohorts are samples, not limits. (R36, R47, R66) |
| Debris | Detached parts and fragments stay **dynamic** bodies for the round (sleep/wake allowed). Never convert to static, delete oldest, merge or budget by count. A wrecked car's **husk** stays too, as a dynamic body on the track or in the derby arena, with no despawn during the round (owner confirmed 2026-10-03, Q-A2). (R58) |
| Replays | No live killcam/PIP/interstitial. Highlight reels play after a round. Stored replay capacity *is* a permitted memory budget; it never limits live play. (R57, R67) |
| Controls | Two big joysticks (R116, superseding R60's layout): left stick **drive** (throttle up, brake/reverse down, deep pull-release wheelie; **drift left/right** sideways behind an angular deadzone; **boost** = the wheelie launch: full pull back then a snap to full forward, on a cooldown), right stick **aim** (**steering** on its x axis; **weapon forward/back** by a deliberate flick up/down). Sticks keep the circle; while drifting, throttle reads the left stick's magnitude. No tap-to-fire, no accelerometer/flick boost. Real tutorial. (R60, R116) |
| Phones | One phone = one player on its touchscreen. A second player on the same phone only via an external controller plugged into/paired with it (own seat). (R65) |
| Dropout | Controller dropout never pauses the room; a visible weak autopilot takes over. Host backgrounding pauses/resumes the same simulation. (R45, R59) |
| L-plates | Visible L-plates. Learners may win, but get a reduced payoff from advanced mechanics (boost, drift, wheelie/hop). No speed cap or forced losing. (R64) |
| Late joins | Race entrants join last, a few seconds behind the last racer. Derby: 3 min, raw points; late joiners are allowed to be disadvantaged. (R56, R63) |
| Dependencies | Runtime assets/libraries remain self-hosted: no runtime CDNs, remote fonts, model hosts or decoder downloads. Start from current stable releases, pinned and qualified. Cloudflare STUN/TURN is an explicitly allowed managed connectivity service, not an asset-CDN exception. (R70, R76, R79) |
| Hosting and transport | Rust HTTPS discovery/room/signalling service; **WebRTC controller ↔ host gameplay from the first multiplayer slice**. Prefer direct LAN where viable, with trickle ICE and Cloudflare standalone STUN/TURN initially. No SFU, mandatory WSS gameplay fallback, per-input Rust hop or coturn deployment prerequisite. Offline bootstrap remains deferred; local gameplay paths are core scope. Runtime player-name TTS is shelved. (R69, R71 amended by R77/R79) |
| Input efficiency | Compact binary state, fair hub batching on one connection per browser endpoint, bounded-age queues and a simple two-channel delivery policy are required from Minimum. Measure bandwidth, packet overhead and latency for phones/pads/keys/hubs; preserve every source and loss-safe release/reconnect. Complexity increases only with evidence. Playtest direct/relay incidence and Cloudflare usage before considering self-hosting. (R80, plan §13.3a) |
| **One screen first** | Minimum and Full focus on one excellent shared display. Additional consuming screens are a **high-effort, low-near-term-reward, separately owner-gated project** (G-SCREENS), not ordinary Stretch or automatic post-playtest work. Extra arenas/modes/themes and release do not depend on it or authorise it. No multi-screen implementation or replication spikes until the owner explicitly approves that scope. Preserve small boundaries, not speculative infrastructure. (R78) |
| Previews | Production on `jammers.dilger.dev`; all rainbow previews on `jammers-preview.dilger.dev/p/<id>/`, each with its own backend. Keep latest + pinned + the 3 newest unpinned; other unpinned expire after 24 h. (R52, R72, R73, R118) |
| Builds | Use RCH for heavy builds/tests/sweeps; record receipts. (R35) Use every machine with spare CPU (R93, below). |
| **Vehicle modelling** | Canonical method: per-tier reference sheets → silhouette masks/measurement → three.js model script (faceted at every tier, one code-drawn atlas, very lean triangle budget) → silhouette-IoU scoring + regularised optimiser → by-eye cue pass → bake to the contract. Skill `lowpoly-model-from-refs`; evidence `spikes/art-pipeline/J-cruze-lowpoly/`. Blender is not the vehicle path. (R81, amends R54) |
| Damage parts (interim) | For now: `front`, `back`, four doors, four wheels; the rest is core. **Each part goes intact → loose → detached; no denting** (R86 amends R82). Loose = visibly hanging/wobbling on its hinge while still attached; detached = a dynamic body left on the track for the round. In Playtest 1. The fuller §8.1/§8.2 anatomy is a later target. (R82, R86) |
| Host recovery (deferred) | Emergency host replacement, recovery export/import, registration CAS, credential revision, host checkpoint/restore after host death, explicit device handoff and the paired host-control phone are **deferred, possibly forever**. A dead host ends the room. A controller still resumes its own seat on the same device, and a host re-registers its room after a server restart. Possible drive-by only if G-SCREENS is ever approved. (R84) |
| Continuous previews | **No dev freeze for playtests.** Rainbow previews ship from the first deployable slice and keep shipping; a playtest is a preview the owner **pins**. A preview index at `https://jammers-preview.dilger.dev/` lists every preview newest first, with what changed, smoke status, pin/expiry and Host/Join links. (R85) |
| TURN (R88) | Self-hosted coturn at `turn.dilger.dev` first (UDP only, REST credentials, private peers denied) behind a narrow geo-restricted FortiGate UDP VIP; Cloudflare TURN is the TCP/TLS and overflow fallback. Everything else stays on Cloudflare tunnels. `docs/infra/turn-and-previews.md`. (R88 amends R79) |
| Audio (R89) | Announcer = the owner's voice cloned with Qwen3-TTS 1.7B on eris (FrankenWhisper transcripts); music = YuE2 at full precision on eris, instrumental only. Highest quality wins; weights/recordings never in the repo. (R89 amends R13/R19/R55) |
| **Validation in the loop** | Every part of the game is introspectable as structured data, settable, steppable/replayable and fixture-testable by agents. Capability required; design is the implementer's call. (R90) |
| Coordination | NTM paused; native Claude Code agents and messaging; Agent Mail for reservations and the commit guard. (R91) **No limit on the number of agents**; agents are fungible generalists that pick work with `bv` (no assigned tracks or roles); a session may pursue a goal spanning several beads. (R93, 2026-10-03) Modes, in the order the owner scales: **solo** (one session does the whole lot and the owner cranks it), then **2**, then **4 workers**, each closing its own beads on green CI, with a **verifier on call** (on demand only, no timers). Any verifying session **registers with Remote Control** so the owner can watch. Workers and solo run Opus 5.5 at medium effort and delegate mechanical work to Sonnet 5.5 subagents; the verifier runs Sonnet 5.5. **Lean by default:** no routine review rounds; the bead is the contract; small outputs. **NTM is back as a launcher (owner, 2026-10-03):** NTM panes may run workers, including OMP on GLM-5.3 at max thinking (`ntm spawn multiplayer-racer --omp=N:zai/glm-5.3:max`), never with `--worktrees`; OMP workers use the `am` CLI for Agent Mail. |
| Cloudflare TURN (R92) | Fallback enabled with an **accepted, bounded** billing risk: lazy issuance on relay-fallback requests with per-room/IP limits, spend guard (alert 10 %, delete keys at 25 % of the free 1,000 GB), CF budget emails. Issued credentials can't be revoked, so no zero-charge guarantee. HA push approved for this alert only; nothing else may depend on Home Assistant. Issuance goes through one `turn-broker` that alone holds the Cloudflare token (approved 2026-10-02; Playtest-1 plan §5.3). (R92) |
| 0.1 code | The 0.1 code was removed from the `v0.2-revamp` branch on 2026-10-02; read it with `git show v0.1-final:<path>` (tag on `main` @ `bbadc3e`). Production stays 0.1 on `main` until 0.2 is promoted. Nothing is ported as code; useful cases are re-expressed as 0.2 tests (Playtest-1 plan §14). (R87) |
| Procedural biomes (R83) | First playtest has all four biomes (town, rocks, outback dirt, outback bitumen) at deliberately minimal variation; breadth comes after the playtest. One seed/terrain core cut, then four parallel biome cuts; derby is separate with rocks vibes. Signs: Wikipedia *Road signs in Australia* is the style source; new/joke signs are allowed if they follow a real sign family's grammar (e.g. yellow diamond "BLOODY BIG JUMPS AHEAD"). Plan §11.5a. 2026-10-02: the seed/RNG and course-graph core may start before G-PROCSPIKE; the rest of the core follows the spike's recommendation, which the owner reviews when convenient rather than as a gate (Playtest-1 plan Q-P1, §15.0). |
| Worker loop (2026-10-02; model 2026-10-03) | Workers get the full development loop: debug, inspect game state, run local and multi-device setups and servers, write and run e2e tests, and iterate on mechanics and models (with visual inspection) until they work. **Since 2026-10-03, Physical Soccer's model:** a session checks its own area, pushes, and closes its own bead once Gitea CI is green on a commit containing it, citing the run; a verifier on call (on demand, no timers) handles hand-offs, red CI and evidence closes. Favour Physical Soccer's test style (scenario banks, journeys) over many unit tests. `docs/process/bead-workflow.md`. |
| Owner feedback never blocks (2026-10-02) | No bead waits on the owner except two gates: the design POC verdict (G-DESIGN, below) and the Playtest-1 qualification itself. Where the owner's eye matters (procgen direction, voice, music, feel, looks, Windows or Mac Safari hosting), work proceeds on its best evidence-backed candidate, the owner judges it at a playtest or when convenient, and a "no" becomes a repair bead (Physical Soccer's habit). |
| **Design POC (G-DESIGN, 2026-10-02)** | Before the UI is built, a POC stage settles the design guide and tokens and mocks the TV grid (players joining and leaving, grids with a gap, first- and third-person tiles mixed, the per-tile HUD), the lobby at 32 players, results, the controller on real phone sizes (plus a live mock on the owner's phone), the in-world look with the real car, motion, brand and components, and derby's shared Overview screen as a design reference (derby itself stays Full). It presents one worked proposal per question, not options on obvious things (2026-10-03); the owner redirects what needs changing. Like a playtest, but it **blocks on the owner's feedback**: the UI and presentation tasks wait for its verdict, so they don't backtrack. Everything else proceeds in parallel. Playtest-1 plan §3a, tasks P1-U01–U04. |
| UI and style references (2026-10-02) | The **H4 round-highlights image** (`docs/plans/ux-study-2026-09-29/images/H4-host-round-results-v2.png`) is the most authoritative style reference. The ute with the bullbar (H1/M1) shows the direction for the wider roster: more vehicles and locations are planned, and Playtest 1's reduced scope (one car, four biomes) de-risks the hardest parts first. The ultra-cartoony look with drivers' heads out of the cars (`art/style/refs/ui_lobby.png`) is mostly superseded by the newer vehicle spikes. Brand badges added by image generation are placeholders and never ship. |
| One shared tree, shared runners (2026-10-02) | No git worktrees or extra clones for agents: one shared working tree, coordinated through native Claude messaging and Agent Mail file reservations (worktrees caused an integration nightmare). Remote per-run directories are only for non-code outputs. All Gitea runners are shared across the owner's projects, deploy runners included; the security trade-off is accepted for these projects. **2026-10-03:** eris keeps a clean, read-only clone synced from pushed commits by `ru` (Jeffrey Emanuel's Repo Updater) for compute; agents never edit there. |
| Compute (2026-10-03, R93) | Use every machine with spare CPU for maximum speed: the shared Gitea runners on TrueNAS, devbox (the RCH worker, a VM on triton; its build storage moves to triton's pool, terabytes free once the resilver finishes), triton's Gitea runner, the Mac and eris whenever it's on. Nothing is pinned to a machine except what hardware dictates: the iOS Simulator needs macOS, a perf receipt is measured on the host it describes (the Mac driving the TCL, or a named reference row), and the R89 audio models live on eris. eris may run anything else, Android emulators and browser lanes included. |
| Weapon pickups (2026-10-03, R94; Full) | Every weapon pickup shares one recognisable shape: a cardboard delivery package/box with an image of the weapon inside printed on the outside, so players read the weapon at a glance while pickups stay visually one family. Reference art for the weapons and the pickup box is still to be generated through the art pipeline. |
| Derby slice (2026-10-03) | The first derby follows the pinned Playtest-1 build (plan §2.5, drop D6): one bowl arena with **passive containment** (walls and lip keep cars in; **no shrinking wall**), **won on damage dealt** (R56), with the Overview camera. A **last-man-standing** mode comes later, with a host switch for dropping in while a round runs; switching it off seats new players for the next round and is never a cap. |
| Items (2026-10-03) | Before the full test after Playtest 1: one weapon and one boost-type item, the **boomerang** and the **sanga** (sausage on bread: for a timed period you shrug off weapons and tank other cars, driving without worrying about their collisions). **Two items per player, used in the order picked up.** Pickups are delivery boxes printed with the item (R94). Other item ideas wait. |
| Effects and shaders (2026-10-03) | An emissive and particle pass (dirt, smoke, fire, contact and crash indicators, feedback wherever it makes sense) is part of the build, using expert three.js shader skills vendored for the agents. |

| Players and controllers (2026-10-03) | The host can remove a player (e.g. they've left the house). The **hub** (a second laptop with pads, a keyboard-only laptop, a phone with a pad) is explicitly supported **before Playtest 1**, with a small UI showing how each controller is connected. A controller's identity lets it reconnect properly, and it remembers the edited name. |
| Development capture (2026-10-03) | No analytics, but game state must be captured well for development (a session recorder). |
| Maps (2026-10-03) | No map export; keep the ability to import a designed map later through dev work. |

| R111 | **2026-10-04: the host renders at the display's native pixel resolution.** On a 4K TV at 4K (or any display at its own resolution, whatever CSS size and devicePixelRatio the browser reports) the world is drawn into the full physical pixel grid: every tile's backing store equals its on-screen size in device pixels, so the aggregate rendered pixels across the grid is the display's pixel count (3840×2160 on the reference TCL at 4K), and the owner expects the pixel density to be used. **The capacity to render at full native resolution must exist on every host, phones included** (a phone host draws at its own physical pixels, e.g. 1080×2340, not CSS pixels), within the browser's real limits (max canvas size, GPU memory), and the host says plainly when a limit stops it. A host **Render resolution** setting (Native, the default, then lower steps such as 75 %, 50 %) lets the owner or host choose less; choosing lower is fine and is the player's call. Any reduction the system makes on its own is only an automatic, **measured last resort** (a frame budget missed on that hardware), never a default, never because the tile or player count is high; the actual render resolution and whether it is native, user-lowered or auto-lowered is always visible in the host settings/overlay, and named in every perf and look receipt. Tile count never lowers tile pixel density by itself: a 24-tile grid on a 4K TV is 24 native-pixel tiles, each smaller on screen, and the ink, filtering and LOD respond to on-screen size (br-dim.3, br-dim.11). Extends R14/R15 and the no-caps rule. |
