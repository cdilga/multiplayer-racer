     - Estimated rect may use fixed bounds not matching actual rendered size
     - HUD element margins may be insufficient
     - Cache invalidation (120ms) may miss dynamic HUD changes
  
  2. **Chase camera culling**: z > 1 check may be incorrect
     - In THREE.js, z < 0 means behind camera, z > 1 means beyond far plane
     - Tight chase framing may legitimately cull 1-2 markers
     - Test expectation of >= 3 may be too strict for focused mode
  
  3. **Marker rect estimation**: Uses assumed dimensions, actual DOM may differ
     - Name length varies (affects width)
     - Font rendering differences across browsers
  
  4. **Race condition risk**: Multiple updates/frames before safe-area stable
     - Low risk for static HUD but noted

SPECIFIC FAILURE ANALYSIS

FAILURE 1: CHASE CAMERA MARKER VISIBILITY

Test: camera-modes.spec.ts line 21
Description: "can switch between party, chase, and hood views from the host controls"
Assertion: expect(chaseState.visibleMarkers).toBeGreaterThanOrEqual(3)
Failure: visibleMarkers = 2 (expected >= 3)
Context: 4 players, camera in chase mode focused on player 1

Root Cause Candidates:
  A) One marker behind camera (z < 0) - likely with tight chase framing
  B) One marker beyond far plane (z > 1) - less likely
  C) One marker off-screen due to tight viewport - possible
  D) One marker hidden due to overlap (non-preferred status) - less likely
  E) Test expectation too strict for focused camera - plausible

Severity: MEDIUM
- Chase mode is a focused camera mode; some marker culling is expected
- 2 visible markers is still useful for orientation
- Could be test expectation issue rather than implementation bug

Assessment: INVESTIGATE NEEDED
- Check if z-culling logic is correct
- Review chase camera FOV/position for tight framing
- Consider if >= 2 is acceptable vs >= 3 for focused mode


FAILURE 2: DERBY HUD OVERLAP

Test: game-flow.spec.ts line 347
Description: "host markers stay visible in 4-car derby without covering HUD or camera controls"
Assertion: expect(boxesOverlap(markerBox, occluderBox)).toBe(false)
Failure: At least one marker overlaps with at least one HUD element
HUD Elements: #race-timer, .hud-lap, .hud-health-bars, .hud-speed, #camera-controls

Root Cause Candidates:
  A) Safe-area detection missing an HUD element selector - unlikely
  B) Safe-area bounds calculated incorrectly - possible
  C) Marker rect estimation size too large or position wrong - likely
  D) Clamping logic failure (marker would clip, but stays positioned) - possible
  E) HUD elements dynamically resized during test - unlikely but possible
  F) Derby mode has additional HUD elements not in selector list - possible

Severity: HIGH
- Violates explicit acceptance criterion ("without covering HUD or camera controls")
- Players' own-car markers obscured during critical derby gameplay
- User experience impact: can't identify own car reliably

Suggested Fixes (Priority Order):
  1. Add console logging to _getSafeArea() to see computed bounds
  2. Add logging to clampMarkerPosition() to see actual clamp results
  3. Increase HUD safe-area margin by 8-16px
  4. Verify estimated rect dimensions match actual DOM rendering
  5. Check if derby mode adds HUD elements not covered by selector list

Assessment: BLOCKING - REQUIRES FIX BEFORE SIGN-OFF
