CORRELATION & PRIVACY REASONING
===============================

Correlation Strategy:
- roomAnalyticsId (opaque, server-generated): Groups all events for one game session
- matchId (UUID): Groups all gameplay events for one match (multi-round derby, laps in race)
- playerAnalyticsId (anonymous hash): Groups events from one session/device; derived from browser fingerprint
- release (git SHA/version): Correlates deployments and identifies version-specific issues

All 4 IDs are present in EVERY event and shared across host, controller, and server. This allows:
- Joining host/controller streams by matchId
- Tracking player behavior without names
- Linking to deployment versions for debugging

Privacy Enforcement:
1. **Proactive scanning:** TelemetryService.emit() checks FORBIDDEN_PATTERNS before queuing
2. **Specific patterns:** Regex scans for player names, IPs, tokens, socket IDs, room codes
3. **Bounded properties:** Max 500 chars/value, depth ≤ 2; prevents large payloads/nested structures
4. **Allowlisting:** Only 20 event names permitted; prevents arbitrary event spam
5. **Correlation IDs:** roomAnalyticsId and playerAnalyticsId are anonymous; raw codes/names never exposed

Correlation Fixture Evidence:
- 7 real-world-like events (host match start, lap complete, weapon; controller network error, perf sample; server room created, spawn validation)
- All events share 4 correlation IDs consistently
- All properties are bounded and privacy-compliant
- Roles (host, controller, server) represented
- Event types (gameplay, error, perf, server) represented

RESIDUAL RISKS
==============

1. **Runtime enforcement only at sender.** Privacy checks happen client-side; a malicious client could bypass. Mitigation: Receiver-side validation planned for Phase 2.

2. **No sampling enforcement in service.** Contract specifies sampling (1/60 frames, 1/100 steps) but TelemetryService doesn't implement it. Consumers must self-throttle. Mitigation: Documented; sampler helpers planned for Phase 2.

3. **Release value not format-validated.** Contract requires release but accepts any string. Low risk; release is app-provided, not user input.

4. **PostHog/Grafana SDKs not wired.** Intentional per scope: this bead defines contract only. Phase 3 (br-jj-observability-analytics-rkt.1) wires actual SDKs.
